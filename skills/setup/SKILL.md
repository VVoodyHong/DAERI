# DAERI setup

기본 응답은 한국어다.
`setup PROFILE`은 해당 profile의 세팅을 시작하며 이름이 없을 때만 이름을 한 번 받는다.
서비스 설명·보존기간·접속값은 질문하지 않는다.
접속값은 DAERI가 생성한 YAML에서 사용자가 입력한다.
기존 초안이 있으면 저장된 선택과 편집 내용을 유지하고 멈춘 단계부터 이어간다.
파일 작성을 마쳤다는 응답은 6단계의 검증으로 이어가며 시작·리소스 선택을 반복하지 않는다.

`../../`는 설치된 플러그인 루트다.
시작 전에 [선택·확인 문구](../../docs/spec/hosts/plugins.md#setup의-정형-질문), [환경 준비](../../docs/spec/installation/environment.md#아무-개발-도구가-없는-최초-진입), [YAML 계약](../../docs/spec/configuration/profiles.md#사용자용-setup-yaml)을 읽는다.
명령 실행은 [공통 관리 진입](../../docs/development/dependencies.md#관리-입력과-결과)을 따른다.

## 세팅 순서

1. 새 세팅은 profile 이름을 확인한 뒤 “DAERI 세팅을 시작할까요?”라고 묻는다.
   선택지는 “세팅 시작”·“중단”이다.
   버전·설치 위치·패키지 목록·내부 명령은 기본 안내에 넣지 않는다.
   중단하면 설정·설치를 진행하지 않는다.
2. 사용자 OS와 플러그인 루트를 확인하고 [최초 준비 절차](../../docs/spec/installation/environment.md#아무-개발-도구가-없는-최초-진입)로 실행 환경을 확인·준비한다.
   정상적인 미준비를 오류로 만들거나 전역 프로그램으로 우회하지 않는다.
   준비·교체 뒤 실제 MCP 재연결 여부는 별도로 확인한다.
   실행 모드에서 `profile list`로 기존 설정을 확인한다.
   [사용자 저장 위치](../../docs/development/dependencies.md#저장-위치와-데이터-역할)의 `setup/<profile>/setup.yaml`·`draft.json` 존재로 초안 재개 여부를 먼저 확인한다.
3. 기존 초안이 없을 때 `setup catalog`로 지원 리소스와 제품을 조회한다.
   “사용할 리소스를 선택해 주세요.”라는 복수 선택에 모든 범주를 동등하게 포함한다.
   각 설명은 “사용 가능한 제품: …”이며 실제 목록만 사용한다.
   Document만 따로 묻지 않으며 도구의 항목 제한은 같은 형식의 일반 분할로 처리한다.
   단일 선택 도구에서는 모든 범주에 같은 “사용”·“사용 안 함”을 제공하고 가능한 질문 수만큼 묶는다.
   선택한 범주의 제품이 하나면 그 제품을 선택하고 여럿이면 제품을 선택받는다.
   사용자에게 포트·어댑터·recipe ID를 선택하라고 하지 않는다.
4. 기존 초안의 기억 검색 선택을 우선 유지하고 초안이 없으면 기존 profile의 선택을 유지한다.
   둘 다 없을 때만 로컬 기억 검색·회사 임베딩 API·키워드 검색 중에서 선택받는다.
   주소·모델·전송 허용 등 세부 입력은 선택한 방식의 YAML에 담는다.
5. `setup draft PROFILE --resource INSTANCE=RECIPE`로 선택한 연결의 초안을 생성한다.
   여러 연결은 `--resource`를 반복하며 새 임베딩 선택은 `--embedding`으로 전달한다.
   기존 초안 재개는 `setup draft PROFILE`로 경로를 확인하며 선택 옵션을 다시 전달하지 않는다.
   반환한 `setup.yaml` 경로와 “파일을 작성한 뒤 알려 주세요.”만 안내하고 입력을 기다린다.
   이미 작성한 초안·기존 설정은 보존하며 필드마다 질문하거나 다른 입력 파일을 대신 작성하지 않는다.
6. 사용자가 작성했다고 하면 `setup validate PROFILE`로 파일 전체를 검증한다.
   오류가 있으면 필드 위치와 수정 안내만 보여 주고 같은 파일을 수정하게 한다.
   유효하면 반환한 변경 요약을 보여 주고 “이 설정을 적용할까요?”에 “적용”·“중단”으로 확인받는다.
   사용자가 적용을 선택하면 그 검증이 반환한 `confirmation_token`으로 `setup apply PROFILE --confirm TOKEN`을 실행한다.
   충돌·파일 변경은 다시 검증·확인하며 최신 개정이나 확인값으로 몰래 바꾸지 않는다.
7. 적용한 연결만 `resource prepare`로 준비하고 [보안 입력](../../docs/spec/configuration/profiles.md#인증-저장과-전달)으로 인증한다.
   비밀번호·토큰은 YAML·채팅·질문창·명령 인자에 넣지 않는다.
   `auth set`의 숨김 입력은 사용자의 실제 터미널에서 받으며 제공자 로그인은 지원 명령으로 진행한다.
   준비 범위가 바뀌거나 추가 권한이 필요할 때만 이유를 설명하고 확인받는다.
8. `resource diagnose`와 [선택한 기억 검색 준비](../../docs/spec/installation/environment.md#임베딩-선택과-준비)를 진행한다.
   회사 API·키워드 검색에는 로컬 모델을 설치하지 않는다.
   실패한 단계와 다음 조치를 안내하며 저장한 정상 설정을 지우거나 다른 제공자로 바꾸지 않는다.
9. profile 저장·리소스별 연결·기억 검색·현재 MCP 연결을 각각 짧게 보고한다.
   확인하지 않은 항목을 성공으로 채우지 않는다.
   이름·식별자를 확인한 profile을 [대화의 선택 대상](../profile/SKILL.md)으로 안내하고 업무는 [work](../work/SKILL.md)로 이어간다.

## 질문과 실행 경계

선택·확인은 현재 호스트의 질문 도구를 사용하고 필드 입력은 YAML로 받는다.
질문 도구의 실제 스키마·모드 제한은 [호스트 계약](../../docs/spec/hosts/plugins.md#setup의-정형-질문)을 따른다.
응답 누락·사전 선택·시간 경과는 동의가 아니다.
파일 작성·적용·설치·로그인은 실행 가능한 모드에서만 수행한다.

명령은 전용 실행기의 절대 경로와 분리한 인자로 전달한다.
출처·인증서·조직 정책을 끄거나 사용자의 PATH·shell 설정을 변경하지 않는다.
세팅 동의는 업무 계획 승인이 아니며 일반 업무가 숨은 설치·설정 변경으로 전환되지 않게 한다.
