# 환경 준비와 배포

상태: 설치·배포 요구사항 확정 + 준비·갱신·복구 설계 제안

개발 도구 없는 PC의 준비·배포·갱신·복구를 정의한다.
호스트 연결은 [플러그인과 실행](../hosts/plugins.md), 리소스·인증 설정은 [사용자 구성](../configuration/profiles.md)이 정본이다.

## 설치 조건과 의존성 범위

사용자 PC에는 Codex 또는 Claude Code만 준비되어 있다고 가정한다.
필요한 프로그램의 실제 경로·지원 버전·필수 기능을 확인하고 없으면 준비할 수 있어야 한다.
macOS를 먼저 구현·검증하고 Windows도 같은 흐름을 지원하도록 설계한다.

profile 없이도 코어·설정 관리를 시작하고 선택한 MCP·인증에 필요한 의존성만 추가한다.

| 역할 | 현재 후보 | 필요한 조건 |
|---|---|---|
| 호스트 | Codex 또는 Claude Code | 사전에 설치된 호스트의 플러그인·MCP 기능 확인 |
| 최초 진입 | OS 기본 도구 또는 독립 배포물 | Python·Node.js·uv·Git이 없는 환경 |
| 환경 준비 | uv | 사용자별 Python 준비 방식으로 채택할 경우 |
| DAERI 실행기·상태 저장 | Python + 공식 MCP SDK + SQLite | 해당 코어 방식을 채택할 경우 |
| 승인 | 로컬 브라우저·WebAuthn 인증기와 검증 라이브러리 | [승인 경로](../hosts/approval.md)의 지원 조건 |
| PostgreSQL | Node.js + Bytebase DBHub | profile에 DBHub stdio 연결이 있을 경우 |
| Redis | Python + Redis 공식 MCP | profile에 Redis stdio 연결이 있을 경우 |
| AWS | Python + MCP Proxy for AWS의 CLI 배포물 | profile에 AWS 관리형 MCP 연결이 있을 경우 |
| AWS 로그인 | AWS CLI | 선택한 인증이 CLI SSO 로그인 등을 요구할 경우 |
| GitLab | DAERI의 HTTP MCP client·OAuth 기능 | GitLab 공식 원격 MCP 연결이 있을 경우 |

코어·지원 버전은 아직 후보이며 MCP 제품 선택은 [최초 연동](../resources/initial-adapters.md)이 정본이다.
GitLab에 Node.js 브리지를 전제하지 않고 AWS CLI는 선택한 인증 방식에만 요구한다.

PostgreSQL·Redis 서버, Docker·Git·Homebrew·WSL·컴파일러는 공통 필수가 아니며 원격 서버 설치·변경을 로컬 준비에 포함하지 않는다.
Git은 선택한 배포 경로·소스 변경 기능에서 필요할 수 있다.

AWS 프록시는 [공식 CLI 배포물](https://github.com/aws/mcp-proxy-for-aws)을 검토한다.
SQLite 후보는 별도 서버·CLI의 존재 대신 실제 Python의 [sqlite3 모듈·라이브러리](https://docs.python.org/3/library/sqlite3.html)와 필요한 기능을 확인한다.

## 버전과 재현 가능한 환경

프로그램·지원 버전·조건별 역할·플랫폼·검사 방법은 구현 단계의 단일 dependency 목록에서 관리한다.
버전 숫자를 명세마다 반복하지 않고 실제 설치 결과와 구분한다.

Python·Node.js 패키지는 표준 잠금 파일을 사용하고 OS 런타임에는 출처·배포물·무결성 정보를 연결한다.
자체 패키지 관리자·별도 전이 의존성 manifest·lock 스키마는 만들지 않는다.

관리 환경은 검증한 잠금 정보와 일치시키며 기존 도구는 지원 범위·필수 기능을 확인한 뒤 재사용한다.
재사용할 수 없으면 기존 설치를 덮어쓰지 않고 사용자 환경에 별도 준비한다.

임의 최신 버전·미러로 전환하지 않고 온라인·오프라인 모두 신뢰한 배포 정보의 해시·발행자를 실행 전에 확인한다.

## 아무 개발 도구가 없는 최초 진입

Python·uv 사전 설치 없이 독립 런처·setup으로 진입한다.
Git 부재와 비공개 저장소 인증은 [최초 배포](#배포-출처와-최초-전달)에서 다룬다.

| 항목 | macOS 우선 설계 | Windows 대응 |
|---|---|---|
| 진입 | 독립 실행물; 필요 시 기본 shell·다운로드 | 독립 실행물; 필요 시 PowerShell·다운로드 |
| 플랫폼 | Apple Silicon·Intel과 실제 OS 확인 | ARM64·x64와 실제 OS 확인 |
| 실행 | 확인한 절대 경로로 호스트 등록 | `.exe`·명령 형식을 확인하고 절대 경로로 등록 |
| 설치 위치 | 사용자 전용 환경 | 사용자 전용 환경 |
| 정책 차단 | 서명·Gatekeeper·회사 정책 안내 | 서명·실행 정책·회사 정책 안내 |

OS 도구도 실행 가능 여부를 확인하며 사전 빌드가 없는 플랫폼에 컴파일러·Homebrew·WSL 등을 자동 추가하지 않는다.
지원할 수 없으면 부족한 배포물·정책·사용자 조치를 안내한다.

[uv 독립 설치](https://docs.astral.sh/uv/getting-started/installation/)와 [설치 위치 옵션](https://docs.astral.sh/uv/reference/installer/)은 Python 없는 사용자별 준비의 후보다.
[Node.js 다운로드](https://nodejs.org/en/download)는 플랫폼별 사전 빌드와 무결성 확인을 위한 근거다.

## 검사·계획·설치

프로그램 검사는 배포물에 정의한 로컬 검사만 수행하며 모델·profile·하위 MCP의 임의 명령·URL을 실행하지 않는다.
원격 인증·진단은 [명시적 관리 등록](../configuration/profiles.md#관리-등록과-진단)으로 구분한다.

1. 호스트·OS·CPU·설치 위치와 필요한 의존성을 파악한다.
2. 실제 실행 경로·버전·필수 기능을 확인한다.
3. 누락·비호환 항목의 출처·설치 위치·권한·영향과 복구 방법을 표시한다.
4. 사용자가 확인한 준비 범위 안에서 새 환경을 별도 위치에 구성한다.
5. 무결성·기능·호스트의 실제 MCP 시작을 확인한다.
6. 성공한 환경만 사용 대상으로 등록하고 연결·인증의 대기 사유를 보고한다.

패키지마다 재확인하지 않으며 출처·추가 도구·권한·시스템 변경이 준비 범위를 벗어날 때 수정 계획을 보여 준다.
시스템 런타임·다른 프로젝트·shell 설정·AWS default를 덮어쓰지 않는다.

항목별 경로·관찰 버전·기능 결과·다음 조치를 기록하며 파일 존재·버전 문자열만으로 준비 완료를 선언하지 않는다.
누락·비호환·정책 차단·판단 불가를 구분한다.

GUI PATH 차이를 고려해 절대 경로를 쓰고 실제 호스트 시작 조건에서도 검사한다.
공백·한글 경로는 실행 파일·인자를 분리해 처리한다.

코어 검사는 임시 저장소에서 수행하며 프로세스 시작 성공을 원격 권한·업무 데이터 접근 성공으로 취급하지 않는다.

## 설치 실패와 재개

잠금으로 중복 설치를 막고 새 환경은 별도 위치에 준비해 완료 검사 뒤 전환한다.
실패하면 기존 정상 환경·사용자 데이터를 보존한다.

재실행은 단계 기록·실제 파일·검사 결과를 대조해 필요한 단계만 수행한다.
외부 설치기 완료가 불명확하거나 정상 환경이 이미 있으면 무조건 재설치하지 않는다.

여러 profile은 배포 환경을 공유하되 [연결·인증 문맥](../configuration/profiles.md#구성과-연결)은 분리한다.
부족한 의존성만 추가하고 기존 업무를 새 환경으로 자동 이동하지 않는다.

## 배포 출처와 최초 전달

사내 GitLab·GitHub의 비공개 저장소·완전한 로컬 패키지로 배포하며 공개 마켓플레이스 입점을 필수로 두지 않는다.
저장소 인증·조직 출처 정책·호스트의 실제 다운로드 기능을 확인한다.

Git 없는 PC는 브라우저로 검증한 ZIP·릴리스를 받아 독립 setup 후 로컬 플러그인을 등록한다.
아직 받지 않은 플러그인의 hook이나 호스트의 Git 제공을 전제하지 않는다.

공통 코어·Skill에서 [호스트·OS별 패키지](../hosts/plugins.md)를 생성하며 라이선스·서명·다운로드·시작 경로를 검증한다.

## 업데이트와 데이터 보존

업데이트도 [별도 환경 준비·전환](#설치-실패와-재개)을 적용한다.
진행 중 업무는 [환경 고정](../hosts/plugins.md#재개동시-사용환경-고정)을 유지하며 재개 조건 확인 전 이전 환경을 제거하지 않는다.

업데이트·재설치·캐시 삭제는 [사용자 저장소](../configuration/profiles.md#사용자-저장-위치)의 설정·비밀 참조·업무·승인·호출·결과 이력을 보존한다.
사용자 간 데이터·비밀 이식은 [공유 경계](../configuration/profiles.md#변경공유복구)를 따른다.

저장 형식 변경은 기존 기록·호환성·복구 가능성을 검사하고 writer·신규 dispatch를 차단한 상태에서 진행한다.
미검증 구·신 코어의 동시 쓰기를 허용하지 않으며 미지원 형식·마이그레이션 실패는 실행을 차단한다.
백업 복원으로 호출·멱등 기록을 잃었을 수 있으면 외부 효과 확인 전 재실행하지 않는다.

동시 갱신·설정 변경은 저장소 잠금·개정 검사로 처리하며 별도 업데이트 서버·범용 migration 엔진을 추가하지 않는다.

## 회사 환경과 자동 준비의 한계

| 상황 | 처리 |
|---|---|
| 네트워크 실패 | 제한된 재시도 후 실패·재개 안내 |
| 사내 프록시·CA | 조직이 허용한 설정·인증서로 재검사 |
| 다운로드 차단 | 허용된 미러·검증 가능한 오프라인 배포물 검토 |
| OS·회사 정책 차단 | 필요한 사용자·조직 조치와 미완료 이유 표시 |
| SSO·OAuth·MFA 필요 | 사용자에게 제공자 인증 흐름 안내 |
| 원격 권한·제품 미지원 | 연결별 실패로 표시; 로컬 설치 성공과 구분 |

TLS 검증·Gatekeeper·ExecutionPolicy·회사 정책을 끄거나 우회해 완료하지 않는다.
도구마다 CA·프록시 적용 방법을 확인한다.
출처: [uv 인증서 설정](https://docs.astral.sh/uv/concepts/authentication/certificates/), [macOS 실행 차단](https://support.apple.com/guide/mac-help/open-a-mac-app-from-an-unknown-developer-mh40616/mac), [PowerShell 실행 정책](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies).

## 구현 전 확인

[초기 호환성 단계](../../plans/initial-implementation.md#1-호환성과-스택)에서 코어·런처·지원 프로그램·OS·CPU·dependency 관리 위치를 정한다.
Mac의 두 호스트에서 개발 도구 없는 최초 전달·MCP 시작을 먼저 확인하고 Windows에서 같은 계약을 검증한다.
공백·한글 경로·GUI PATH·관리자 권한 없는 계정·회사 제한과 중간 실패·중복 설치·오프라인 무결성·데이터 보존을 확인한다.
실제 다운로드·설치·갱신·호스트 시작·인증·리소스 연결은 아직 검증하지 않았다.
