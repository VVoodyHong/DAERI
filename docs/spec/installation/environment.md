# 환경 준비와 배포

상태: 명시적 환경 준비·준비 성공 후 MCP 등록 구현; 실제 호스트 설치·Windows 실행 미검증

개발 도구가 없는 PC에서 profile에 필요한 환경을 준비하고 유지하는 기준이다.
호스트 연결은 [플러그인과 실행](../hosts/plugins.md), 리소스·인증 설정은 [사용자 구성](../configuration/profiles.md)을 따른다.
선택한 연결의 [사용자용 setup YAML](../configuration/profiles.md#사용자용-setup-yaml)을 생성·검증·확인한 뒤 일괄 적용한다.

## 설치 조건과 의존성 범위

사용자 PC에는 Codex 또는 Claude Code만 준비되어 있다고 가정한다.
DAERI는 동작에 필요한 프로그램과 지원 버전·필수 기능을 검사하고 누락 항목을 준비할 수 있어야 한다.
macOS를 먼저 구현·검증하며 Windows도 같은 사용 흐름을 지원하도록 설계한다.

| 역할 | 필요한 조건 |
|---|---|
| 호스트 | 설치된 호스트의 플러그인·MCP 기능 확인 |
| 최초 설정 진입 | 설치된 호스트와 OS 기본 실행 기능으로 준비 시작 |
| 로컬 runtime | DAERI 실행과 사용자 설정·업무 기록 관리 |
| 로컬 저장 | SQLite·FTS5와 사용자 영역의 파일 저장·조회 |
| 기억 검색 | SQLite 벡터 확장의 호환성·로컬 저장 공간; 선택한 임베딩 제공자의 준비 |
| 선택한 리소스 연결 | profile에 등록한 어댑터·MCP에 필요한 프로그램 |
| 인증 보조 | 선택한 제공자·인증 방식에서 필요한 프로그램 |

프로그램 준비의 범위는 사용자 PC에서 선택한 연결을 실행하는 전용 의존성이다.

## 버전과 재현 가능한 환경

구현한 프로그램·지원 버전과 잠긴 패키지 조합은 [개발 의존성의 정본](../../development/dependencies.md#의존성의-정본)에서 관리한다.
저장별 역할과 SQLite·FTS5 채택은 [로컬 저장 구조](../configuration/profiles.md#로컬-저장-구조)를 따른다.
임베딩·벡터 패키지도 runtime의 잠금 파일에서 관리하고 모델 배포 정보는 기억 기능의 준비 기준을 따른다.
최초 준비 도구의 지원 범위·설치 버전·공식 배포 위치·무결성 값은 `scripts/dependencies.env`에서 관리한다.
실제 설치 상태와 지원 기준은 구분한다.

전용 도구·Python·패키지 환경은 경로·버전·필수 기능을 확인해 재사용하고 절대 경로로 실행한다.
기존 시스템·프로젝트 환경과 사용자·시스템 PATH·shell 시작 파일은 유지한다.
설치 허용 조건은 고정한 출처·버전·무결성의 일치이며 실패하면 해당 진단과 재시도 조치를 반환한다.

## 아무 개발 도구가 없는 최초 진입

최초 설정은 배포물의 준비 스크립트를 설치된 호스트·OS 기본 기능으로 실행한다.
마켓플레이스 접근·호스트 설치의 선행 조건은 배포 안내에서 확인한다.

profile을 확인한 뒤 [고정된 시작 질문](../hosts/plugins.md#setup의-정형-질문)으로 세팅 시작·중단을 확인한다.
시작을 선택하면 필요한 최소 실행 환경을 준비한다.
그 뒤 실제 카탈로그 선택 → YAML 생성·편집 → 검증·확인·일괄 적용 → 선택한 연결 준비로 이어진다.
선택·확인 항목은 호스트 계약의 단계 표, 접속 정보·인증값은 YAML, 기존 맥락·기간은 저장된 설정을 따른다.

OS·기기 종류·사용자 설치 위치·호스트의 시작 환경을 확인한다.
사용자 권한으로 준비하는 것을 기본으로 하고 추가 권한이나 조직 조치가 필요하면 그 이유를 안내한다.
지원 배포물이 없거나 회사 정책에 막히면 미완료 사유와 가능한 다음 조치를 보고한다.

## 구현한 자동 준비의 입출력과 경계

입력은 설치된 플러그인 루트와 `check` 또는 `prepare` 동작이다.
macOS는 `setup.sh`, Windows는 `setup.ps1`을 사용한다.
profile은 YAML 구성 단계의 입력이며 준비 스크립트의 입력은 플러그인 루트와 동작이다.
준비 스크립트의 쓰기 대상은 실행 프로그램·후보 환경·전용 준비 캐시와 설치 사본의 MCP 연결 구성이다.

| 동작 | 수행 조건과 처리 | 결과 |
|---|---|---|
| 검사 | 준비된 runtime만 사용해 Python 지원 범위·MCP·SQLite FTS5 실제 검색 확인 | JSON 검사 결과와 종료 코드 |
| 준비 | 사용자가 setup 설치 범위를 요청하면 도구·Python·잠긴 패키지 준비 | 검사한 실행 환경 활성화·MCP 구성 발행 또는 미완료 이유 |
| 로컬 임베딩 준비 | 로컬 제공자의 준비 요청에 선택 추론 패키지 포함 | 검사한 추론 환경 활성화·MCP 구성 발행 또는 미완료 이유 |
| 일반 MCP 시작 | 준비 성공 후 등록한 전용 Python의 절대 경로로 실행 | 실제 MCP 초기화·도구 목록 또는 연결 실패 진단 |

검사는 기본 동작이며 기존 파일·실행 환경을 읽고 준비 상태·누락 항목·종료 코드를 반환한다.
다운로드·설치는 명시적 준비 동작에서 수행한다.
JSON의 `ready`는 runtime 기본 검사의 성공 여부이며 기억·리소스·호스트 연결은 [단계별 결과](#로컬-저장검색-준비)로 확인한다.
MCP 등록이 누락된 설치 사본은 명시적 준비를 다시 실행해 연결 구성을 발행한다.

setup Skill은 [관리 진입](../../development/dependencies.md#관리-입력과-결과)으로 `check`를 호출한다.
관리 스크립트가 `.venv`·`.venv.previous`·`.venv.prepare.*`·`.daeri-setup.lock`의 상태를 판정한다.
실행 환경과 중단 흔적이 모두 부재하면 `setup_required`를 반환하고 확인한 세팅의 준비 단계로 이어간다.
이때 `.runtime`만 있는 상태도 정상 준비 대상으로 분류한다.
기존 환경의 비정상 경로·실행 권한 부족·끊어진 링크·중단 흔적은 실제 실패·복구 필요 상태로 반환한다.
`--check`·`-Check`의 성공 조건은 준비된 유효 환경이며 미준비·손상은 실패로 반환한다.
첫 배포 사본은 Skill로 진입하고 MCP 등록은 아래 준비의 성공 조건을 충족한 뒤 생성한다.

macOS의 검사·준비는 플러그인 루트에서 `sh scripts/setup.sh --check`·`--prepare`로 실행한다.
Windows는 `powershell -NoProfile -ExecutionPolicy RemoteSigned -File scripts/setup.ps1 -Check`·`-Prepare`를 사용한다.
기본 검사가 성공하면 `check` JSON의 `version`과 `pyproject.toml`의 프로젝트 버전도 대조한다.
기존 runtime과 배포본의 버전이 다르면 확인한 세팅 범위에서 전용 환경을 교체하고 버전 일치를 재확인한다.

준비는 다음 순서로 진행한다.

1. 같은 플러그인의 준비 잠금을 확보하고 이전 활성화 중단 흔적을 확인한다.
2. 플러그인 루트의 `.runtime/uv.exe`와 고정된 배포 기준을 확인한다.
   전용 도구가 미준비이면 OS·CPU에 맞는 공식 배포물을 해당 위치에 다운로드한다.
   uv 실행 대상은 이 전용 경로로 고정한다.
3. 다운로드 파일의 SHA256을 배포물에 고정한 값과 비교한 뒤 실행 파일을 발행한다.
   배포 해시·실행 검사가 모두 성공한 파일을 실행 대상으로 등록한다.
4. 전용 uv를 절대 경로로 실행하고 사용자 데이터 경로의 `runtime/python`·`runtime/cache`에 관리 Python과 준비 캐시를 둔다.
   준비에 사용하는 Python은 이 관리 경로에서 선택하고 기존 환경은 보존한다.
5. 잠긴 패키지를 플러그인 루트의 별도 후보 가상환경에 준비한다.
   공통 진입 파일과 가상환경 설정·패키지를 확인하고 Python 격리 모드로 실제 기본 실행을 검사한다.
6. 검사한 후보를 `.venv`로 전환하고 해당 환경의 Python으로 `scripts/register_mcp.py`를 실행한다.
   이 표준 라이브러리 기반 스크립트는 설치 사본의 루트 `.mcp.json`을 임시 파일에서 원자적으로 발행한다.
   구성의 `runtime`은 설치 루트의 `.venv/bin/python.exe` 절대 경로와 `-I -m daeri.server`, 빈 `__PYVENV_LAUNCHER__` 환경값을 사용한다.
7. 환경 전환과 구성 발행이 모두 성공하면 이전 `.venv.previous`를 정리한다.
   후보 준비·검사·활성화·구성 발행 실패는 후보를 정리하고 기존 환경과 기존 MCP 구성을 보존하거나 복원한다.

생성한 `.mcp.json`은 해당 설치 사본에 귀속되는 로컬 실행 자산이다.
Git 배포 원본과 sdist·wheel은 이 설치별 구성과 구성 발행의 임시 파일을 제외한다.
배포물은 Skill·준비 스크립트를 전달하고 준비 성공 시 두 호스트의 기본 파일 탐색으로 MCP 구성을 제공한다.
호스트가 새 구성을 읽는 절차와 실제 연결의 확인은 [호스트 연결 계약](../hosts/plugins.md#설치부터-업무-시작까지의-실제-경계)을 따른다.

DAERI 패키지는 플러그인의 `.venv`, 준비 도구는 같은 플러그인의 `.runtime/uv.exe`에 둔다.
관리 Python과 캐시는 플러그인 업데이트 뒤에도 기존 하위 MCP 환경이 사용할 수 있도록 사용자 데이터 경로의 `runtime/`에 유지한다.
환경 교체는 프로그램 영역을 대상으로 하며 업무 데이터·profile·인증은 [별도 사용자 저장소](../configuration/profiles.md#로컬-저장-구조)에 유지한다.
사용자 지정 `DAERI_DATA_DIR`는 절대 경로나 현재 사용자의 `~/` 경로만 받는다.
경로 검증 성공 후 프로그램·캐시 디렉터리를 생성한다.
상대 경로 입력은 준비 전 경로 오류로 반환한다.

### 공통 실행 파일과 환경 격리

관리 CLI와 일반 MCP의 Python 진입은 두 OS에서 플러그인 루트의 `.venv/bin/python.exe`로 통일한다.
macOS는 가상환경의 `bin/python`을 가리키는 상대 심볼릭 링크를 만들고, Windows는 `Scripts/python.exe`를 `bin/python.exe`로 복사한다.
`.exe`는 두 호스트·OS의 배포 설정에서 같은 경로를 사용하기 위한 이름이며 Windows의 실제 실행은 별도로 검증한다.
실행 파일의 상위 가상환경 설정을 읽는 [Python 경로 초기화 규칙](https://docs.python.org/3/library/sys_path_init.html#virtual-environments)을 사용하고 실제 환경 경로가 일치하는지 검사한다.

Python은 [`-I` 격리 모드](https://docs.python.org/3/using/cmdline.html#cmdoption-I)로 실행해 사용자 site-packages·현재 작업 디렉터리·Python 환경 변수에 의한 모듈 주입을 막는다.
macOS의 별도 가상환경 선택 변수 `__PYVENV_LAUNCHER__`는 호스트 MCP 구성에서 빈값으로 두고 관리 명령의 자식 환경에서는 제거한다.
준비 명령과 Python 자식 프로세스에는 `UV_*`·`PYTHON*`·`VIRTUAL_ENV`·`CONDA_*` 등 프로그램 선택·주입용 환경을 제거하고 필요한 관리값만 부여한다.
정리한 환경은 자식 프로세스에 전달하고 사용자의 원래 환경·shell 설정은 보존한다.

명시한 `DAERI_DATA_DIR`, OS 실행·네트워크·인증서 조건과 선택한 인증 참조는 해당 기능에 필요한 범위에서 유지한다.
하위 MCP의 환경·인증 전달에는 격리 기준과 [리소스 계약](../resources/initial-adapters.md#첫-버전의-실제-연결-방식)의 허용 목록을 함께 적용한다.
일반 MCP의 시작 명령은 전용 Python의 `-I -m daeri.server`다.
전용 실행 환경의 누락·손상은 시작 실패와 setup 복구 안내로 반환한다.

| 준비 중 실패 | 처리와 다음 행동 |
|---|---|
| 지원 OS·CPU 배포물 부재 | 확인한 OS·CPU와 배포물 부재를 알리고 준비 종료 |
| 네트워크·인증서·해시 검사 실패 | 활성 환경 유지, 공식 출처·조직 네트워크 확인 후 명시적 재시도 |
| 패키지 준비·실행 검사·MCP 구성 발행 실패 | 후보 환경 정리, 기존 환경·기존 MCP 구성 유지 또는 복원, 준비 미완료 보고 |
| 같은 플러그인의 중복 준비 | 두 번째 준비 차단; 먼저 실행 중인 준비 상태 확인 |
| 강제 종료 후 잠금 잔존 | 다른 준비 프로세스가 없는지 확인한 뒤 잠금 제거·재시도 안내 |
| 환경 교체 중 중단 | 활성 환경이 없고 이전 환경만 남으면 다음 준비에서 이전 환경 복원 |
| 준비 뒤 전용 실행 파일·환경 누락·손상 | 실제 연결 실패와 setup의 명시적 검사·복구 안내 |

프로그램 준비 성공과 현재 호스트의 MCP 재연결 성공은 구분해 보고한다.

이전 버전이 추가한 PATH 설정이 남아 있으면 과거 항목임을 알리고 사용자에게 수동 정리를 안내한다.
과거 항목의 정리는 사용자가 해당 shell 설정에서 확인해 수행한다.

Windows 준비 진입은 해당 프로세스에만 `RemoteSigned` 실행 정책을 적용할 수 있다.
실행은 조직 Group Policy와 인터넷 파일의 서명·출처 검사를 충족해야 한다.
조직 정책으로 스크립트 실행이 차단되면 관리자 조치를 안내한다.

## 검사·계획·설치

profile 설정에서 선택한 연결·인증 방식과 [기억 기능](../tasks/memory.md)에 맞춰 필요한 프로그램을 계산한다.
기본 검사는 로컬 실행 기능을, 제공자 인증은 명시적 로그인 경로를, 업무 자료 조회는 승인된 실행 경로를 사용한다.
전체 진행 순서는 [관리 등록과 진단](../configuration/profiles.md#관리-등록과-진단)을 따르며 선택한 항목의 실행 가능 여부·버전·필수 기능을 검사한다.

기본 응답과 기술 정보의 표시 조건은 [공통 사용자 안내](../hosts/plugins.md#사용자-안내)를 따른다.
상세 진단은 프로그램 버전·정확한 설치 경로·패키지 목록과 배포 출처·무결성 검사 결과를 제공한다.
출처·무결성·환경 격리 검사는 준비 코드에서 수행하고 범위 변경에는 판단할 이유와 다음 조치를 확인받는다.

runtime은 확인한 준비 범위 안에서 필요한 순서로 프로그램을 준비한다.
범위를 벗어난 프로그램·권한·시스템 변경은 변경 내용과 필요한 조치를 제시해 확인받는다.
설치 동의는 [업무 계획 승인](../tasks/approval.md)과 별개다.

누락·비호환·정책 차단·판단 불가를 구분하고 실제 확인 결과를 남긴다.
호스트에서 시작한 환경과 수동 실행 환경의 차이도 확인한다.

### 로컬 저장·검색 준비

SQLite·FTS5는 DAERI runtime에 포함하거나 사용자 전용 Python runtime으로 준비한다.
SQLite 사용 경로는 runtime 안의 바인딩이다.
현재 준비 검사는 다음 실행 단계로 나눈다.

| 실행 단계 | 실제 확인 범위 |
|---|---|
| `check`·준비 후보 검사 | Python 지원 범위·MCP import와 버전, 메모리 SQLite의 실제 FTS5 검색 |
| 사용자 저장소 열기 | 전용 경로·파일 권한, SQLite 스키마·WAL·트랜잭션·FTS5, 만료·미공개 파일 정리 |
| 기억 서비스 시작·상태 | 기억 테이블·키워드 색인·벡터 확장 로딩, 선택 제공자와 이미 준비된 로컬 모델 상태 |
| 인증·연결 진단 | 선택 인증 참조의 해소와 해당 연결·대상의 실제 진단 |

기본 `ready`는 첫 행의 검사 결과이며 현재 호스트 MCP 연결은 실제 연결 결과로 확인한다.

벡터 확장은 OS·기기 종류·runtime 바인딩과 맞는 검증된 배포물을 사용한다.
벡터 확장의 호환 실패는 현재 선택을 유지하고 미완료 항목·준비 조치를 안내한다.
저장 경로의 사용 가능 여부는 실제 파일 쓰기·참조 발행·트랜잭션 결과로 확인한다.
OS 인증 저장소 접근은 YAML 적용의 등록 결과·`auth status`·연결 진단의 실제 해소 결과로 확인한다.
메모리·디스크의 사전 용량 산정은 확장 설계이며 현재는 실제 준비·실행 결과로 가용성을 판정한다.

### 임베딩 선택과 준비

profile별로 로컬 모델·회사 API·키워드 전용 중에서 선택한다.
회사 API는 등록된 연결 방식을 확인한 뒤 해당 어댑터의 설정·인증·진단을 진행한다.
입력·기본값·선택 적용은 [임베딩 제공자 설정](../configuration/profiles.md#임베딩-제공자-선택), 전송·실패·색인 호환성은 [기억 계약](../tasks/memory.md#임베딩-api-계약)이 소유한다.

| 선택·관리 동작 | 수행·결과 |
|---|---|
| 기본 runtime 준비 | 공통 의존성·실행 기능 준비; 로컬 추론은 선택 의존성의 별도 준비 |
| `memory status [--profile NAME]` | 네트워크·비밀 해소 없이 제공자·API 연결 방식·로컬 준비 확인; API 호환은 미검증 |
| `memory diagnose --profile NAME` | 선택한 로컬 모델·허용된 회사 API에 고정 시험 문장으로 벡터 생성 검사; 키워드 전용은 거부 |
| `memory prepare [--profile NAME]` | 로컬 제공자만 모델 다운로드·준비; API·키워드 전용 profile은 거부 |
| `memory reindex [--profile NAME]` | 선택한 제공자로 현재 허용 정본만 재색인; 실패는 대기 상태 유지 |

회사 API 진단의 입력은 고정 시험 문장이다.
설정한 어댑터가 회사의 인증·요청·응답 규격을 처리하는지 실제 응답으로 확인한다.
연결 방식 확인이 남은 초안은 보존하고 사용자와 해당 API 계약을 확인한 뒤 적용·진단으로 이어간다.
`memory status`는 네트워크 진단 없이 선택·로컬 준비를 조회하므로 `api_verified`는 항상 `false`다.
`vector_ready`는 선택 제공자 객체와 로컬 벡터 확장의 준비 상태이며 API 호환·전체 기억 색인 완료는 별도 결과다.
인증 참조의 현재 해소 가능 여부는 `auth status REFERENCE`로 확인한다.
API·키워드 전용은 로컬 추론 패키지·모델 없이 사용하며 다른 profile에 필요한 로컬 모델은 공유 준비 자산으로 유지할 수 있다.

로컬 제공자는 먼저 macOS의 `sh scripts/setup.sh --prepare-local-embedding` 또는 Windows의 같은 PowerShell 진입에 `-PrepareLocalEmbedding`으로 추론 패키지를 준비한다.
그 뒤 `memory prepare --profile NAME`으로 모델을 준비한다.
로컬 추론 패키지·모델 준비는 로컬 제공자의 명시적 관리 경로에서 수행한다.

로컬 모델 준비는 고정 시험 문장의 추론 성공으로 확인한다.
용량·조직 제약이 있거나 추가 조치가 필요하면 해당 이유를 설명한다.
현재 로컬 모델은 등록된 모델 이름을 준비 라이브러리로 내려받고 실제 모델·토크나이저 바이트의 지문을 계산한다.
이 지문은 색인 호환성을 구분한다.
모델의 배포 revision·예상 해시를 고정해 다운로드와 대조하는 검증은 추가 배포 설계 범위다.

일반 업무는 준비된 모델을 사용하고 모델 누락은 검색 제한·setup 준비 조치로 반환한다.
로컬 실행 실패는 현재 제공자 선택을 유지하고 제한·setup 조치를 안내한다.

모델 가중치는 같은 사용자의 여러 profile이 재사용할 수 있다.
기억과 검색 결과의 profile·실제 대상 경계는 계속 유지한다.
모델 교체 뒤 같은 모델 지문의 호환 색인을 사용하거나 유효 정본으로 재색인한다.
실행 한도·지원 기기·배포 크기는 실제 모델을 선택한 뒤 검증해 의존성 목록에 기록한다.

## 설치 실패와 재개

준비 잠금·후보 검사·활성화·실패 복구는 [자동 준비 계약](#구현한-자동-준비의-입출력과-경계)을 적용한다.
재실행 시 현재 파일·패키지·실행 검사를 대조해 미완료 단계부터 재개한다.
설치 성공·인증 성공·원격 권한·업무 데이터 접근 성공은 각각 구분한다.
여러 profile이 실행 환경을 공유할 수 있어도 연결과 인증 문맥은 분리한다.

## 배포 출처와 최초 전달

사용자는 소스 저장소를 마켓플레이스에 추가하고 DAERI 플러그인을 설치한 뒤 profile 설정을 시작한다.
현재 사용할 저장소와 호스트는 [사용 예정 환경](../product.md#사용-예정-환경)에 정리한다.
배포 경로는 호스트가 지원하는 저장소·마켓플레이스 전달 계약으로 결정한다.

저장소 접근 권한과 호스트가 요구하는 전달 조건을 확인한다.
마켓플레이스 추가 전에 필요한 프로그램이 있으면 그 선행 조건과 준비 경로를 안내한다.
저장소 접근이 어려운 환경에서는 검증 가능한 완전한 배포물을 통한 최초 진입을 검토한다.

공통 기능과 Skill을 바탕으로 [호스트별 패키지](../hosts/plugins.md)를 구성한다.
실제 저장소 추가·설치·업데이트 가능 여부는 각 호스트에서 검증한다.

## 업데이트와 데이터 보존

업데이트는 새 환경을 검사한 뒤 전환하고 전환 중 실패에는 기존 환경을 유지하거나 복원한다.
전환 성공 후 이전 프로그램 환경은 정리하며 업무 기록은 별도 사용자 저장소에 유지한다.
진행 중인 업무는 저장한 스냅샷·현재 환경의 연결 계약·권한·승인 유효성을 확인해 재개한다.

업데이트·재설치·임시 자료 정리는 profile·인증 참조·업무·승인·호출 기록과 유효한 기억 정본을 보존한다.
조회 자료·보고서·생성 파일은 [업무 보존 조건](../tasks/workflow.md#이력과-완료-근거)의 기한·만료·삭제 상태를 업데이트·복구 뒤에도 승계한다.
기억·검색 색인·캐시의 복구는 [기억 보존 기준](../tasks/memory.md)의 현재 유효 정본만 대상으로 한다.
사용자 간 데이터·비밀 공유는 [공유·복구 경계](../configuration/profiles.md#변경공유복구)를 따른다.

저장소의 루트 경로나 SQLite 파일을 옮기거나 교체하는 복구는 runtime 연결을 종료한 뒤 진행한다.
설정한 저장 위치의 SQLite 본체·WAL 등 저장소 파일의 일관성을 확인한 뒤 새 연결에서 해당 저장소를 연다.
실행 중 변경을 발견한 오류·중단·재연결은 [저장소 동일성 검사](../configuration/profiles.md#설정과-업무-기록의-저장)를 따른다.

저장 형식 변경과 profile 백업·복원은 [이관·백업·복원 계약](../configuration/profiles.md#이관백업복원)을 따른다.
현재 저장 스키마와 구현한 이관은 [개발 안내](../../development/dependencies.md#실행-진입점과-모듈)의 저장 모듈에서 관리한다.

현재는 단일 profile의 허용 설정·업무·기억·등록 파일을 암호화 묶음으로 이관하며 새 환경의 인증·연결 진단·실행 승인을 다시 확인한다.
여러 profile과 공유 설치 자산을 함께 이관하는 저장소 전체 묶음은 추가 설계 범위다.

## 회사 환경과 자동 준비의 한계

| 상황 | 처리 |
|---|---|
| 네트워크 실패 | 실패 항목과 재개 방법 안내 |
| 조직의 네트워크·인증서 설정 | 조직이 허용한 설정을 적용해 재검사 |
| 다운로드 차단 | 허용된 배포 경로나 검증 가능한 오프라인 배포물 검토 |
| OS·회사 정책 차단 | 필요한 사용자·조직 조치와 미완료 이유 표시 |
| 제공자 로그인 필요 | 해당 제공자 안내에 따른 사용자 인증 |
| 원격 권한·기능 미지원 | 연결별 상태로 표시하고 로컬 설치 결과와 구분 |

설치 완료는 배포 신뢰 검증과 회사 정책을 충족한 실제 실행 검사를 조건으로 한다.
자동화할 수 없는 사용자 인증과 조직 조치는 명확하게 안내한다.

## 검증과 사용자 환경 확인

[준비 회귀](../../../tests/test_bootstrap.py)와 [관리 진입 회귀](../../../tests/test_management_entry.py)는 임시 경로·가짜 다운로드·프로세스로 해시·중복·경로·실패 복구를 확인한다.
macOS의 임시 HOME과 빈 전용 캐시에서 공식 uv·관리 Python·잠긴 실행 환경 준비, Source 도구의 별도 환경 재사용, 공통 Python MCP 시작을 확인한 근거도 있다.

실제 호스트 설치·회사 인증·운영 연결·Windows 실행과 캐시 없는 사용자 PC의 전체 흐름은 해당 환경에서 별도 검증한다.
구현별 근거·추가 확인 범위는 [검증 지도](../../plans/initial-implementation.md#확보한-검증-근거), 로컬 실행 방법은 [개발 안내](../../development/dependencies.md#개발-환경과-검사)를 따른다.
