# 서비스 profile·인증·로컬 저장

상태: profile·로컬 인증·SQLite·파일 저장과 사용자 설정 YAML 구현; 실제 운영 연결·호스트 UI·Windows 실행 미검증

profile에 리소스·운영 맥락·기억 정책을 묶고 연결 준비와 로컬 데이터 저장·조회·삭제를 정의한다.
기능의 탐색·등록·실행은 [리소스 계약](../resources/contract.md)을 따른다.
기억의 내용·검색·갱신·보존은 [profile별 장기기억](../tasks/memory.md)이 정본이다.

## profile의 의미

profile은 서비스·환경별 리소스와 운영 정보를 묶는 DAERI의 설정 단위다.
DB·Cache·Infra·Source·Document·Issue 등 필요한 범주와 여러 인스턴스를 함께 등록한다.
범주 예시는 [리소스 범주](../resources/adapters.md), 실제 사용 예정 제품은 [사용 예정 환경](../product.md#사용-예정-환경)을 따른다.

| 구분 | 가상 예시 | 책임 |
|---|---|---|
| DAERI profile | `service-prod` | 서비스·환경과 리소스 묶음 |
| 리소스 인스턴스 | `primary-db`, `reference-db` | 실제 대상과 역할 |
| 연결 | `primary-db-connection` | 어댑터·실행 위치·인증 설정 |
| 제공자 인증 설정 | `operations-account` | 해당 제공자의 로그인·자격 증명 |

DAERI profile과 제공자 인증 설정은 별개다.
하나의 DAERI profile이 여러 제공자·계정의 인증 설정을 참조할 수 있다.

## 구성과 연결

profile은 식별자·이름·기본 운영 맥락·리소스 연결·제공 정책·보존기간으로 구성한다.
서비스·환경은 이름과 기본 맥락으로 설명하고 실제 대상은 각 리소스의 `target`으로 구분한다.
개정이 달라도 같은 profile의 식별자를 유지하고 업무의 대상·당시 설정은 [스냅샷](#업무에-고정하는-스냅샷)에 기록한다.

각 리소스에는 범주·역할·어댑터·연결 위치·실제 대상·인증 참조·접근 정책을 등록한다.
연결이 어디서 실행되고 어떤 자료가 외부로 전달되는지 설정에서 확인할 수 있어야 한다.

자료·기억의 실제 사용 범위는 업무 계획에 담아 사용자에게 승인받는다.
profile 정책은 회사 규칙이나 사용자가 정한 추가 상한으로 적용하며 기본값과 입력 의미는 아래 [자료 정책](#자료-제공보관-정책)·[기억 정책](#profile의-기억-허용-설정)을 따른다.
사용자가 설정한 안정적인 서비스 설명·용어·업무 규칙은 profile의 기본 맥락으로 관리한다.
기본 맥락과 접근 정책의 변경은 사용자가 요청한 관리 작업으로 적용한다.

같은 연결을 여러 profile에서 쓰려면 각각 명시적으로 등록한다.
인증·대상·정책이 다른 연결은 표시명이 같아도 구분한다.
실행 대상은 해당 profile에 등록한 연결과 그 연결의 인증 참조로 결정한다.

업무 자료의 보존기간은 profile별로 설정하며 새 profile의 기본값은 무기한이다.
기간 변경은 새 업무에 적용하고 기존 기한·만료 상태는 [업무 보존](../tasks/workflow.md#이력과-완료-근거)과 [기억 보존](../tasks/memory.md#보존과-장기-운영지식) 계약으로 유지한다.

## 구현한 profile 입력과 공개 설정

사용자가 등록하는 JSON은 아래 구성 필드만 허용한다.
내보내기는 아래 공개 구성 필드를 반환한다.
식별자·개정·진단은 사용자 저장소의 관리 정보이며 인증 비밀은 해당 인증 저장소에서 관리한다.
다른 PC에서 가져오면 그 PC의 인증 저장·실행 파일 경로·연결 진단을 다시 준비한다.

| 최상위 입력 | 의미·기본값 |
|---|---|
| `name` | 필수 이름; 영문·숫자로 시작하는 영문·숫자·`_`·`-`, 최대 64자 |
| `core_context` | 사용자가 관리하는 기본 운영 맥락 문자열 목록; 기본 빈 목록 |
| `resources` | 같은 profile의 리소스 인스턴스 목록; 기본 빈 목록 |
| `retention_days` | 새 업무 본문·조회 자료·보고·파일의 보존일; 양의 정수 또는 null, 새 profile의 기본 null은 무기한 |
| `long_term_memory_days` | 별도 허용한 장기 지식의 보존일; 양의 정수 또는 null, 새 profile의 기본 null은 무기한 |
| `memory_policy` | 호환용 추가 기억 상한; 생략·null·빈 객체는 계획 기반 기본값, 내용 있는 객체는 제한 |
| `embedding` | profile별 임베딩 선택; 새 profile에서 생략하면 로컬, 기존 profile에서는 생략한 선택 보존 |

현재 가져오기·내보내기 파일은 UTF-8 JSON이며 최대 2 MiB·중첩 32단계다.
중복 키·NaN·무한대·알 수 없는 필드·잘못된 인증 참조를 저장 전에 거부한다.
명시한 맥락·리소스는 목록, 임베딩은 객체로 입력한다.
`memory_policy`는 객체 또는 null이며 두 기간 필드의 null은 무기한을 뜻한다.
유한 기간은 양의 정수이며 기준 UTC 시각에 해당 일수를 더한 시각을 표현할 수 있어야 한다.
저장·기존 설정 조회·YAML 검증과 실제 기한 계산에 같은 조건을 적용하고 범위를 벗어나면 `INVALID_INPUT`으로 반환한다.
검증 성공 때 새 개정을 활성화한다.
검증 실패는 기존 활성 개정을 유지하고 필드·오류 코드 중심의 진단을 반환한다.
빈 자료·기억 정책은 조회 시 계획 기반 기본값으로 해석하고 다음 설정 저장에서 null로 정규화한다.

`profile export NAME`은 위 공개 구성을 표준 출력의 JSON으로 반환한다.
`profile import CONFIG_JSON`은 그 파일의 이름으로 전체 구성을 새 개정에 저장한다.
기존 이름이면 같은 식별자를 유지하며 동일한 구성도 새 개정을 만든다.
생략한 맥락·리소스는 빈 목록, 두 기간은 무기한으로 저장한다.
새 profile의 생략한 기억 정책은 null이며 기존 profile의 생략한 `memory_policy`·임베딩 선택은 저장한 값을 유지한다.
가져오는 리소스가 기존과 같은 `instance_id`이면 생략한 `policy`도 기존 값을 유지하고 새 인스턴스는 null을 사용한다.
명시한 정책 객체·null은 해당 값을 적용하며 나머지 구성은 전체 교체 규칙을 따른다.
기존 구성의 일부를 바꿀 때에는 전체 export를 수정해 import하거나 아래 YAML·개별 관리 경로를 사용한다.
import의 동시 저장은 트랜잭션으로 직렬화하며 기대 개정 확인은 YAML 적용과 개별 `configure` 경로에서 제공한다.

관리형 연결은 내보낸 POSIX·Windows 절대 경로의 `tools/<recipe>/<버전-잠금 지문>/.venv/<실행 디렉터리>/<실행 파일>`을 현재 카탈로그·잠금 조합과 대조한다.
범주·정식 어댑터·기본 인수와 현재 준비 지문까지 일치하면 `connection.command`만 가져온 PC의 관리 경로로 바꾼다.
인스턴스·실제 대상·인증 참조·정책·조회 제약은 유지하고 프로그램 준비·인증 등록·연결 진단은 가져오기 뒤 수행한다.
수동 경로·이전 잠금 조합·사용자 정의 인수는 입력한 구성을 유지한다.
이 연결을 다른 PC에서 사용할 때에는 내보낸 전체 JSON의 실행 경로·필요한 공개 설정을 수정해 가져오고 인증과 실제 대상을 다시 진단한다.

`profile create`는 새 이름의 구성을 생성하며 이미 있으면 `PROFILE_ALREADY_EXISTS`로 거부하고 기존 개정·연결·정책을 유지한다.
리소스의 정형 입력 변경은 아래의 [설정 입력과 검증](#리소스-설정-입력과-검증)으로 선택한 인스턴스만 반영한다.
임베딩과 연결은 [YAML setup](#사용자용-setup-yaml) 또는 아래의 개별 관리 명령으로 변경한다.
그 밖의 전체 설정 이동은 JSON import·export를 사용한다.

### 리소스 인스턴스

| 입력 | 의미 |
|---|---|
| `instance_id` | profile 안에서 고유; 영문·숫자로 시작하는 영문·숫자·`_`·`.`·`:`·`-`의 1~128자 |
| `type`, `adapter` | 범주와 현재 설치한 어댑터 계약 |
| `target` | 실제 서버·저장 영역·계정 또는 로컬 Source 디렉터리 등의 대상 정보 |
| `identity_ref` | 해당 연결의 인증 문맥을 식별하는 비밀 없는 이름; 로컬 Source는 `local-user` |
| `connection` | MCP 실행·전달·인증 설정 또는 로컬 Source의 `transport: host` |
| `capabilities` | 1~128개의 명시적 기능; 고유 `capability_id`·`tool_name`·`constraints`, 선택 `description` |
| `discover_tools` | 선택적인 내부 호환 값; 새 외부 서비스 연결은 true로 읽기 기능 탐색, 로컬 Source와 생략·false 설정은 명시적 기능 선택 |
| `policy` | 선택적인 자료·기억 상한; 생략·null·빈 객체는 계획 기반 기본값, 내용 있는 객체는 제한 |

stdio 연결은 이미 준비할 실행 파일의 절대 경로와 문자열 인자·일반 환경 값·`auth_env` 참조를 등록한다.
실행 파일은 검증한 비-shell 프로그램이며 인자·일반 환경 값은 공개 설정만 받는다.
원격 연결은 `streamable_http`의 명시적인 HTTPS URL과 `auth_headers` 참조를 사용한다.
원격 연결 URL은 HTTPS 주소·경로로 구성하고 인증은 `auth_headers`의 참조로 전달한다.
외부 서비스용 기본 어댑터의 검증된 연결은 로컬 stdio다.
원격 연결은 실제 리소스 대상·인증 문맥을 입증하는 어댑터 계약이 필요하며 해당 계약이 없는 연결의 진단·실행은 `UNSUPPORTED_CONSTRAINT`다.

로컬 Source는 `target.path`에 디렉터리의 절대 경로를, `connection`에 `{"transport":"host"}`를 등록한다.
설정 구조는 절대 경로 문법과 연결 필드를 검증하며 다른 PC의 경로도 저장·조회·복원할 수 있다.
setup 입력은 현재 디렉터리의 존재·읽기·탐색 접근을 확인하고 심볼릭 링크를 해소한 실제 경로로 저장한다.
준비·진단·관찰 등록은 해당 PC의 접근 가능 여부와 저장된 실제 경로의 일치를 다시 확인한다.
`local_source` 어댑터의 `source-observe` 관찰 기능은 [Source 연결 계약](../resources/adapters.md#로컬-소스-코드)을 따른다.

인증 참조는 `credential:이름` 또는 명시적으로 선택한 `env:환경변수명`이다.
전자는 OS 인증 저장소, 후자는 현재 호스트가 받은 해당 환경 변수에서만 해소한다.
참조 해소에 실패하면 해당 연결의 인증 필요 상태를 반환한다.
`auth_env`와 `auth_headers`의 값도 실제 비밀 대신 이 참조만 받는다.

인스턴스·범주·인증 문맥·기능의 ID는 영문·숫자로 시작하는 영문·숫자·`_`·`.`·`:`·`-`의 1~128자다.
각 리소스 설정은 UTF-8 JSON 256 KiB 이내이며 필드·타입·어댑터 조합과 비밀 참조를 저장 전에 검사한다.
자동 탐색으로 추가한 실제 도구의 개수·이름·스키마 조건은 [등록 설정과 진단](../resources/adapters.md#등록-설정과-진단)을 따른다.

외부 서비스의 새 연결은 인증 문맥을 `identity:<profile>:<인스턴스>`로 생성하고 128자를 넘으면 두 값의 해시로 구성한다.
인증 비밀의 기본 참조는 profile·인스턴스·인증 필드로 생성한다.
조합한 이름이 인증 참조의 문자·길이 조건을 벗어나면 세 값의 결합을 해시한 고유 참조를 사용한다.
같은 입력은 같은 참조로 생성하고 기존에 등록한 유효 참조는 유지한다.

도구 등록·대상 해석·계약 변경은 [리소스 계약](../resources/contract.md), 제품별 호환 식별자는 [어댑터 지원 경계](../resources/adapters.md#어댑터별-실제-지원-경계)를 따른다.
`discover_tools`는 카탈로그와 확인한 기능 갱신에서 구성하고 실제 사용은 현재 정책·승인 검사를 거친다.

### 자료 제공·보관 정책

리소스 `policy`는 업무 계획에 추가로 적용할 자료·기억 상한이다.
생략·null·빈 객체는 별도 상한 없이 실제 계정·어댑터 제약과 현재 승인 계획으로 허용 범위를 결정한다.
runtime은 등록된 정책에서 모델 제공·파일·본문 보관·기억의 기본값을 해소한다.
호스트는 목적·조회 대상·결과·완료 조건을 계획으로 제시하고 실제 사용자 승인 뒤 수행한다.

내용 있는 정책 객체는 명시한 항목을 상한으로 적용한다.
그 객체에서 생략한 허용 항목은 빈 값으로 해석하고 기존 제한을 유지한다.
이전 버전의 빈 객체도 계획 기반 기본값으로 해석한다.
연결 진단의 동일성은 실제 연결·대상·기능 의미로 확인하며 정책 표현의 차이와 무관한 profile 변경은 기존 연결을 유지한다.

| 정책 필드 | 의미 |
|---|---|
| `allowed_model_fields` | 호스트 모델에 제공할 수 있는 필드 선택자 목록 |
| `export_fields` | 사용자 산출물에 포함할 수 있는 필드 선택자 목록 |
| `retained_fields` | 선택한 보존기간 안에서 로컬 본문에 보관할 수 있는 필드 선택자 목록 |
| `masking` | 선택 필드를 제거하거나 값을 가리는 규칙 |
| `memory` | 기억 범주·출처 필드·사용자 확인 자료·보존·회상 허용 상한 |

선택자·마스킹 문법은 [공통 필드 선택](../mcp/common.md#필드-경로와-선택)을 따른다.
빈 `segments`는 전체 자료를 뜻하므로 모든 자료 제공을 의도한 경우에만 명시한다.
명시한 정책 객체와 승인 계획의 선택자·마스킹을 모든 제공·보존 경로에 함께 적용한다.

### profile의 기억 허용 설정

`memory_policy`는 profile 전체의 추가 기억 상한이다.
생략·null·빈 객체는 아래 네 범주·현재 등록 리소스를 대상으로 승인한 업무의 선별 기억·향후 회상을 사용한다.
이는 계획 작성의 상한이며 실제 저장·미래 회상에는 승인한 계획과 유효 출처가 필요하다.

내용 있는 객체는 리소스의 `policy.memory`와 함께 제한을 검사한다.
그 객체에서 생략한 범주·리소스는 빈 목록, 허용 값은 `false`이며 기존 제한을 유지한다.

| 공개 입력 | 타입·허용값 | 적용 |
|---|---|---|
| `categories` | 중복 없는 문자열 목록 | `service_rule` 서비스 규칙, `resource_structure` 리소스 구조, `procedure` 수행 절차, `lesson` 주의·교훈 중 선택 |
| `instance_ids` | 같은 profile에 등록한 리소스 ID의 중복 없는 목록 | 이 리소스들이 기여한 기억만 저장·재사용 |
| `model_allowed` | JSON boolean | 기억을 호스트 모델에 제공할 수 있는 상한 |
| `retain_allowed` | JSON boolean | 기억 본문을 보관할 수 있는 상한 |
| `long_term_allowed` | JSON boolean | 원문 기한과 독립적인 장기 지식 보존을 허용할 수 있는 상한 |
| `exports_allowed` | JSON boolean | 기억 내용을 사용자 산출물에 포함할 수 있는 상한 |

기본 업무 흐름은 환경 설정과 업무 계획 승인으로 기억 저장·회상까지 연결된다.
위 필드는 추가 제한을 설정한 profile의 호환 계약이며 실제 사용은 승인 계획과 현재 제한을 함께 검사한다.

runtime은 선택한 각 인스턴스의 현재 `target`을 정렬된 JSON의 SHA-256으로 계산해 내부 `target_bindings`에 저장한다.
runtime이 실제 `target`에서 바인딩을 계산하므로 사용자 입력은 리소스 ID와 허용 정책으로 구성한다.
내보내기는 사용자 입력 필드를 반환하고 가져올 때 현재 설정으로 바인딩을 다시 계산한다.

내부 설정을 다시 저장하며 `target_bindings`를 전달한 경우에는 선택한 리소스 ID와 소문자 64자리 해시 형식만 받는다.
값은 현재 실제 대상으로 다시 계산하고 기억 재사용 때 출처의 대상 바인딩과 일치를 검사한다.
명시한 객체의 선택 리소스·허용 값은 그대로 유지하고 계획 기반 기본값은 현재 등록 리소스·대상에서 해소한다.
명시한 `instance_ids`는 적용 후 등록 리소스의 부분집합이어야 한다.
알 수 없는 필드·범주·미등록 ID·중복·잘못된 타입은 개정 저장 전에 거부한다.

기억 출처·장기 보존·정정·검색의 상세 조건은 [기억 명세](../tasks/memory.md)를 따른다.

### 임베딩 제공자 선택

`embedding`은 기억 검색용 벡터를 만드는 방법이며 업무 판단용 호스트 모델 설정과 구분한다.
`provider`는 로컬 모델·회사 API·키워드 전용을, API의 `adapter`는 회사와 주고받는 연결 규격을 선택한다.
회사 API를 선택해도 기억 정본·벡터·키워드 색인은 사용자 로컬 저장소에 유지한다.

| 필드 | 타입·기본값·조건 |
|---|---|
| `provider` | 필수; `local`·`api`·`keyword_only`, 새 profile의 기본값은 `local` |
| `adapter` | `api`에서 필수; 등록된 연결 방식의 ID |

`local`·`keyword_only` 객체의 입력은 `provider` 하나다.
`api`의 추가 입력은 선택한 어댑터의 생성·검증 계약을 따른다.
실제 선택지는 `setup catalog`의 `embedding_adapters`가 반환하고 등록 책임은 [임베딩 API 계약](../tasks/memory.md#임베딩-api-계약)이 소유한다.

현재 제공하는 연결 방식은 `openai_compatible`이다.
이는 인증·요청·응답 형식이며 회사 모델의 제조사·종류와 구분한다.
이 방식의 추가 입력은 다음과 같다.

| 필드 | 타입·기본값·조건 |
|---|---|
| `endpoint` | 필수; HTTPS의 정확한 embeddings 요청 URL |
| `model` | 필수; 회사에서 지정한 모델 또는 배포 이름 |
| `credential_ref` | 필수; 기존 `credential:이름` 또는 `env:환경변수명` 참조 |
| `dimensions` | 선택; 1~8192의 정수, 생략하면 응답 벡터의 차원을 사용 |
| `timeout_seconds` | 선택; HTTP 네트워크 단계별 제한, 기본 15초·1~60의 정수 |

이 어댑터의 URL은 HTTPS 요청 주소이고 인증은 별도 참조로 해소한다.
요청은 등록한 정확한 URL에 전송하고 redirect 응답은 실패로 처리한다.
query에는 API 버전 같은 공개 설정을 사용할 수 있다.
`provider: api`의 선택·설정 적용은 해당 회사 API를 임베딩에 사용한다는 뜻이다.
적용 요약에는 등록한 endpoint·모델과 허용 기억 본문·검색 질의의 전송을 표시하고 사용자 확인을 받는다.
`local`은 준비한 로컬 모델을, `keyword_only`는 키워드 검색을 사용한다.
setup의 인증값 입력은 [YAML 인증 필드](#접속-정보와-인증값)를 사용하고 저장한 임베딩 구성에는 `credential_ref`를 둔다.

이전 입력의 `provider: openai_compatible`은 `provider: api`·`adapter: openai_compatible`로 해석한다.
저장·공개 설정은 이 정규 형식을 사용하며 같은 endpoint·모델·차원의 기존 벡터 식별은 유지한다.
기존 profile은 조회 시 메모리에서 정규화하고 저장 파일·개정·벡터를 유지한다.
기존 YAML 초안은 편집한 바이트와 확인 절차를 보존하고 재검증에서 같은 의미로 해석한다.
이전 boolean `allow_remote`는 true·false 모두 정규 설정에서 정리하며 저장한 `provider`로 사용 방식을 결정한다.
API 사용 여부 변경은 setup의 제공자 선택·변경 요약·적용으로 진행한다.

기본 setup은 [YAML의 `embedding`](#사용자용-setup-yaml)을 검증·적용한다.
개별 관리에는 `memory configure PROFILE --config CONFIG_JSON --expected-revision N`으로 임베딩 객체 파일만 적용할 수 있다.
대상 profile은 미리 존재해야 하며 명령은 다른 연결·정책을 보존하고 `embedding`만 교체한다.
확인한 구성의 개정을 전달하고 충돌하면 현재 구성의 차이를 다시 확인한 뒤 적용한다.
검증 실패는 현재 설정을 유지하며 같은 설정의 재적용은 기존 개정을 반환한다.
설정 저장은 임베딩 구성의 검증·개정 적용까지 담당한다.
프로그램 준비·진단·재색인은 각각의 관리 요청으로 수행하고 업무 자료 조회는 승인된 업무로 수행한다.

선택에 따른 준비·상태 조회·시험 진단은 [환경 명세](../installation/environment.md#임베딩-선택과-준비)를 따른다.
전송 전 권한 검사·실패 처리·모델 변경 후 색인 호환성은 [기억 사양](../tasks/memory.md#혼합-검색과-색인)이 소유한다.

## 관리 등록과 진단

setup은 [호스트 질문](../hosts/plugins.md#setup의-정형-질문) → YAML 검증·확인·적용 → 프로그램·인증·연결 진단·기억 준비로 진행한다.
연결 진단은 [도구 등록 계약](../resources/contract.md#도구-등록)의 초기화·기능 확인을 수행하고 실제 자료 조회는 업무 계획 승인 뒤 시작한다.
저장·리소스별 연결·기억·현재 MCP 연결 결과와 남은 조치를 안내하고 준비 실패는 저장한 설정에서 미완료 단계만 재시도한다.
완료한 profile은 [대화의 새 업무 대상](#선택과-기본값)으로 안내한다.

## 사용자용 setup YAML

최초 setup과 이후 설정 변경에 같은 profile별 YAML을 사용하는 계약이다.
선택한 연결의 접속 정보·인증, 임베딩과 필요한 권한·보존 설정을 이 파일에서 편집한다.
호스트는 리소스 선택과 진행을 안내하고 필드 생성·검증·변환은 DAERI 코드가 담당한다.
업무에서 사용할 연결·범위와 자율적인 질의·수행 선택은 [계획 승인](../tasks/approval.md)을 따른다.

### 생성과 파일 위치

사용자 편집 파일은 사용자 저장 영역의 `config/profiles/<profile>.yaml`이다.
기준 개정·규격 지문 등 내부 편집 상태는 `setup/<profile>/draft.json`에서 관리한다.
적용한 뒤에도 같은 YAML을 계속 편집하고 검증·확인·적용하며 활성 설정은 아래의 [저장 계약](#설정과-업무-기록의-저장)을 따른다.

세팅 시작 시 `setup status PROFILE`이 이 두 파일과 이전 위치인 `setup/<profile>/setup.yaml`을 확인한다.
상태 조회는 저장소 개설·초안 생성 전에도 실행할 수 있는 로컬 읽기 전용 명령이다.
runtime은 경로·파일 종류와 읽기 가능 여부를 검사하고 `profile`·`state`·`path`를 JSON으로 반환한다.

| 검사 결과 | 반환과 처리 |
|---|---|
| 사용자 YAML·이전 YAML·내부 상태 모두 부재; 상위 디렉터리 부재 포함 | `state: new`, `path: null`, 종료 코드 0; 리소스·기억 검색 방식 선택 |
| 사용자 YAML과 내부 상태가 읽을 수 있는 일반 파일 | `state: resume`, 사용자 YAML의 `path`, 종료 코드 0; 저장된 편집·선택으로 재개 |
| 이전 YAML과 내부 상태만 읽을 수 있는 일반 파일 | `state: resume`, 이전 YAML의 `path`, 종료 코드 0; 다음 초안 재개에서 위치 이관 |
| 두 위치의 YAML이 함께 존재 | `INVALID_INPUT`; 두 파일을 보존하고 사용할 편집본의 복구 안내 |
| YAML·내부 상태 중 일부만 존재·심볼릭 링크·경로 종류 불일치 | `INVALID_INPUT`; 기존 자료를 보존하고 복구 안내 |
| 읽기·권한 오류 | `STORE_UNAVAILABLE`; 기존 자료를 보존하고 복구 안내 |

오류는 [관리 CLI의 공통 오류](../../development/dependencies.md#관리-입력과-결과)와 종료 코드 1로 반환한다.
호스트는 코드와 현재 단계로 복구 방법을 안내한다.
파일 내용·필드·스키마·profile 개정의 유효성은 초안 재개와 전체 검증 단계에서 확인한다.

`setup draft PROFILE`은 이전 위치에만 있는 YAML과 내부 상태를 확인해 사용자 설정 위치로 옮긴다.
위치 이관은 원문 바이트·주석·인증 참조와 기존 내부 기준을 보존하고 이후 재개·추가·`--refresh`는 각각의 입력 조건을 적용한다.
위치만 옮긴 경우 기존 검증의 확인값을 유지한다.
이관 완료 전 저장 실패는 이전 파일을 유지하거나 새 경로를 정리하며, 이관 완료 뒤 후속 저장 실패는 새 위치와 기존 기준에서 재개한다.
이관 전 `setup validate`·`setup apply`는 상태 조회에서 확인한 이전 파일을 사용할 수 있다.
두 위치의 충돌·불완전한 파일 쌍은 복구한 뒤 다시 요청한다.

먼저 [호스트 질문 계약](../hosts/plugins.md#setup의-정형-질문)으로 리소스 종류·제품과 제품별 연결 개수를 확정한다.
호스트는 각 제품의 확정한 개수 N을 해당 recipe의 연결 인수 N개로 변환한다.
각 연결은 기본 이름의 `--resource RECIPE` 또는 사용자가 지정한 역할 이름의 `--resource INSTANCE=RECIPE`로 전달한다.
개수 질문·응답 검증은 호스트가, 전달된 recipe·연결 이름·블록 검증은 runtime이 담당한다.
개수는 이번 초안 생성에서 구성할 제품별 연결 수이며 호환되는 기존 연결을 재사용하고 부족한 연결을 생성한다.
예를 들어 Jira 2개는 `--resource issue-jira`를 두 번 전달한다.
같은 선택으로 다시 생성하면 해당 두 자리를 재사용한다.

`setup draft`는 선택한 연결의 `setup_fields`로 사용자 YAML과 내부 편집 상태를 생성한다.
같은 종류·제품의 여러 연결도 서로 다른 인스턴스 블록으로 구성한다.

새 파일에는 profile·인스턴스 이름·어댑터 선택값을 미리 채운다.
호환되는 기존 연결은 저장한 입력값을 채우고 새 필드에만 스키마의 기본값을 표시한다.
기본값 없는 필수값은 비워 두고 설명·가상 예시를 주석으로 표시한다.
`embedding`도 표시한 필드마다 의미·입력 형식을 주석으로 안내한다.
API 연결에는 주소·모델·인증 입력과 허용 기억·검색 질의의 전송을 설명하고 선택 필드가 있으면 차원·시간 제한도 함께 표시한다.
공통 필드의 설명은 runtime이, 연결 규격별 설명은 해당 [임베딩 어댑터](../tasks/memory.md#임베딩-api-계약)가 소유한다.

일반 재개는 저장한 선택·블록·편집값을 유지한다.
연결 추가 요청에는 부족한 블록만 추가하고 기존 값은 보존하며 주석·서식은 다시 생성할 수 있다.
파일 작성 완료 응답은 검증으로 이어간다.
필드가 달라진 어댑터는 차이와 수정할 항목을 안내한 뒤 다시 검증한다.
기본 실행 환경이 미준비이면 [최초 준비](../installation/environment.md#아무-개발-도구가-없는-최초-진입) 후 등록 스키마로 YAML을 생성한다.

설정 파일과 내부 상태는 플러그인 캐시·현재 소스 저장소와 분리한다.
새 디렉터리는 `0700`, 새 파일은 `0600`을 지원하는 OS에서 적용해 현재 사용자 전용으로 생성한다.
setup을 다시 실행하거나 호스트를 바꾸어도 같은 사용자 저장소의 파일을 사용한다.
profile 삭제 때 사용자 설정 YAML·이전 YAML과 내부 편집 상태를 함께 정리한다.
사용자가 별도로 복사한 파일은 사용자 관리 영역에 남는다.

### 공통 구조와 어댑터 입력

`resources`의 키는 profile 안의 연결 식별자이며 제품 선택은 각 블록의 `adapter`로 구분한다.
이름을 생략한 `--resource RECIPE`는 runtime이 범주의 소문자 이름으로 연결을 생성한다.
기본 이름은 `db`·`cache`·`infra`·`source`·`document`·`issue`이며 추가 범주도 같은 규칙을 따른다.
같은 종류의 복수 연결은 `db-2`·`db-3`처럼 두 번째부터 번호를 붙인다.
이미 다른 연결이 해당 이름을 사용하면 다음 빈 번호를 선택한다.

자동 선택은 기본 이름·번호의 각 자리를 확인한다.
초안은 같은 이름·recipe인 연결의 입력을 재사용한다.
기존 profile은 선택한 recipe와 실행 파일·인수·기능·어댑터의 공통 호환 검사를 통과한 연결을 재사용한다.
다른 recipe의 초안·수동 HTTP·다른 runtime 등 호환 조건이 다른 연결은 보존하고 다음 번호를 선택한다.
명시한 이름은 먼저 예약하고 자동 선택은 그다음 빈 자리를 사용한다.
기존 연결의 식별자·인증 참조·업무 자료는 `postgres` 같은 제품 기반 이름도 포함해 저장한 이름으로 유지한다.
역할을 구분할 때는 `--resource primary-db=RECIPE`처럼 이름을 명시할 수 있다.
명시한 이름은 그대로 사용한다.
같은 이름에 다른 제품을 명시 선택하면 새 제품의 템플릿으로 초안을 구성하고 [검증·확인·적용](#검증과-변경-의미)으로 연결을 교체한다.

| YAML 항목 | 의미와 입력 기준 |
|---|---|
| `profile` | 대상 profile; setup 요청 대상과 같아야 함 |
| `resources` | 인스턴스 이름을 키로 갖는 객체; 선택한 연결만 포함 |
| `resources.<이름>.adapter` | 카탈로그의 recipe ID; 선택 단계에서 자동 입력하며 범주와 runtime 어댑터는 코드가 해석 |
| `resources.<이름>.inputs` | 해당 어댑터의 `setup_fields` 필드 ID와 값; 접속 정보·공개 인증 설정 |
| `resources.<이름>.credentials` | 어댑터가 제공한 논리 인증 필드와 입력값; 아래 인증값 계약 적용 |
| `resources.<이름>.policy` | 호환용 [추가 제한](#자료-제공보관-정책); 생략·null·빈 객체는 계획 기반 기본값 |
| 선택 profile 설정 | `core_context`·`retention_days`·`long_term_memory_days`·`memory_policy`; [공개 설정](#구현한-profile-입력과-공개-설정)의 의미·타입을 그대로 사용 |
| `embedding` | 선택한 제공자의 설정만 생성; [임베딩 제공자 선택](#임베딩-제공자-선택)의 의미·타입을 그대로 사용 |

기본 템플릿은 `profile`·`resources`와 해당 어댑터의 접속·인증 필드를 보여 준다.
선택 설정은 현재 값을 수정하거나 사용자가 요청했을 때 필요한 항목만 추가한다.
`inputs`의 필드·타입·목록·선택값은 선택한 어댑터의 입력 스키마에서 결정한다.
패키지 버전·실행 파일·명령 인자·환경 변수·MCP 도구 매핑·내부 개정은 runtime이 카탈로그와 관리 정보에서 구성한다.
기존 초안·profile의 임베딩 선택을 재사용하며 둘 다 없을 때만 방식부터 선택한다.
회사 API를 선택하면 연결 방식을 확인하고 해당 어댑터의 입력만 생성한다.
연결 방식 확인이 남아 있으면 아래의 미완료 초안으로 보존한다.
이 상태의 검증은 `embedding.adapter`의 선택 필요를 반환하고 적용은 완성된 등록 어댑터 설정에서 진행한다.

```yaml
embedding:
  provider: api
  adapter: null
```

회사 API 규격은 해당 조직의 계약으로 확인하고 등록된 연결 방식과 대조한다.
추가 규격은 어댑터를 구현·등록·검증한 뒤 선택할 수 있으며 사용자는 초안을 보존하거나 키워드 전용으로 변경할 수 있다.
기억 검색 입력은 선택한 제공자에 필요한 필드로 구성한다.

현재 연결별 입력은 다음과 같다.
접속 정보는 `inputs`, 비밀번호·토큰은 같은 블록의 `credentials`에 입력한다.

| 범주 | 접속 입력 | 인증 입력 |
|---|---|---|
| DB | 호스트·포트·데이터베이스·사용자명 | `password`; 기존 URI 방식은 `uri` |
| Cache | 호스트·포트·저장 영역 번호·TLS·클러스터 모드 `cluster_mode`·선택 사용자명 | `password` |
| Infra | 제공자 인증 profile·지역·계정 | 제공자 로그인 |
| Source | 로컬 디렉터리의 절대 경로 `path` | 없음 |
| Document | 서버 주소·사용자명 | `token` |
| Issue | 서버 주소·인증 방식·사용자명 | `token` |

프로젝트·이슈 키·검색식 등 세부 조회 대상과 질의는 업무 목표·승인 범위 안에서 호스트가 선택한다.

소스 코드 제품 `source-local`을 두 개 선택한 가상 예시는 다음과 같다.
경로마다 별도 연결과 업무 근거를 사용하며 준비·진단은 디렉터리 접근을 확인한다.

```yaml
profile: service-prod
resources:
  source:
    adapter: source-local
    inputs:
      path: /Users/example/projects/service-api
  source-2:
    adapter: source-local
    inputs:
      path: /Users/example/projects/service-web
```

도메인이 다른 이슈 시스템도 같은 profile의 별도 연결로 등록한다.
아래 가상 예시는 `--resource issue-jira`를 두 번 선택한 경우다.
두 연결은 서버·인증 참조·자료 정책을 각각 가지고 업무 계획에서도 개별 `instance_id`로 승인받는다.

```yaml
profile: service-prod
resources:
  issue:
    adapter: issue-jira
    inputs:
      server: https://team-a.atlassian.net
      auth_type: api_token
      username: reader@example.test
    credentials:
      token: null
  issue-2:
    adapter: issue-jira
    inputs:
      server: https://issues.team-b.example.test
      auth_type: personal_token
      username: ""
    credentials:
      token: null
```

`api_token`은 계정·API 토큰, `personal_token`은 Server/Data Center의 개인 액세스 토큰(PAT)을 사용한다.
Cloud는 `api_token`과 사용자명이 필요하다.
두 방식 모두 `credentials.token`에 입력하고 선택한 인증 방식의 저장 참조로 연결한다.
제품별 조회·인증 경계는 [실제 지원 범위](../resources/adapters.md#어댑터별-실제-지원-경계)를 따른다.

### 접속 정보와 인증값

runtime은 어댑터가 선언한 인증 필드만 생성하고 각 필드에 용도·입력 방법을 한국어 주석으로 표시한다.
새 필드는 `null`, 기존 필드는 현재 인증 참조의 `{ref: ...}`로 생성한다.

리소스 인증은 `resources.<이름>.credentials`, 임베딩 API 인증은 `embedding.credentials`에 둔다.
현재 API 방식의 인증 필드는 `api_key`다.

각 인증 필드의 값은 다음 중 하나다.

| 값 | 검증과 적용 |
|---|---|
| 생략 또는 `null` | 해당 연결의 현재 참조 유지; 새 연결은 runtime이 기본 참조 생성 |
| 비어 있지 않은 한 줄 문자열 | 최대 16,384자, 제어 문자 검사 후 확인한 적용에서 OS 인증 저장소에 등록 |
| `{ref: credential:이름}` | 지정한 OS 인증 참조 사용 |
| `{ref: env:환경변수명}` | 실행 환경의 해당 참조 사용 |

문자열 등록 대상은 `credential:` 참조이며 `env:` 참조는 현재 환경에서 해소한다.
같은 인증 참조에 여러 문자열을 지정하면 값의 일치를 검증한다.
인증 입력의 위치·타입·알 수 없는 필드는 검증 결과의 경로와 고정 수정 안내로 반환한다.
미입력 상태로 설정을 적용할 수 있으며 실제 인증 준비는 `auth status`와 연결 진단에서 확인한다.

로컬 DAERI가 YAML 원문을 읽고 호스트는 검증 요약·인증 참조·등록 상태를 사용한다.
검증은 인증 저장소의 값 쓰기 없이 설정과 인증 입력을 확인한다.
적용은 확인한 파일·개정·계약을 대조한 뒤 문자열 인증값을 OS 저장소에 등록하고 같은 파일의 문자열을 `{ref: ...}`로 치환한다.
profile JSON·SQLite·관리 정보와 공개 결과에는 인증 참조·처리 상태를 저장한다.
파일 지문과 확인값은 실제 인증 입력의 변경도 감지한다.

```yaml
embedding:
  provider: api
  adapter: openai_compatible
  endpoint: https://embedding.example.test/v1/embeddings
  model: company-embedding
  credential_ref: credential:service-prod.embedding
  credentials:
    api_key: null  # 회사 API 키를 입력하거나 기존 인증 참조를 유지합니다.
```

저장된 API 설정의 `credential_ref`는 위 인증 필드로 연결한다.
같은 필드에 새 문자열을 입력하면 기존 참조의 값을 갱신하고 나머지 인증은 재사용한다.
연결 실패 시 같은 YAML의 잘못된 접속·인증 항목만 수정하고 검증·확인·적용 뒤 해당 연결을 재진단한다.
제공자 로그인은 선택한 제공자의 별도 로그인 경로를 따른다.

### 검증과 변경 의미

YAML은 UTF-8의 단일 문서이며 현재 JSON과 같은 크기·중첩 제한을 적용한다.
키는 문자열이고 값은 JSON으로 표현 가능한 객체·목록·문자열·숫자·boolean·null만 허용한다.
중복 키·알 수 없는 필드·비유한 숫자·사용자 정의 태그·앵커·별칭·merge는 거부한다.
파일의 문자열은 그대로 값으로 처리한다.
문자열·숫자는 파싱된 타입으로 필드 스키마를 검증하고 어댑터의 정규 설정으로 변환한다.
`null`·빈 목록은 해당 필드 스키마의 허용 조건으로 검증한다.
AWS 연결의 `account`는 12자리 문자열 또는 12자리 정수를 받고 저장·검증 미리보기에는 문자열을 사용한다.
예를 들어 `account: 123456789012`와 `account: "123456789012"`는 같은 계정으로 해석한다.
앞자리가 0인 계정은 문자열로 보존하며 소수·boolean·음수·자리 수가 다른 값은 입력 오류로 반환한다.
YAML의 [주석과 자료 표현](https://yaml.org/spec/1.2.2/)을 사용하되 입력 기능은 이 제한된 범위로 정한다.

`setup validate`는 전체 파일의 문법·profile·인스턴스·어댑터·필수값·정책과 기존 연결의 갱신·교체 구성을 저장 전에 검증한다.
입력 오류는 `issues`의 필드 경로 또는 문법 오류 위치·코드·짧은 한국어 수정 안내로 반환한다.
예를 들어 `resources.db.inputs.host`의 미입력은 해당 경로와 필수값 수정 안내로 반환한다.
검증의 실행 범위는 로컬 초안·스키마·현재 구성의 대조이며 실패하면 활성 설정을 유지한다.
개정·계약 충돌과 저장소 실패는 공통 오류 코드로 구분하고 아래 재시도 절차를 따른다.

파일에 있는 인스턴스의 명시한 필드만 추가·갱신하며 생략한 기존 리소스·설정·정책은 보존한다.
기존 필수값은 호환 설정에서 재사용하고 명시한 빈값은 해당 스키마의 값으로 검증한다.
같은 어댑터의 `inputs`는 필드별로 갱신하고 명시한 목록과 `policy`·`memory_policy`·`embedding` 객체는 해당 값 전체를 교체한다.
정책의 null·빈 객체는 계획 기반 기본값이다.
같은 어댑터의 내용 있는 기존 제한은 생략 시 그대로 유지하고 명시한 변경은 확인한 적용에서 반영한다.
기간의 `null`은 무기한이라는 기존 의미를 따른다.
새 인스턴스는 선택·초안 검증으로 추가하고 삭제는 별도 명시 관리 요청으로 처리한다.
기존 이름에 다른 어댑터를 명시 선택하면 해당 제품의 새 템플릿과 입력으로 교체안을 검증한다.
대상·환경·인증·기능은 새 어댑터의 계약으로 구성하며 변경 요약을 확인한 적용에서 함께 저장한다.
과거 업무는 당시 설정 스냅샷을 보존하고 교체한 연결은 준비·진단 뒤 새 업무에서 사용한다.

새 연결은 해당 어댑터의 읽기·관찰 기능과 실제 접근 권한을 사용하며 [어댑터 지원 경계](../resources/adapters.md#어댑터별-실제-지원-경계)를 따른다.
호스트는 실제 읽기 권한과 명시한 범위 안에서 필요한 질의·키 탐색·후속 조회를 선택한다.
명시적 관리자 조건은 전체 JSON의 `capabilities[].constraints`로 적용하고 자료 정책은 보존한다.
일반 접속값 갱신은 기존 도구 선택과 조건을 유지한다.
새 읽기 계약으로 전환하는 setup 적용은 바뀔 기능 범위를 미리보고 확인한 뒤 갱신한다.
알려진 과거 생성 기본값인 전체 DB의 자동 행 상한과 Jira의 기본 페이지 상한만 새 계약으로 교체한다.
사용자 지정 조건이 있는 과거 연결은 해당 조건·도구 선택을 유지하고 새 도구는 확인한 기능 갱신으로 추가한다.
과거 SQL 테이블·컬럼 등 의미 제약의 실행·갱신은 `UNSUPPORTED_CONSTRAINT`로 반환한다.
이 경우 실제 DB 권한 또는 지원하는 명시적 필드 조건으로 관리 설정을 바꾸고 재진단·새 계획으로 전환한다.
내용 있는 기존 제한 때문에 계획을 구성할 수 없으면 해당 항목과 가능한 범위를 설명한다.
명시적으로 설정을 바꾼 뒤 업무 연결은 [맥락 갱신 조건](../mcp/tasks.md#daeri_task_update)에 따라 스냅샷 갱신 또는 새 업무로 진행한다.
설정 적용·인증·업무 계획은 각 대상과 범위에 맞는 사용자 확인을 받는다.

### 확인·적용·재개

1. 초안 생성 때 소유 profile의 식별자·기준 개정 또는 신규 생성 기준을 내부 관리 정보에 연결한다.
2. 편집한 파일 전체를 검증하고 추가·변경 항목, 접근·자료 정책과 필요한 준비 작업을 요약한다.
   채워 둔 기본값도 요약에 포함하고 사용자가 파일 내용과 변경 범위를 확인하면 확정한다.
   확인 단위는 전체 파일과 변경 요약이다.
3. 확인한 파일 내용의 지문·profile 식별자·기준 개정·어댑터 계약이 그대로일 때만 적용한다.
   파일이나 현재 설정이 바뀌면 차이를 제시하고 새 검증·확인을 받는다.
   새 profile은 적용 시점에도 같은 이름이 미등록이어야 하며 다른 호스트의 동시 생성은 충돌로 거부한다.
4. 같은 setup 저장 트랜잭션에서 인증값의 기존 상태 확인·변경과 설정·초안 반영을 직렬화한다.
   모든 인스턴스를 검증하고 변경할 인증값을 OS 저장소에 등록한 뒤 하나의 profile 개정으로 저장한다.
   성공하면 같은 YAML의 인증 문자열을 참조로 치환하고 초안을 반환한 profile 식별자·개정에 연결한다.
   인증·설정·파일 저장이 실패하면 기존 값으로 복구하고 편집 초안을 보존한다.
   복구가 미완료이면 `CREDENTIAL_UPDATE_PENDING`을 반환하며 같은 파일의 재검증·확인·적용으로 다시 시도한다.
   같은 설정·인증값의 재적용은 기존 개정을 반환하며 실제 인증값이 바뀌면 새 개정으로 저장한다.
5. 설정 저장 후 확인한 범위에서 프로그램 준비·인증·연결 진단을 진행하고 기억 준비·현재 호스트 MCP 연결 상태를 각각 확인한다.
   저장 이후 준비가 실패하면 검증한 설정을 유지하고 해당 리소스의 미완료 단계만 재시도한다.

진행 중인 업무는 저장한 스냅샷·승인을 유지한다.
YAML은 최초 setup과 이후 관리에 사용하는 편집용 입력이며 적용 뒤의 설정 정본은 [개정별 profile JSON과 SQLite의 활성 개정](#설정과-업무-기록의-저장)이다.
다른 PC로 설정을 이동할 때는 인증 참조로 정리한 YAML 또는 공개 JSON export를 사용한다.
YAML 이동은 대상 PC의 setup으로 편집 상태를 만든 뒤 해당 사용자 설정 파일에 공개 설정을 반영한다.
이동한 PC의 인증·실행 환경·연결은 그 PC에서 준비·진단한다.
업무·기억·승인 기록은 해당 사용자 저장소에 유지한다.
전체 JSON 이동은 `profile import/export`, 정형 스키마를 제공하는 선택 연결의 편집은 YAML을 사용한다.

### 관리 명령과 재시도

| 명령 | 입력과 결과 |
|---|---|
| `setup catalog` | `groups`의 리소스 종류·기본 연결 이름·제품과 `embedding_adapters`의 구현된 API 연결 방식 반환 |
| `setup status PROFILE` | [초안 파일 상태](#생성과-파일-위치)를 읽어 신규·재개 또는 복구 필요 반환 |
| `setup draft PROFILE --resource RECIPE` | 종류별 기본 이름으로 초안·기준 상태 생성; 여러 연결은 옵션 반복 |
| `--resource INSTANCE=RECIPE` | 역할을 나타내는 명시적 연결 이름으로 생성·재사용 |
| `--embedding PROVIDER` | 초안 생성 시 선택한 `local`·`api`·`keyword_only` 포함; 이전 `openai_compatible` 입력도 해석 |
| `--embedding-adapter ID` | 회사 API의 등록 연결 방식 선택; 해당 어댑터의 입력 필드 생성 |
| `setup validate PROFILE` | 로컬 초안·현재 구성 대조, 전체 검증·변경 요약·확인값 반환 |
| `setup apply PROFILE --confirm TOKEN` | 확인한 파일·현재 개정·계약 대조 후 인증 등록·일괄 저장·YAML 참조 치환 |
| 초안 생성의 `--refresh` | 충돌 내용을 검토한 뒤 기준 상태만 갱신; 파일 편집 내용 유지 |

초안 생성은 `path`·`profile`·`resources`·`existing`·`base_revision`을 반환한다.
`--embedding`을 생략하면 기존 초안·profile의 선택을 유지하고 둘 다 없으면 저장 기본값인 로컬을 쓴다.
새 초안의 사용자 흐름은 제공자 선택을 명시적으로 받은 뒤 생성한다.
새 `api` 선택의 연결 방식은 `--embedding-adapter`로 전달하며 생략하면 위 미완료 초안을 생성한다.
기존 API 설정의 재개는 저장한 연결 방식과 입력을 유지한다.
YAML의 `embedding` 블록을 생략하면 저장된 제공자 설정·인증 참조를 적용하고 같은 구성의 적용은 기존 개정을 유지한다.
검증은 `valid`·`complete`·`issues`와 유효한 전체 입력의 `preview`·`confirmation_token`을 반환한다.
`preview`의 인증값은 참조이며 `changes.credentials`는 등록할 문자열이 있는 필드 경로의 목록이다.
`changes.resource_contracts`는 읽기 선택·조건이 바뀌는 기존 연결 이름별 `before`·`after` 요약이다.
각 요약은 `discover_tools`, 선택한 `capabilities`의 `capability_id`·`tool_name`·`constraints`와 `enabled_tools`를 포함한다.
`enabled_tools`는 하위 MCP의 `ENABLED_TOOLS` 필터이며 필터가 없으면 `null`이다.
`discover_tools: true`는 연결 진단에서 확인한 읽기 도구를 추가할 예정이라는 뜻이며 실제 도구 목록은 진단 뒤 확정한다.
관리자 조건을 유지해 기능 선택이 그대로인 연결은 이 목록에서 제외한다.
`changes.changed`는 인증 입력을 포함한 변경 예정 상태이며 같은 값의 실제 재등록·개정 여부는 적용에서 판정한다.
오류는 검증한 필드 경로·코드·고정 수정 안내로 구성한다.
확인값은 검증한 파일·기준 상태·적용 예정 설정에 연결하며 어느 하나라도 바뀌면 적용을 거부한다.

profile 개정·어댑터 스키마가 충돌하면 최신 구성과 초안의 차이를 검토하고 `--refresh`로 기준을 갱신한다.
스키마에 없는 `inputs` 필드는 현재 연결 입력 계약에 맞춰 수정한 뒤 다시 검증·확인한다.
`--refresh`는 편집값을 보존하고 기준 개정·스키마 지문을 갱신한다.
중단·검증 실패에는 활성 설정과 편집 초안을 유지한다.

## 리소스 설정 입력과 검증

YAML 생성과 기존 JSON 관리 명령은 같은 어댑터 입력 계약을 사용한다.
JSON 명령은 개별 연결을 관리하는 경로로 유지하며 기본 setup은 위 YAML 절차를 따른다.

정형 setup의 공개 입력은 선택한 어댑터의 `setup_fields`, 인증 입력은 `setup_credentials`가 소유한다.
각 필드는 JSON Schema의 타입·제목·설명·가상 예시·기본값·허용 값과 제약, 필수 여부, 설정 목적지 경로를 정의한다.
하나의 입력값을 실제 대상과 연결 환경 등 여러 위치에 함께 반영해야 하면 같은 필드에 목적지 경로들을 둔다.
Skill·호스트는 이 입력 계약을 참조해 해당 제품의 필드·기본값·설명을 사용한다.

`resource setup-schema RECIPE`는 다음 자료를 반환한다.

| 반환 항목 | 의미 |
|---|---|
| `recipe_id`, `adapter`, `type`, `display_name` | 선택한 설치 조합·정식 어댑터·범주·제품 표시명 |
| `input_schema` | 입력 객체의 JSON Schema; 필드 설명·타입·제약과 `required` 포함 |
| `configuration_paths` | 입력 필드별 리소스 설정 목적지; 기존 값 재사용과 적용에 사용 |
| `authentication.credential_environment` | 해당 recipe가 자격 증명을 받는 환경 변수 이름 목록 |
| `authentication.fields` | 인증 환경 변수별 논리 `field`·한국어 `description`; YAML 인증 필드 생성에 사용 |
| `authentication.provider_login` | 해당 recipe의 제공자 로그인 지원 여부인 boolean |

리소스의 `setup_credentials`는 인증 환경 변수에 논리 `field`와 `description`을 연결한다.
`resource_credential_fields(resource)`는 현재 인증 방식에 필요한 논리 필드별 `reference`·`description`·`environment`를 반환한다.
임베딩 API의 같은 메타데이터는 설정 참조 키에 논리 필드·설명을 연결하며 `embedding_credential_fields`가 `reference`·`description`·`config_key`로 해석한다.
생성기는 이 메타데이터로 YAML 인증 블록과 주석을 구성하고 원래 참조는 profile의 등록 설정에 유지한다.

정형 setup은 `setup_fields`를 제공하는 연결을 지원하며 그 밖의 연결은 전체 JSON 관리 경로를 안내한다.

입력은 필드 ID를 키로 사용하는 값 객체이며 파싱된 문자열·숫자·목록의 타입으로 검증한다.
검증을 통과한 입력은 어댑터의 `normalize_setup_values`가 저장 표현으로 변환한 뒤 목적지에 반영한다.
기본 구현은 입력 타입을 유지하고 어댑터는 스키마가 허용한 대체 표현의 변환을 소유한다.
`finalize_setup_resource(resource, profile_name=...)`는 대상 profile과 반영한 입력으로 연결·인증 참조를 완성한다.
생성한 연결은 공통 구조·기능 목록 검사 뒤 어댑터의 최종 연결 검증을 거친다.
예를 들어 Issue의 토큰 종류를 바꾸면 선택한 인증 필드와 그 인스턴스의 참조를 구성한다.
입력·인증·조회 상한은 위 [YAML 검증과 변경 의미](#검증과-변경-의미)를 따른다.

`resource validate-setup RECIPE VALUES_JSON`은 UTF-8 JSON 파일의 값 객체를 부분 검증한다.
`VALUES_JSON` 인자는 공개 값 객체를 담은 파일의 경로다.
결과는 다음 검증 상태와 필드별 오류로 구성한다.

| 반환 필드 | 의미 |
|---|---|
| `valid` | 현재 제공한 값이 스키마와 지원 범위를 만족하는지 여부 |
| `complete` | 모든 필수값이 있고 전체 입력이 유효한지 여부 |
| `missing_fields` | 아직 없는 필수 필드 ID 목록 |
| `issues` | 검증 실패 필드의 `field`와 오류 `code` 목록 |

부분 검증의 `valid`·`complete`는 개별 필드 스키마와 필수값의 충족 여부다.
실제 저장은 전체 입력을 구성하고 인증 방식·계정 같은 필드 간 조건과 최종 연결 검증까지 통과해야 한다.
제공한 값이 유효하면 필수값이 남아 있어도 종료 코드는 0이며 `missing_fields`로 남은 입력을 알린다.
제공한 값의 검증 실패는 종료 코드 1이다.

스키마 조회와 부분 검증의 입력은 배포 스키마·공개 값 파일이며 로컬 함수의 반환으로 완료한다.
Plan 모드에서는 스키마 조회와 이미 있는 개별 JSON 입력 파일의 검증을 수행할 수 있다.
파일 생성·설정 적용·프로그램 준비·로그인·진단은 실행 가능한 모드에서 수행한다.
각 처리는 현재 호스트 모드의 파일·실행 권한 안에서 수행한다.

입력과 실행 범위를 확인한 뒤 `resource configure RECIPE --profile NAME --instance ID --values VALUES_JSON --expected-revision N`으로 해당 인스턴스를 적용한다.
이 명령은 기존 profile만 수정하므로 새 profile이면 먼저 실행 모드에서 `profile create`로 만들고 현재 개정을 확인한다.
`--expected-revision`은 필수이며 적용 요약을 확인받은 구성의 개정을 전달한다.
충돌하면 최신 설정과 차이를 읽고 변경된 값·적용 범위를 다시 확인한 뒤 그 개정으로 진행한다.
한 번 확인한 범위의 여러 리소스를 순차 적용할 때는 직전 `configure` 성공의 반환 개정을 다음 기대 개정으로 이어간다.

같은 어댑터의 기존 인스턴스를 갱신할 때 외부 서비스는 `stdio` 연결·현재 recipe 전용 실행 파일 경로·인자가, 로컬 Source는 `{"transport":"host"}` 연결이 일치해야 한다.
`capabilities`의 기능 ID·도구 이름 쌍도 recipe와 같은 순서여야 한다.
같은 어댑터의 수동 HTTP·사용자 정의 연결은 전체 JSON import 경로로 관리한다.

runtime은 호환되는 기존 인스턴스의 생략한 입력·자료 정책·명시적 조건을 유지한다.
기존 이름에 다른 어댑터를 명시하면 선택한 제품의 템플릿과 입력으로 교체한다.
신규·교체 인스턴스는 `policy: null`과 해당 어댑터의 읽기·관찰 기능을 사용한다.

전체 필수 입력·최종 연결 검증을 통과한 구성만 저장하고 다른 리소스·profile 설정은 유지한다.
중단·검증 실패는 기존 구성을 유지하고 같은 구성의 재적용은 기존 profile·개정을 반환한다.

기존 관리형 연결의 기능 계약은 위 `resource configure`에 `--refresh-contract`를 명시해 갱신할 수 있다.
사용자용 YAML 적용은 검증 미리보기와 확인값에 계약 전환을 포함하고 확인한 적용에서만 저장한다.
이전 생성 기본값은 전환하고 사용자 지정 조건은 보존 또는 지원 오류로 처리하며 상세 범위는 위 [변경 의미](#검증과-변경-의미)를 따른다.
갱신 후 명시적으로 재진단하고 새 기능 계약으로 업무 계획을 승인받는다.

설정 적용의 결과는 검증한 profile 개정이며 프로그램 준비·인증·연결 진단은 각 관리 경로로 이어간다.
호스트의 선택·확인과 파일 편집 안내는 [setup 질문 계약](../hosts/plugins.md#setup의-정형-질문)을 따른다.

## 준비 카탈로그와 개별 프로그램 설치

카탈로그는 [사용 예정 환경](../product.md#사용-예정-환경)의 첫 연결에 사용할 검증 대상 조합을 제공한다.
연결 제품의 정본은 카탈로그이며 외부 프로그램의 패키지·버전·실행 이름은 recipe 잠금 파일과 함께 관리한다.
실제 회사 서비스의 자료 접근은 승인한 읽기 호출 결과로 확인한다.

setup의 프로그램 준비는 `resource prepare PROFILE`로 적용한 연결 전체를 입력받는다.
runtime이 저장 순서대로 연결의 범주·어댑터·연결 설정을 카탈로그와 대조해 준비 방식을 결정한다.
로컬 Source는 등록한 경로의 존재·읽기·탐색 접근과 실제 경로 일치 확인만으로 준비를 완료한다.
외부 서비스 연결은 실행 파일·인자와 고정 안전 설정을 확인한 뒤 해당 recipe를 준비한다.
접속 포트·저장 영역처럼 입력 스키마의 목적지로 등록한 값은 사용자 선택을 적용한다.
읽기 전용 제어 등 고정 안전 설정은 계속 대조한다.
실행하는 패키지·버전·준비 명령은 검증한 recipe의 잠긴 조합으로 결정한다.

결과는 전체 `ready`와 연결별 `resources`다.
성공 항목은 `instance_id`·`recipe`·`ready`·`reused`를 반환한다.
외부 프로그램은 `version`·`command`, 로컬 Source는 `transport: host`를 함께 반환한다.
실패 항목은 `instance_id`·`recipe`·`ready: false`·[오류와 다음 조치](../../development/dependencies.md#관리-입력과-결과)를 반환하며 recipe를 식별하지 못한 값은 null이다.

연결별 준비 실패는 결과에 기록하고 나머지 연결을 계속 준비한다.
전체 성공과 빈 연결 목록은 종료 코드 0이며 일부 실패는 1이다.
재실행은 검증된 설치를 재사용하고 미완료 연결의 준비를 이어간다.
개별 연결을 지정할 때는 `resource prepare PROFILE INSTANCE --recipe RECIPE`의 인스턴스·recipe를 함께 전달한다.

프로그램은 사용자 저장소 `tools/` 아래 recipe·패키지 버전·잠금 지문별 격리 환경에 준비한다.
플러그인의 고정된 전용 uv를 절대 경로로 사용하고 [관리 Python과 환경 격리](../installation/environment.md#공통-실행-파일과-환경-격리) 기준을 적용한다.
새 후보를 잠긴 조합으로 설치하고 Python의 격리·패키지 버전·실행 파일을 확인한 뒤 공개한다.
같은 검증 설치는 재사용하며 준비 과정에서 기존 정상 조합·profile 개정·인증·업무 자료를 보존한다.
설치 실패·시간 초과·실행 파일 누락·패키지 버전 불일치는 `CONNECTION_NOT_READY`로 반환한다.
중복 준비는 해당 프로그램의 미완료 상태로 반환한다.

하위 MCP와 DAERI runtime은 각각의 격리 환경과 잠금 파일로 SDK 주 버전을 관리한다.
첫 DB recipe는 상위 패키지의 SQL 파서 요구와 실제 배포 버전의 호환을 위해 명시적인 override를 둔다.
같은 recipe의 SDK 주 버전 제한도 삭제된 API를 사용하는 상위 패키지와 맞추기 위한 조건이다.
정확한 호환 조건과 잠금 조합은 `recipes/db-postgres/pyproject.toml`·`uv.lock`을 설치 기준으로 적용한다.

프로그램 준비와 실제 연결 진단은 별개다.
외부 서비스 진단은 현재 인증 참조·실제 대상 바인딩을 확인하고 하위 MCP의 초기화와 도구 목록에서 읽기 기능의 계약을 등록한다.
로컬 Source 진단은 현재 디렉터리 접근을 확인하고 고정 관찰 기능의 계약을 등록한다.
실제 업무 도구 호출·원격 자료 조회는 진단 이후 승인된 업무 경로에서 수행한다.
실제 연결·대상·읽기 기능의 입출력이나 제약이 바뀌면 해당 연결을 재진단한다.
인증값·SSO 캐시 갱신은 현재 인증으로 이어서 확인한다.

## 선택과 기본값

profile Skill은 [현재 설치의 연결 준비](../hosts/plugins.md#설치부터-업무-시작까지의-실제-경계)를 겸한 `--connect profile list`·`--connect profile show PROFILE`로 공유 저장소의 등록 이름·식별자를 확인하고 현재 대화의 기본 대상을 선택한다.
기존 profile은 저장한 접속·인증·임베딩 선택을 재사용하고 요청한 구성 변경만 setup으로 반영한다.
지정이 없거나 모호하면 호스트의 [정형 질문](../hosts/plugins.md#setup의-정형-질문)으로 선택하고 빈 목록은 setup을 안내한다.
구성 조회 실패·질문 취소·미응답은 이전 선택을 유지한다.

확인한 `profile_id`·이름은 현재 호스트 대화의 맥락에 보존하고 이후 새 업무의 기본 대상으로 사용한다.
새 대화·문맥 압축·호스트 전환 후 선택 증거가 불확실하면 정형 질문으로 다시 선택한다.

work는 새 업무 접수 전에 `--connect profile show PROFILE`로 대상의 현재 이름·식별자와 등록을 확인한다.
사용자가 등록 profile·식별자를 명확하게 지정하면 그 새 업무에 사용하고 대상을 안내한다.
이 지정은 해당 업무에 적용하며 대화의 기본 선택은 유지한다.
명시한 대상이 없으면 현재 대화에서 확인한 기본 대상을 사용한다.
대상을 특정할 수 없거나 지시가 모순되면 접수 전에 정형 질문으로 확인한다.
호스트는 확인한 `profile_id`를 업무 접수 입력에 전달한다.

list-profiles Skill은 이름순의 profile·등록 리소스 범주와 구별에 필요한 식별자를 요약한다.
사용 가능한 기능은 별도 진단으로 확인하고 자료 접근 실패는 해당 읽기 결과로 안내한다.
profile 선택·목록 조회는 저장된 구성·기존 업무·승인을 보존한다.
관리 CLI 시작 시 적용되는 일반 만료 정리 등 사용자 저장소 동작은 그대로 따른다.

업무당 profile 하나를 사용하고 현재 권한과 유효한 계획 승인을 함께 검사한다.
다른 profile의 리소스가 필요하면 사용할 연결들을 하나의 profile로 구성해 새 업무로 시작한다.

## 업무에 고정하는 스냅샷

업무를 시작할 때 선택한 profile 구성·리소스·대상·인증 문맥·정책·보존기간과 기억 정책을 기록한다.
업무 기록의 인증 정보는 비밀을 제거한 인증 참조로 보존한다.
이 기록은 계획과 실행이 어느 환경을 대상으로 했는지 확인하는 기준이다.

승인한 업무의 실행 바인딩은 저장한 연결·계정·대상으로 고정한다.
같은 구성 안의 방법·허용 범위 변경은 [수정 계획](../tasks/approval.md)으로 처리한다.
승인 이후 profile의 대상·인증 주체 자체를 바꿔야 하면 새 업무로 시작한다.

대화의 기본 profile이 바뀌어도 기존 업무의 대상은 유지한다.
무관한 설명·보존 설정·인증값 갱신은 현재 구성을 읽어 이어가고 같은 연결의 도구 의미 변경은 재진단·수정 계획으로, 연결·계정·실제 대상 변경은 새 업무로 확인한다.
work로 기존 업무를 재개하면 저장된 대상·스냅샷을 우선하고 대화 선택과 다른 점을 안내한다.
재개할 때에는 저장된 구성과 현재 권한·연결 상태를 함께 확인한다.
접근 철회·인증 실패는 새 호출을 막되 이미 수행한 호출과 미확인 실행 기록을 보존한다.
기억 조회에도 고정한 대상과 현재 접근·모델 제공 범위를 적용한다.
기존 기억의 제공은 출처·기한·현재 profile 정책을 검사하고 업무 계획에는 실제 적용한 기억을 연결한다.
임베딩 제공자는 현재 profile의 관리 설정을 사용하고 업무의 리소스 대상·승인·스냅샷은 유지한다.
제공자 변경 뒤 벡터는 모델 지문이 일치하는 색인에서 사용하고 그 밖에는 검색 제한·재색인 필요를 알린다.

## 사용자 저장 위치

같은 PC·OS 사용자의 Codex와 Claude Code는 같은 DAERI 설정·업무·기억 저장소를 사용한다.
각 호스트의 실행 환경은 해당 플러그인 사본에 준비하고 생성한 MCP 구성은 선택한 저장소의 해소된 절대 경로를 사용한다.
설정·이력·산출물·기억 정본·검색 색인은 프로젝트 저장소와 플러그인 캐시 밖의 사용자 전용 영역에 보관한다.
실제 OS별 기본 경로·지정 우선순위는 [저장 위치](../../development/dependencies.md#저장-위치와-데이터-역할)를 따른다.
업데이트·재설치·색인 재생성은 이 저장소의 설정·업무 기록·유효 기억을 보존한다.

## 로컬 저장 구조

사용자 설정 YAML·적용된 JSON·사용자별 SQLite·관리 파일·인증 저장소의 책임을 나눈다.
SQLite는 DAERI 내부 로컬 저장 엔진이며 외부 DB 리소스는 등록 어댑터를 통해 연결한다.
별도 DB 서버나 벡터 DB 서버를 운영할 필요가 없는 구성을 기본으로 한다.

### 디렉터리 구성

기본 저장 위치 아래의 구성은 다음과 같다.
모델·연결 도구·작업 영역은 해당 기능을 준비하거나 사용할 때 생성한다.

```text
DAERI/
├── config/profiles/<profile>.yaml
├── setup/<profile>/draft.json
├── profiles/<id>.json
├── daeri.sqlite3
├── records/<id>.json
├── artifacts/<id>.<확장자>
├── workspaces/<업무 지문>/
├── resources/
│   ├── <profile·인스턴스 지문>.json
│   └── processes/<연결 지문>/
├── tools/<recipe>/<버전-잠금 지문>/
│   ├── .venv/
│   └── prepared.json
├── models/
│   ├── prepared.json
│   └── <모델·토크나이저 파일>
├── runtime/
│   ├── python/
│   └── cache/
└── staging/<id>.json
```

`config/profiles`는 사람이 편집할 입력이고 `profiles`는 적용한 구성의 불변 파일이다.
`setup`은 같은 입력을 다시 검증·적용할 기준 개정과 규격 지문을 보관한다.
SQLite가 생성하는 `daeri.sqlite3-wal`·`daeri.sqlite3-shm`은 DB와 함께 사용하는 보조 파일이다.
리소스 도구 준비 중에는 `tools/<recipe>/.prepare.lock/`·`.prepare.<id>/`를 사용하고 정상 종료·실패 시 정리한다.
중단으로 잠금이 남으면 실행 중인 준비의 유무와 후보 상태를 확인한 뒤 복구한다.
설치 사본의 프로그램·임시 파일 수명은 [설치 파일 구성](../installation/environment.md#설치-파일-구성)을 따른다.

### 데이터별 정본과 형식

| 데이터 | 형식·저장 위치 | 정본과 수명 |
|---|---|---|
| 사용자 설정 | `config/profiles/<profile>.yaml` | 최초 setup·이후 연결·임베딩·정책·보존 설정의 편집 입력; 적용 뒤 인증 문자열을 참조로 치환 |
| 내부 편집 상태 | `setup/<profile>/draft.json` | 편집 기준 개정·규격 지문; [사용자 YAML](#생성과-파일-위치)의 검증·확인·적용에 사용 |
| 현재 profile·기본 맥락 | `profiles/`의 개정별 JSON 파일 | 설정 내용의 정본; SQLite는 활성 개정·파일 참조만 관리 |
| 업무 고정 구성 | SQLite의 구조화된 스냅샷 | 업무 시작 당시 대상·연결·정책·기간 보존 |
| 업무·계획·승인·위임·호출 제어 | SQLite의 구조화된 행·JSON 필드 | 상태·소유권·위임 범위·예산·결정·출처·멱등 비교 정보의 정본 |
| 요청·답변·계획·하위 에이전트 할당·결과·조회 본문 | `records/`의 JSON 파일 | 비밀 제거·마스킹한 허용 본문; SQLite에는 참조·권한·기한 |
| 보고·과거 표 | `records/`의 보고 JSON·과거 표 JSON | 호스트의 자유형 결과와 별도 상태·출처·파일 참조; 기존 자료의 읽기 호환 |
| 자동 기억 처리 | `records/`의 보고별 후보·처리 JSON과 SQLite 참조 | 검증한 후보의 대기·색인·재시도; 대기 저장 실패는 보고 보존과 재제출 안내, 업무 기한·현재 정책 승계 |
| 파일 산출물 | `artifacts/`의 호스트 생성 파일 복사본 | 바이트·미디어 타입·출처·해시·기한 등록; 실제 작성·내용 검증은 호스트 담당 |
| 호스트 파일 작업 | `workspaces/`의 업무별 전용 디렉터리 | 생성 파일의 등록 입력; 등록한 동일 바이트의 일반 파일은 다음 정리에서 제거하고 나머지는 업무 기한·profile 삭제로 정리 |
| 선별한 기억 | SQLite의 본문 TEXT·구조화된 출처·개정·상태·기한 | 기억 정본; 최소 추적 이력과 분리해 기한 적용 |
| 키워드·벡터 색인 | SQLite의 FTS5·기억별 벡터 테이블 | 기억에서 재생성하는 파생 자료; 정본의 허용·기한·삭제 상태 승계 |
| 인증 비밀 | OS·제공자의 안전한 저장소 | profile·SQLite는 인증 참조만 보관 |
| 로컬 임베딩 모델·임시 자료 | 로컬 선택의 `models/`, 준비 파일의 `staging/` | 선택 제공자에 필요한 준비 자산; 파일 공개는 참조 발행 성공 후 |
| 연결 등록·작업 영역 | `resources/`의 계약 JSON과 `resources/processes/` | 현재 연결 진단과 하위 MCP의 분리된 작업 위치; profile 소유 참조로 추적 |
| 공유 실행 도구·Python runtime | `tools/`의 recipe별 환경, `runtime/`의 관리 Python·캐시 | 여러 profile이 재사용하는 준비 자산; profile 삭제 시 유지 |

표의 디렉터리는 사용자 저장 영역의 논리적 구분이며 실제 파일은 runtime의 등록 참조로 접근한다.
자료·메타데이터에는 profile·실제 대상·업무·기록·개정의 연결을 둔다.
파일 권한은 본문 동일 여부와 별도로 profile·실제 대상·현재 주체 조건에 결합한다.

SQLite 하나에 여러 profile을 두고 등록 ID·개정·실제 대상·현재 제공 조건으로 설정·상태·기억을 조회한다.
스냅샷의 비만료 최소 이력은 실행 바인딩·정책·개정·기한으로 구성한다.
기본 맥락·자유 설명·자료 본문은 해당 보존기간의 정본에서 관리한다.
업무 스냅샷은 구조화된 실행·정책 정보를 저장하고 기본 맥락은 현재 profile에서 조회한다.
시작·정리 시 이전 버전이 복사한 설명도 제거하며 업무 상태·개정·대상·정책·기한은 유지한다.

불변 계획의 설명·자료에도 선택한 보존 정책을 적용하고 비만료 식별·검증 정보와 분리한다.
불변 본문은 보존 중 동일 개정을 유지하고 기한 뒤 삭제 조건을 적용한다.
본문 만료 뒤에는 업무 식별·결정·참조·비밀을 제거한 입력 비교 지문을 유지한다.

### 설정과 업무 기록의 저장

profile 변경은 새 JSON 개정을 검증·준비하고 SQLite 트랜잭션에서 활성 개정·등록 참조를 바꿔 공개한다.
JSON 내용이 설정의 정본이고 SQLite의 활성 개정은 사용할 불변 파일을 선택한다.
두 호스트의 설정 변경·업무 생성·현재 정책 검사는 같은 profile 개정의 일관된 경계에서 처리한다.
변경 직후 이전 JSON은 그대로 남을 수 있으며 다음 저장소 시작·정리에서 활성 참조가 없는 파일을 제거한다.
현재 관리 기능은 활성 구성 조회·변경을 제공하며 과거 실행 대상·정책은 업무 스냅샷으로 추적한다.

새 업무는 활성 JSON과 SQLite의 개정·무결성을 대조하고 실행에 필요한 스냅샷을 저장한다.
설정은 일반 파일·등록 크기·SHA-256을 확인하며 파일 종류 변경·직접 수정·손상은 `STORE_UNAVAILABLE`로 관리 경로의 복구를 요구한다.
활성 파일·SQLite의 무결성이 맞지 않으면 저장소 오류로 복구한다.
정상적인 profile 설정 변경은 현재 설정을 읽고 사용 중인 연결·대상에 영향을 주는지 대조한다.

업무 상태·계획 연결·승인 결정·호출 의도·예약·멱등 기록은 SQLite 트랜잭션으로 보존한다.
실행 의도 보존을 확인한 뒤 원격 요청을 보내며 저장 실패·잠금 충돌은 로컬 저장 복구로 처리한다.
DB 쓰기 잠금은 상태 검사·예약·확정의 짧은 트랜잭션에서 확보하고 네트워크 대기·모델 추론 전에 해제한다.
동일 업무 소유권·개정·예산 검사는 [실행 제어](../tasks/workflow.md#실행-검사와-기록)를 따른다.
하위 에이전트 배정·복구·요약의 수명은 [하위 에이전트 계약](../mcp/tasks.md#daeri_subagent)에서 정의한다.

SQLite의 동시 접근은 같은 PC의 로컬 저장소를 대상으로 한다.
[WAL의 읽기·쓰기 동시성](https://sqlite.org/wal.html)을 검증하되 쓰기는 트랜잭션으로 직렬화하고 잠금 대기를 제한한다.
저장소 개설은 SQLite 본체·WAL·공유 메모리·journal의 기존 파일 종류를 확인하고 일반 파일 조건을 벗어나면 `STORE_UNAVAILABLE`로 반환한다.

runtime은 저장소를 열 때 관리 루트 디렉터리와 SQLite 본체의 식별을 고정한다.
매 DAERI 도구 요청과 저장 트랜잭션의 진입·커밋 직전에 경로가 같은 루트·본체를 가리키는지 확인한다.
이동·삭제·재생성·DB 교체로 동일성 확인에 실패하면 진행 중인 트랜잭션을 롤백하고 DB 연결을 닫는다.

새 DAERI 도구 요청·저장 진입에서 발견한 오류는 `STORE_UNAVAILABLE`·`next_action: stop`과 저장소 변경·연결 다시 시작 안내로 반환한다.
이미 전송한 호출의 결과 보존 실패·미확인 결과는 [업무 실행의 복구 절차](../tasks/workflow.md#중단재개와-외부-결과-확인)를 따른다.

오류를 낸 runtime은 닫힌 연결 상태를 유지한다.
사용자는 설정한 저장 위치의 SQLite 본체·WAL 등 저장소 파일의 일관성을 확인한 뒤 새 연결을 시작한다.
새 연결은 현재 설정한 저장 위치의 저장소를 연다.

호스트 세션·관리 명령별 연결 수명은 [로컬 실행](../hosts/plugins.md#로컬-실행과-연결-수명)을 따른다.
OS 파일 조작과 runtime 검사는 각각 진행되므로 판정 기준은 각 검사 시점의 경로·식별 상태다.

### 본문과 파일의 공개

1. 현재 입력·권한·제공 필드·마스킹·보존 조건과 중복 요청을 검사한다.
2. 사용자 전용 `staging/`에 허용 본문 또는 호스트 파일의 복사본을 쓰고 동기화한다.
3. 새 관리 위치로 옮기고 크기·SHA-256을 등록 정보로 준비한다.
4. 현재 업무 상태·권한을 다시 검사한 뒤 SQLite에서 준비 파일의 참조를 공개한다.
   보고·산출물·종료 상태·멱등 결과의 확정은 기존 결과 도구의 트랜잭션 단위를 따른다.
5. 공개 상태가 확인된 참조만 모델·사용자에게 반환한다.

구조화 본문은 비밀 제거·마스킹 후 저장하고 호스트 파일은 작성된 바이트를 복사해 출처·제공 권한·해시로 등록한다.
파일 내용 검증·작업 영역·재첨부 조건은 [호스트 결과와 파일](../mcp/tasks.md#호스트-결과와-파일)을 따른다.
파일 발행 뒤 SQLite 참조 공개가 성공하면 해당 업무 개정과 함께 경로·내용을 제공한다.

중단 뒤에는 준비 기록을 대조해 미공개 파일을 정리하거나 같은 요청의 공개 여부를 확인한다.
저장소 시작·명시적 정리는 SQLite의 활성 참조와 관리 파일을 대조해 등록 참조가 없는 파일을 제거한다.
이미 공개한 본문·산출물은 일반 파일·등록 크기·SHA-256을 확인하고 파일 유실·종류 변경·손상은 `RECORD_UNAVAILABLE`로 반환한다.
본문·파일 유실은 기록 가용성 오류로 처리하고 기존 외부 호출과 결과 기록은 유지한다.

### 조회와 기억 검색

정확한 업무 복구는 SQLite의 상태·현재 개정·계획·호출 참조로 수행한다.
본문 조회는 등록 참조를 해소해 현재 권한·마스킹·기한·파일 무결성을 검사한 뒤 필요한 범위만 읽는다.

기억 검색은 현재 허용한 profile·실제 대상·유효 기억 개정을 대상으로 한다.
SQLite 정본에서 [FTS5](https://sqlite.org/fts5.html)·벡터 색인을 만들고 후보를 반환하기 직전에 현재 정책·개정·상태·기한을 재검사한다.
기억 변경은 정본 개정·이전 개정 차단·색인 갱신 대기를 함께 보존하고 색인 실패는 유효 정본에서 복구한다.
검색·미준비·복구의 계약은 [기억 검색](../tasks/memory.md#혼합-검색과-색인), 구현체·모델은 [의존성 정본](../../development/dependencies.md#의존성의-정본)을 따른다.

### 삭제와 만료

자료의 기한은 [업무 보존](../tasks/workflow.md#이력과-완료-근거)과 [기억 보존](../tasks/memory.md#보존과-장기-운영지식)이 소유한다.
자료의 기한은 저장 위치·파일 형식 변경 뒤에도 그대로 승계한다.

| 삭제·만료 대상 | 사용 차단과 정리 |
|---|---|
| 현재 profile | 사용 차단 뒤 귀속된 업무·기억·파일·설정·인증 참조를 정리하고 profile을 마지막에 삭제 |
| 기한 있는 업무 본문·산출물 | 기한 검사로 즉시 제공 차단, 다음 실행 때 파일·DB 본문 사본·캐시 정리 |
| 기억의 만료·정정·무효화 | 정본의 상태·현재 개정으로 즉시 차단, FTS5·벡터·캐시의 해당 항목 정리 |
| 사용자 삭제·보존 철회 자료 | 원출처와 영향받는 파생물의 사용 차단; 연결된 기억·파일·색인까지 정리 |
| 인증 비밀 | 선택한 인증 참조의 해소·사용 중단 후 OS·제공자 관리 경로에서 처리; 공유 연결 영향 확인 |
| 모델·미공개 임시 파일 | 참조·사용 중 여부 확인 후 관리 경로에서 정리; 설정·기억 정본은 유지 |

runtime은 시작할 때 일반 자료의 만료·삭제 대기를 정리하고 완료 여부를 기록한다.
파일이나 색인 삭제가 실패해도 사용 차단 상태를 유지하고 이후 실행에서 남은 정리만 재시도한다.
profile 전체 삭제 실패는 아래 관리 명령의 명시적 재시도로 이어간다.
업무 파일 작업 영역은 profile의 소유 디렉터리로 추적하고 같은 삭제 범위에 포함한다.
조회·캐시·재전달은 실제 파일이 아직 남아 있어도 차단을 적용한다.

시작·명시적 정리의 기한 처리는 본문·파생 자료를 정리하고 최소 추적·미확인 외부 효과·중복 방지 정보는 유지한다.
삭제 상태의 필드는 ID·기한·차단 이유·정리 대상이다.
별도 허용한 장기 운영지식은 원문 파일 정리 뒤에도 자신의 기한과 삭제 조건을 따른다.

profile 삭제의 귀속 자료·인증·공유·외부 사본 범위는 아래 계약을 따른다.

기본 맥락·자유 설명의 변경·삭제 조건은 이전 profile JSON 개정에도 적용한다.
과거 대상·정책·개정의 추적은 업무 스냅샷으로 유지하고 이전 JSON 본문은 같은 변경·삭제 조건으로 정리한다.

### profile 삭제

사용자는 profile Skill에서 `profile delete PROFILE`을 요청한다.
호스트는 실제 대상과 삭제 범위를 확인하고 관리 CLI 한 경로를 호출한다.
연관 자료의 탐색·사용 차단·삭제 순서·실패 복구는 runtime의 profile 삭제 경로가 담당한다.

| 단계 | 입력·처리·결과 |
|---|---|
| 미리보기 | `profile delete NAME`; `profile_id`·`name`·`revision`·`counts`·`state`·`deletion_token` 반환 |
| 사용자 확인 | 호스트가 대상·관련 자료와 보존되는 공유·외부 자료를 요약하고 삭제 여부 확인 |
| 실행 | `profile delete NAME --confirm TOKEN`; 미리보기의 대상·개정과 대조한 뒤 사용 차단·연관 자료 정리 시작 |
| 완료 | 귀속 자료 정리 후 profile 행을 최종 삭제하고 `profile_id`·`deleted: true`·`counts` 반환 |
| 중단·실패 | 사용 차단·전체 정리 목록 유지; 같은 대상과 확인값으로 재시도하고 이미 없는 항목은 완료로 취급 |

`state`는 삭제 전 `ready`, 정리 중 `deleting`이다.
`counts`는 `tasks`·`records`·`artifacts`·`memory_versions`·`credentials`·`shared_credentials`를 반환한다.
각각 업무·조회 및 보고 기록·생성 파일·모든 기억 개정·삭제할 인증 참조·보존할 공유 인증 참조의 수다.
정리 중 미리보기와 완료 결과의 건수도 최초 확정한 전체 범위다.
인증 참조 수는 설정과 소유 기록에 등록된 참조를 기준으로 계산한다.

미리보기는 로컬 설정·소유 참조의 메타데이터로 삭제 대상·건수·확인값을 반환한다.
관리 CLI 시작에 적용되는 일반 만료 정리 등 기존 저장소 동작은 그대로 따른다.
확인값은 특정 profile 식별자·개정에 결합하고 호스트는 별도로 실제 사용자 삭제 응답을 받는다.
미리보기 뒤 구성 충돌은 새 범위의 미리보기·사용자 확인으로 처리한다.
확인값 검사는 이름과 함께 profile 식별자·개정의 일치를 요구한다.

삭제 시작 시 해당 profile의 새 업무·설정 변경·조회·검색·호출을 차단한다.
해당 profile의 프로그램 준비·로그인·연결 진단이나 원격 호출이 진행 중이면 `PROFILE_BUSY`로 시작을 거부한다.
진행 중인 작업을 완료하거나 중단한 뒤 다시 요청한다.
소유 프로세스 확인은 OS의 생존 상태 조회로 수행한다.
소유 프로세스 상태가 불명확하면 `PROFILE_BUSY`로 반환하고 상태 확인 후 삭제를 재요청한다.

| 귀속 자료 | 정리 범위 |
|---|---|
| 업무·제어 기록 | 모든 업무 상태·계획·승인·호출·스냅샷·기억 검색 기록·귀속 멱등 결과 |
| 본문·산출물 | 조회 자료·보고·표·생성 파일의 DB 참조와 관리 파일 |
| 장기기억·색인 | 해당 profile의 모든 기억 개정·출처·FTS5·벡터·등록 캐시 |
| 설정·임시 작업 | 사용자 설정 YAML·이전 setup YAML·내부 편집 상태·현재와 과거 profile JSON·연결 등록 자료·프로세스 작업 영역 |
| 로컬 인증 비밀 | 리소스·임베딩의 현재 및 추적한 과거 `credential:` 중 삭제 대상 profile이 단독 소유·참조하는 DAERI 인증 저장 항목 |

다른 profile과 공유하는 인증 비밀은 남기고 삭제 대상의 참조·소유 기록만 제거한다.
공유 설치 자산인 실행 도구·모델·runtime·전역 검증 키도 유지한다.
`env:` 환경 변수·제공자의 표준 로그인 캐시·원격 리소스와 권한·로컬 Source 원본 디렉터리·사용자 내보내기 사본은 해당 사용자·외부 관리 경로에 남는다.
이 범위는 profile 소유 자료의 누락과 구분하며 미리보기·완료 안내에서 설명한다.
외부 인증의 소유 기록이 유실된 이전 버전 자료는 해당 제공자의 관리 경로에서 확인·정리한다.
이전 버전의 소유 profile 미기록 전역 중복 방지 지문은 다른 profile 보호를 위해 유지한다.
이 지문에는 업무 본문이 없으며 현재 소유자를 추적하는 요청 기록은 삭제 대상에 포함한다.

파일·색인·인증 저장소 정리가 실패하면 `PROFILE_DELETE_PENDING`으로 반환하고 profile의 사용 차단을 유지한다.
다시 미리보기하면 `last_error`에 실패 단계인 `stage`와 비밀 없는 오류 `code`를 반환한다.
호스트는 실패 단계·오류 코드로 복구와 재시도를 안내한다.
profile 행과 전체 정리 목록은 유지하며 같은 확인값으로 재시도한다.
이미 없는 파일·인증 항목은 완료로 취급하고 DB 정리도 같은 범위에서 다시 적용한다.
소유 참조는 `profile_references`, 삭제 진행과 정리 목록은 `profile_deletions`에서 관리한다.
기억 정리는 해당 profile의 저장 ID·색인 참조로 수행하고 다른 profile의 정본·색인은 유지한다.
삭제 중단 뒤에도 사용 차단과 완료한 정리를 유지하며 남은 정리부터 재시도한다.
모든 종속 자료를 정리한 뒤 profile을 최종 삭제하고 삭제된 식별자의 재사용 차단용 최소 표식만 남긴다.
완료 표식의 보존 필드는 삭제된 profile 식별자와 `deleted` 상태다.
저장장치 잔류 데이터와 외부 백업 사본은 별도 저장장치·백업 관리 절차에서 처리한다.

### 이관·백업·복원

저장 스키마 이관은 같은 사용자 저장소의 runtime을 조정해 독점 처리한다.
신규 승인·리소스 호출은 이관·무결성 검사 성공 후 허용한다.
실패는 검증한 원본을 유지한 이관 오류로 반환한다.

현재 구현은 기존 기억 테이블의 보존기한 필드를 무기한 표현이 가능한 형식으로 전환한다.
필수 컬럼을 확인한 뒤 알려진 형식만 이관하며 구조가 불완전하면 `STORE_UNAVAILABLE`로 복구를 요청한다.
정본·벡터·외래키 연결을 하나의 트랜잭션에서 보존하고 실패하면 원래 테이블로 되돌린다.
이 전환은 기존 profile·기억의 유한 기한을 보존한다.
다른 저장 스키마의 범용 변환은 현재 지원 범위 밖이다.

이전 명칭의 하위 에이전트 기록·요청 메타데이터와 v1 백업은 현재 명칭으로 해석하며, 원 본문·해시·식별자·개정·출처와 백업 확인값은 유지한다.

`memory_versions.source_lineage`에는 개별 출처의 비밀 없는 식별 지문 목록과 차단 시각을 보존한다.
본문 제거 뒤에도 이 지문·차단 시각으로 재조합한 출처의 삭제·기한을 검사한다.
기존 본문이 있으면 출처 연결을 채우고, 이미 제거되어 연결을 복구할 수 없으면 이관 이후 확인한 새 자료를 요구한다.
복원·기한 적용의 기준은 [기억 보존](../tasks/memory.md#보존과-장기-운영지식)을 따른다.

설정 전용 `profile import/export`는 위 [공개 설정 이동](#구현한-profile-입력과-공개-설정) 계약을 유지한다.
전체 데이터 이동은 선택한 profile 하나를 버전 있는 논리 묶음으로 저장하는 `profile backup/restore`를 사용한다.
등록된 논리 행·출처 연결·허용 본문·파일을 일관된 스냅샷으로 확보하고 저장 경로는 목적지에서 새로 발행한다.
준비·진단·리소스 호출이 진행 중이면 `PROFILE_BUSY`로 완료 후 재시도를 요청한다.

| 관리 명령 | 입력·처리·결과 |
|---|---|
| `profile backup PROFILE FILE` | 현재 설정·소유 자료·제공 범위·기한·파일 무결성을 확인하고 새 암호화 파일 생성 |
| `profile restore FILE` | 암호화·형식·본문·출처 연결을 검사하고 대상·건수·확인값을 미리보기로 반환 |
| `profile restore FILE --confirm TOKEN` | 미리보기 확인값·목적지 충돌을 검사하고 검증한 자료를 새 공간에 공개 |
| `--password-file PATH` | 두 명령의 비밀번호 파일 입력; 생략하면 숨김 터미널 입력 사용 |

암호 입력은 사용자 터미널의 숨김 입력 또는 비공개 비밀번호 파일로 받는다.
입력 경로가 필요하면 `input_required`·종료 코드 0으로 안내하고 입력 대기 상태로 종료한다.
비밀번호는 UTF-8 8~1,024바이트의 한 줄이며 파일 끝의 LF 또는 CRLF 한 개를 허용한다.
파일은 최대 1,026바이트·일반 파일·Unix의 사용자 전용 권한을 검사한다.
확인값은 정규화한 manifest JSON의 SHA-256이며 묶음이 바뀌면 새 미리보기·사용자 확인을 요구한다.
출력은 사용하지 않은 새 파일에 발행하고, 기존 파일·잘못된 비밀번호·손상·미지원 형식은 `INVALID_INPUT`으로 반환한다.

암호화 형식 1은 `DAERI-PROFILE\0\1` 식별자·16바이트 salt·12바이트 nonce·암호문·16바이트 인증 태그로 구성한다.
Scrypt(`n=32768, r=8, p=1`)로 만든 256비트 키와 AES-256-GCM을 사용하고 헤더도 인증한다.
인증을 완료한 뒤 ZIP과 논리 참조를 검사하며 임시 평문은 사용자 전용 디렉터리에서 처리한다.
암호화 파일·전체 비압축 자료는 각각 최대 1GiB, manifest·개별 JSON 본문은 32MiB, ZIP 항목·논리 행은 각각 100,000개다.
ZIP 이름은 `manifest.json`과 `blobs/<SHA256>`이며 경로·링크·중복·해시·참조 소유권·출처 순환을 검사한다.
논리 JSON은 값 타입·키와 문자열의 UTF-8 인코딩·숫자의 유한성·컨테이너 순환을 검사한다.
SQLite 정수로 저장할 값은 부호 있는 64비트 범위로 검사한다.
ZIP64 확장 종료 영역은 거부하고 중앙 목록은 항목당 평균 256바이트 이내로 제한한다.

manifest의 `format: daeri-profile`·`version: 1`·`created_at`은 형식과 스냅샷 시점을 표시한다.
`profile`은 현재 공개 설정 전체에 `profile_id`·`revision`을 더한 객체이며 나머지 자료는 다음 행 배열이다.

| 배열 | 행 필드 |
|---|---|
| `tasks` | `task_id`, `profile_id`, `revision`, `metadata`(업무 제어 이력), `expires_at` |
| `records` | `record_ref`, `task_id`, `kind`, `size`, `sha256`, `expires_at`, `blocked`, `cleaned`, `blob` |
| `artifacts` | `artifact_ref`, `task_id`, `extension`, `size`, `sha256`, `blob` |
| `requests` | `scope`, `request_key`, `fingerprint` |
| `memory_heads` | `memory_id`, `profile_id`, `current_ref`, `invalidated` |
| `memory_versions` | `memory_ref`, `memory_id`, `profile_id`, `version`, `body`, `content_hash`, `source_hash`, `created_at`, `expires_at`, `source_lineage` |

기한의 null은 무기한, `blob`·기억 `body`의 null은 본문 제외, 상태 플래그는 정수 0·1이다.
blob은 SHA-256 이름·크기와 일치해야 하며 참조는 선택 profile의 업무·기억 그래프 안에서 연결한다.
`source_lineage`는 `keys`(출처 지문 배열 또는 연결 불명인 null)와 `blocked_at`(차단 시각 또는 null)을 담는다.
필드 추가·변경은 형식 버전으로 구분하고 입력은 정의한 필드·타입·출처 연결과 대조한다.
입력 스키마·연결 검사는 [논리 검증기](../../../src/daeri/config/profile_bundle_validation.py), 암호화·파일 검사는 [묶음 형식](../../../src/daeri/config/portable_archive.py)이 구현한다.

| 묶음에 포함하는 자료 | 제공·보존 조건 |
|---|---|
| 공개 설정·업무 스냅샷·계획·과거 승인·호출·중복 방지 정보 | 선택 profile의 연결·개정·상태·기한과 귀속 중복 방지 지문 보존 |
| 요청·조회·보고·하위 에이전트 자료·등록 파일 | 현재 내보내기·마스킹·출처·무결성 검사를 통과한 본문과 바이트만 포함 |
| 모든 기억 개정과 출처 이력 | 현재 허용 본문과 개정·기한·무효화·출처 지문·차단 시각 보존 |
| 만료·차단·본문 정리 기록 | 식별·연결·기한·차단 이력을 남기고 사용할 수 없는 본문은 제외 |

v1은 현재 보존 중인 업무 본문 전체의 내보내기가 허용될 때 묶음을 생성한다.
일부 관찰 필드나 인용한 기억의 내보내기가 허용되지 않으면 `ACCESS_DENIED`로 전체 생성을 거부한다.
자유서술·파일이 사용한 관찰값을 그대로 보존할 수 있는 조건을 검사하며 선택적 축약은 후속 범위다.
만료·차단·무효화·내부 기억 처리 대기 본문은 메타데이터만 유지한다.
기억의 본문은 현재 허용 범위로 선별하고 기억 검색·갱신·후처리 기록은 메타데이터만 유지한다.
등록된 파일의 유실·변조는 무결성 오류로 생성 단계를 중단한다.

인증값·세션·하위 에이전트 토큰·프로세스 소유권·연결 진단·편집 중 YAML·로컬 Source 원본 디렉터리·미등록 작업 파일·설치 자산·검색 색인은 이동 대상에서 제외한다.
인증이 필요한 리소스·임베딩은 복원 대상의 새 인증 참조로 다시 등록하고 프로그램 준비·대상 연결 진단을 수행한다.
로컬 Source의 저장 설정·백업 검사·복원은 원본 디렉터리의 존재 여부와 분리해 처리한다.
다른 PC에서 경로가 달라지면 setup에서 해당 연결을 현재 디렉터리로 갱신하고 준비·진단한 뒤 새 업무에 사용한다.
키워드 색인은 유효 기억 정본에서 복구하며 벡터는 사용자가 명시적으로 재색인할 때 선택한 제공자로 다시 만든다.

v1의 복원 목적지는 profile과 내부 ID를 새로 등록할 수 있는 공간이다.
다른 profile이 있는 공유 저장소도 이름·내부 ID·귀속 요청 키의 충돌이 없으면 사용할 수 있다.
이력의 연결과 출처 지문을 보존하기 위해 원 식별자를 유지하며 현재 저장소의 같은 식별자·삭제 표식과 충돌하면 복원을 거부한다.
기존 profile을 덮어쓰는 복구·증분 병합·식별자 재배정은 지원 범위 밖이다.
복원 실패에는 기존 자료를 유지하고 준비한 미공개 파일을 정리하며 검증을 통과한 전체 참조만 공개한다.
물리 정리 실패로 남은 미공개 파일은 다음 저장소 정리에서 재처리한다.

복원은 원래 절대 기한과 현재 시각·정책·삭제·차단 상태를 적용한다.
DB의 시간 비교에 쓰는 만료·기억 생성 시각은 같은 순간의 UTC 표현으로 정규화한다.
출처 종속 기억은 원 기억·저장한 출처·현재 출처 기록의 기한 중 가장 빠른 시각으로 단축한다.
과거 승인 결정은 `historical_state`·`historical_ever_approved`와 원 응답에 보존하고 실행용 `ever_approved`는 false로 초기화한다.
소유권을 비우고 활성 승인·대기 응답·하위 에이전트 권한을 무효화하며 미종료 업무는 paused로 복원한다.
귀속 요청 키·지문은 이력 표식으로 복원하고 재전달에는 `CONTEXT_CHANGED`와 새 요청 ID 확인을 반환한다.
새 실행은 현재 소유권·연결 진단과 새 계획 승인을 거친다.
호출 소비·미확인 결과·중복 방지 지문은 유지하고 결과 확인·재시도는 [중단·복구 계약](../tasks/workflow.md#중단재개와-외부-결과-확인)을 따른다.

묶음이 보장하는 자료 상태는 스냅샷 시점까지다.
그 뒤 원본의 삭제·권한 철회·외부 호출 결과를 반영하려면 최신 묶음을 다시 확보해야 한다.
현재 확인할 수 없는 권한·출처는 사용을 차단하고 새 관찰·출처 확인으로 재검증한다.
사용자가 보관·전달하는 암호화 사본과 별도 복사본의 보관·폐기는 사용자 관리 범위다.

## 인증 저장과 전달

profile은 비밀값 대신 로컬 인증 참조를 보관한다.
runtime은 등록된 연결을 위해서만 그 참조를 해소하고 필요한 인증 정보를 전달한다.
참조 해소의 입력은 등록한 연결이 명시한 인증 참조다.

비밀값은 OS 또는 제공자의 안전한 저장소를 사용한다.
잠김·만료·미지원이면 해당 인증 저장소의 복구 조치를 안내한다.
macOS는 키체인, Windows는 자격 증명 보관 기능의 native backend를 선택한다.
지원 OS의 native backend와 현재 저장소의 해소 성공을 비밀 저장·사용 조건으로 적용한다.

비밀은 제공자 로그인 또는 안전한 로컬 입력 경로에서 처리한다.
모델·기록·진단·산출물에는 비밀을 제거한 인증 참조·처리 상태만 제공한다.
원격 인증 정보는 등록 대상과 신뢰 조건을 검사한 해당 연결에 전달한다.

기본 setup은 [YAML 인증 필드](#접속-정보와-인증값)로 입력·수정하고 확인한 적용에서 OS 인증 저장소에 등록한다.
호스트는 현재 연결의 `auth_env`·`auth_headers`와 API의 `credential_ref`를 기준으로 `auth status REFERENCE`를 확인한다.
누락·실패한 인증은 같은 파일의 해당 항목을 수정·적용한 뒤 실제 연결을 재진단한다.
제품별 실제 인증·대상 바인딩은 [접속 계약](../resources/adapters.md#실제-접속-대상과-인증-문맥)을 따른다.

`auth set/status/delete`는 개별 인증을 관리하는 별도 CLI 경로다.

`auth set`의 일반 입력은 실제 사용자 터미널의 숨김 입력이다.
호출 환경에 사용자 터미널이 없으면 `status: input_required`·`reference`·`stored: false`와 사용자 터미널 안내를 반환하고 종료 코드는 0이다.
이는 로컬 입력 대기 상태이며 인증 저장·DB 접속의 실패와 구분한다.
참조 형식 오류·숨김 입력 기능 오류·실제 인증 저장소 오류는 해당 오류와 종료 코드 1로 반환한다.
`--stdin`은 사용자가 선택한 비밀 관리자 등 로컬 프로그램 사이의 보안 표준 입력을 연결하는 별도 경로다.
입력은 내용이 있는 한 줄·최대 16,384자로 검증한다.
등록·상태·삭제 결과는 인증 참조와 처리 여부, 필요한 사용자 조치만 제공한다.

인증 `status`는 지정 참조의 현재 해소 가능 여부를 확인한다.
참조 해소 실패·저장소 잠김은 `available: false`다.
원격 권한·로그인 성공은 해당 제공자의 별도 결과로 확인한다.
`env:` 참조는 상태 확인·연결에서 현재 값을 읽으며 값의 등록·삭제는 호스트 환경의 관리 경로가 담당한다.

제공자가 사용자 로그인을 요구하면 해당 안내에 따라 사용자가 인증한다.
계획 승인을 대화에서 받는 것과 제공자 인증 절차는 구분한다.
업무 실행은 원격 권한과 DAERI 업무 계획의 유효 승인을 함께 요구한다.

### Infra 제공자의 최초 SSO 로그인

첫 Infra recipe는 자체 격리 환경의 제공자 SDK로 device authorization을 수행한다.
제공자 로그인 자식은 해당 recipe의 Python을 `-I`로 실행하고 [공통 환경 격리](../installation/environment.md#공통-실행-파일과-환경-격리)를 적용한다.
인증 보조 기능은 준비된 recipe의 SDK 환경에서 제공한다.
로그인의 시작 조건은 사용자가 명시한 관리 로그인 요청이다.

| 입력·조건 | 처리·결과 |
|---|---|
| profile·인스턴스 | 준비된 Infra recipe와 실제 대상의 제공자 profile·계정·지역 일치 확인 |
| 최초 연결의 시작 URL·SSO 지역·역할 | 선택한 제공자 profile의 초기 인증 설정 준비 |
| 기존 제공자 설정 | 해당 profile·SSO session을 읽어 같은 대상의 재로그인 준비 |
| 사용자 확인 | 제공자가 발급한 HTTPS 확인 URL·사용자 코드만 표시하고 브라우저 인증 대기 |
| 인증 완료 | 표준 제공자 인증 캐시에 토큰 보관, profile·계정·역할·만료 시각만 보고 |

같은 제공자 profile에 다른 계정·시작 URL·역할이 등록되어 있으면 구성 충돌로 처리한다.
기존 SSO session은 시작 URL·SSO 지역이 같은 경우에 재사용하고 충돌하면 별도 제공자 profile이나 명시적인 구성 변경으로 처리한다.
제공자 profile은 설정·로그인·대상 검사에서 같은 입력 계약을 사용한다.
첫 Infra 연결은 1~128자의 이름에 공백·`@`·인용부호를 허용하고 대괄호·제어문자는 거부한다.
설정 파일의 인용된 기존 이름은 같은 이름으로 해소하며 같은 이름으로 해석되는 중복 항목은 거부한다.
다른 실제 대상으로 변경하려면 별도 profile이나 명시적인 구성 변경 경로로 처리한다.
기존 파일의 다른 profile은 유지하고 저장 직전 파일 변경을 대조해 외부 수정과 충돌하면 재확인을 요구한다.

등록한 public client로 device authorization을 시작한 뒤 제공자가 정한 간격으로 확인한다.
로그인 SDK는 선택한 SSO 지역의 제공자 endpoint를 사용한다.
사용자 인증 대기는 최대 10분이며 대기·속도 제한 응답에 맞춰 간격을 늘릴 수 있다.
거절·만료·인증 오류·시간 초과는 해당 로그인 요청의 종료 결과로 반환하고 새 로그인은 명시적 요청으로 시작한다.

인증 브라우저는 제공자의 사용자 로그인을 담당하고 DAERI 업무 계획 승인은 호스트 대화에서 받는다.
브라우저를 자동으로 열 수 없거나 사용자가 비활성화하면 표시한 URL로 직접 인증할 수 있다.
사용자는 제공자의 인증 화면에서 비밀번호·인증 토큰을 처리한다.

제공자 설정은 사용자 홈의 `.aws/config`, 인증 토큰은 표준 `.aws/sso/cache` 형식으로 보관한다.
새 파일은 사용자 전용 권한으로 쓰고 임시 파일을 완료 후 교체하며 심볼릭 링크 저장 위치는 거부한다.
로그인 응답은 위 표의 공개 URL·사용자 코드·결과 필드로 구성하고 비밀 토큰은 제공자 캐시에 저장한다.
로그인 성공 뒤 연결 진단과 실행 시점의 대상·권한·업무 승인 검사를 거친다.

[제공자 SDK의 public client 등록](https://docs.aws.amazon.com/boto3/latest/reference/services/sso-oidc/client/register_client.html), [device authorization](https://docs.aws.amazon.com/boto3/latest/reference/services/sso-oidc/client/start_device_authorization.html), [토큰 확인](https://docs.aws.amazon.com/boto3/latest/reference/services/sso-oidc/client/create_token.html)을 사용한다.
가짜 응답의 대기·속도 제한·거절·만료와 네트워크를 차단한 실제 SDK의 요청·표준 캐시 읽기를 검증했다.
실제 회사 SSO 로그인·브라우저 UI·계정 권한은 사용자 환경의 검증 대상이다.

## 만료·교체·철회와 재개

인증 만료·잠김·철회·참조 해소 실패 시 새 호출을 보류한다.
재인증 이후 실제 사용 주체·대상·권한과 업무 승인 범위를 다시 확인한다.
재개 대상은 기존 업무에 바인딩한 계정·연결이다.

같은 실제 대상의 인증값·SSO 캐시 갱신은 기존 연결과 승인을 유지한다.
연결·계정·실제 대상 변경은 새 업무에서 진단·계획 승인으로 확인한다.
같은 연결의 도구 입출력·읽기 의미 변경은 재진단·수정 계획으로 이어간다.
중단된 읽기는 원 기록을 보존하고 현재 승인 범위에서 새 관찰로 이어간다.

연결 해제·로컬 로그인 종료·제공자 권한 철회는 서로 다른 작업이다.
사용자가 선택한 종료·철회 범위를 처리하고 다른 연결의 공유 인증은 해당 소유·참조 조건에 따라 보존한다.

공유 템플릿은 범주·역할·공개 입력·인증 참조를 담고 받는 사용자가 자신의 인증·연결을 준비한다.

설정·인증·저장·삭제·이관의 담당 구현과 로컬·실제 환경의 검증 범위는 [개발 안내](../../development/dependencies.md#구현과-대표-검증)를 따른다.
