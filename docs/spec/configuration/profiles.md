# 서비스 profile·인증·로컬 저장

상태: profile·로컬 인증·SQLite와 파일 저장 구현; 관리 CLI·격리 준비 구현, 실제 운영 연결·Windows 실행 미검증

profile에 리소스·운영 맥락·기억 정책을 묶고 연결 준비와 로컬 데이터 저장·조회·삭제를 정의한다.
기능의 탐색·등록·실행은 [리소스 계약](../resources/contract.md)을 따른다.
기억의 내용·검색·갱신·보존은 [profile별 장기기억](../tasks/memory.md)이 정본이다.

## profile의 의미

profile은 서비스·환경별 리소스와 운영 정보를 묶는 DAERI의 설정 단위다.
DB·Cache·Infra·Source·Document 등 필요한 범주와 여러 인스턴스를 함께 등록한다.
범주 예시는 [리소스 범주](../resources/initial-adapters.md), 실제 사용 예정 제품은 [사용 예정 환경](../product.md#사용-예정-환경)을 따른다.

| 구분 | 가상 예시 | 책임 |
|---|---|---|
| DAERI profile | `service-prod` | 서비스·환경과 리소스 묶음 |
| 리소스 인스턴스 | `primary-db`, `reference-db` | 실제 대상과 역할 |
| 연결 | `primary-db-connection` | 어댑터·실행 위치·인증 설정 |
| 제공자 인증 설정 | `operations-account` | 해당 제공자의 로그인·자격 증명 |

DAERI profile과 제공자 인증 설정은 별개다.
하나의 DAERI profile이 여러 제공자·계정의 인증 설정을 참조할 수 있다.

## 구성과 연결

profile에는 식별자·이름·기본 운영 맥락·리소스 연결·제공 정책·보존기간을 둔다.
서비스·환경 설명은 이름과 기본 맥락으로 표현하며 실제 실행 대상은 각 리소스의 `target`으로 구분한다.
같은 이름을 다시 저장하면 식별자는 유지하고 새 개정을 만든다.
식별자를 다른 실제 대상에 재사용하지 않으며 현재 관리 경로는 별도 이름 변경 기능을 제공하지 않는다.

각 리소스에는 범주·역할·어댑터·연결 위치·실제 대상·인증 참조·접근 정책을 등록한다.
같은 범주의 여러 리소스를 허용하며 필요한 범주를 추가할 수 있어야 한다.
연결이 어디서 실행되고 어떤 자료가 외부로 전달되는지 설정에서 확인할 수 있어야 한다.

기억 정책에는 저장 가능한 지식 범주·원본 필드·사용자 확인 자료·모델 제공 범위·보존 조건을 둔다.
이 정책은 업무 계획이 허용할 수 있는 상한이며 개별 업무의 리소스별 허용을 대신하지 않는다.
사용자가 설정한 안정적인 서비스 설명·용어·업무 규칙은 profile의 기본 맥락으로 관리한다.
업무에서 얻은 경험이 이 설정이나 접근 정책을 자동으로 바꾸지 않는다.

같은 연결을 여러 profile에서 쓰려면 각각 명시적으로 등록한다.
인증·대상·정책이 다른 연결은 표시명이 같아도 구분한다.
등록되지 않은 연결이나 주변 실행 환경의 다른 계정을 자동 선택하지 않는다.

업무 본문·조회 자료·보고·표·파일의 보존기간은 profile별로 변경할 수 있다.
새 profile은 기본 무기한이며 양의 정수로 유한 기간을 선택할 수 있다.
상세 보존 조건은 [이력과 완료 근거](../tasks/workflow.md#이력과-완료-근거)를 따른다.
변경한 기간은 새 업무에 적용하고 기존 기한이나 만료 자료를 자동 연장하지 않는다.
원본을 요약한 기억과 별도로 보존을 허용한 운영 지식의 기간은 [기억 보존 기준](../tasks/memory.md)을 따른다.

## 구현한 profile 입력과 공개 설정

사용자가 등록하는 JSON은 아래 구성 필드만 허용한다.
내보내기는 같은 형식을 반환하며 내부 `profile_id`·개정 번호·진단 결과·인증 비밀을 이동 파일에 복사하지 않는다.
다른 PC에서 가져오면 그 PC의 인증 저장·실행 파일 경로·연결 진단을 다시 준비한다.

| 최상위 입력 | 의미·기본값 |
|---|---|
| `name` | 필수 이름; 영문·숫자로 시작하는 영문·숫자·`_`·`-`, 최대 64자 |
| `core_context` | 사용자가 관리하는 기본 운영 맥락 문자열 목록; 기본 빈 목록 |
| `resources` | 같은 profile의 리소스 인스턴스 목록; 기본 빈 목록 |
| `retention_days` | 새 업무 본문·조회 자료·보고·표·파일의 보존일; 양의 정수 또는 null, 새 profile의 기본 null은 무기한 |
| `long_term_memory_days` | 별도 허용한 장기 지식의 보존일; 양의 정수 또는 null, 새 profile의 기본 null은 무기한 |
| `memory_policy` | 기억의 범주·대상·모델 제공·보존 상한; 기본 빈 객체로 허용 없음 |

설정 파일은 UTF-8 JSON이며 최대 2 MiB·중첩 32단계다.
중복 키·NaN·무한대·알 수 없는 필드·잘못된 인증 참조를 저장 전에 거부한다.
잘못된 입력으로 활성 profile 개정을 만들지 않으며 오류에 원문·비밀값을 되돌려 주지 않는다.

두 보존 설정의 무기한 기본값은 새 profile에 적용한다.
기존 profile에 명시한 30일·365일 등의 설정과 기존 업무·기록·기억의 유한 기한은 자동 변경하지 않는다.
`profile create`는 새 이름만 받으며 이미 있으면 `PROFILE_ALREADY_EXISTS`로 거부하고 기존 개정·연결·정책을 유지한다.
기존 설정 변경은 export한 전체 설정에서 요청한 필드나 리소스만 반영해 import한다.
무기한은 허용된 자료를 시간 경과만으로 삭제하지 않는 설정이며 자료 제공·보관·기억 저장 권한을 새로 부여하지 않는다.
원문 보관과 선별 지식 저장은 별도 정책·승인을 적용한다.
업무 자료의 기한 계산은 [업무 보존](../tasks/workflow.md#이력과-완료-근거), 지식의 사용 차단·새 검증은 [기억 보존](../tasks/memory.md#보존과-장기-운영지식)을 따른다.

### 리소스 인스턴스

| 입력 | 의미 |
|---|---|
| `instance_id` | profile 안에서 고유한 리소스 식별자 |
| `type`, `adapter` | 범주와 현재 설치한 어댑터 계약 |
| `target` | 실제 서버·저장 영역·계정·프로젝트 등의 대상 정보 |
| `identity_ref` | 해당 연결의 인증 문맥을 식별하는 비밀 없는 이름 |
| `connection` | 준비된 실행 파일·전달 방식·인증 참조 |
| `capabilities` | 사용할 하위 MCP 도구·기능 ID·강제할 조회 제약 |
| `policy` | 모델 제공·내보내기·보관·마스킹·기억의 최대 허용 범위 |

stdio 연결은 이미 준비할 실행 파일의 절대 경로와 문자열 인자·일반 환경 값·`auth_env` 참조를 등록한다.
shell을 리소스 실행 파일로 등록하거나 비밀을 인자·일반 환경 값에 넣지 않는다.
원격 연결은 `streamable_http`의 명시적인 HTTPS URL과 `auth_headers` 참조를 사용한다.
URL의 계정·비밀번호·query·fragment는 허용하지 않는다.

인증 참조는 `credential:이름` 또는 명시적으로 선택한 `env:환경변수명`이다.
전자는 OS 인증 저장소, 후자는 현재 호스트가 받은 해당 환경 변수에서만 해소한다.
기본 계정이나 다른 이름의 자격 증명으로 자동 대체하지 않는다.
`auth_env`와 `auth_headers`의 값도 실제 비밀 대신 이 참조만 받는다.

사용할 도구 이름·출력 스키마·대상 해석은 [리소스 계약](../resources/contract.md)이 소유한다.
관리 입력만으로 외부 도구 전체를 신뢰하거나 임의 명령·쓰기 기능을 열지 않는다.

### 자료 제공·보관 정책

`policy`가 빈 객체이면 자료 제공·내보내기·보관·기억을 허용하지 않는다.
필요한 항목만 명시적으로 설정하고 업무마다 계획의 리소스별 제공 범위를 다시 승인받는다.

| 정책 필드 | 의미 |
|---|---|
| `allowed_model_fields` | 호스트 모델에 제공할 수 있는 필드 선택자 목록 |
| `export_fields` | 사용자 산출물에 포함할 수 있는 필드 선택자 목록 |
| `retained_fields` | 선택한 보존기간 안에서 로컬 본문에 보관할 수 있는 필드 선택자 목록 |
| `masking` | 선택 필드를 제거하거나 값을 가리는 규칙 |
| `memory` | 기억 범주·출처 필드·사용자 확인 자료·보존·회상 허용 상한 |

선택자·마스킹 문법은 [공통 필드 선택](../mcp/common.md#필드-경로와-선택)을 따른다.
빈 `segments`는 전체 자료를 뜻하므로 모든 자료 제공을 의도한 경우에만 명시한다.
생략한 정책을 전체 허용으로 해석하지 않으며 마스킹한 비밀을 다른 제공·보존 경로로 되살리지 않는다.

### profile의 기억 허용 설정

`memory_policy`는 profile 전체의 기억 상한이며 리소스의 `policy.memory`와 함께 검사한다.
빈 객체는 기본 거부다.
생략한 범주·리소스는 선택하지 않고 생략한 허용 값은 `false`로 해석한다.

| 공개 입력 | 타입·허용값 | 적용 |
|---|---|---|
| `categories` | 중복 없는 문자열 목록 | `service_rule` 서비스 규칙, `resource_structure` 리소스 구조, `procedure` 수행 절차, `lesson` 주의·교훈 중 선택 |
| `instance_ids` | 같은 profile에 등록한 리소스 ID의 중복 없는 목록 | 이 리소스들이 기여한 기억만 저장·재사용 |
| `model_allowed` | JSON boolean | 기억을 호스트 모델에 제공할 수 있는 상한 |
| `retain_allowed` | JSON boolean | 기억 본문을 보관할 수 있는 상한 |
| `long_term_allowed` | JSON boolean | 원문 기한과 독립적인 장기 지식 보존을 허용할 수 있는 상한 |
| `exports_allowed` | JSON boolean | 기억 내용을 사용자 산출물에 포함할 수 있는 상한 |

가상 예시로 이미 등록한 `source-one`의 수행 절차를 기한 내에 기억하려면 아래를 `memory_policy`로 설정한다.
장기 보존과 산출물 포함은 허용하지 않는 예시다.

```json
{
  "categories": ["procedure"],
  "instance_ids": ["source-one"],
  "model_allowed": true,
  "retain_allowed": true,
  "long_term_allowed": false,
  "exports_allowed": false
}
```

이 설정만으로 리소스 자료를 수집하거나 기억하지 않는다.
해당 리소스의 `policy.memory`에도 같은 범주·허용한 출처 필드·`source_bound` 보존·`allow_model_recall: true`를 설정해야 한다.
출처 필드는 리소스의 모델 제공·본문 보관 허용에도 포함되어야 하며 업무 계획에서 실제 기억 범위를 다시 승인받는다.
`model_allowed`나 `retain_allowed`를 생략하거나 `false`로 바꾸면 해당 profile 기억의 제공·재사용을 차단한다.

실행기는 선택한 각 인스턴스의 현재 `target`을 정렬된 JSON의 SHA-256으로 계산해 내부 `target_bindings`에 저장한다.
사용자가 해시를 만들 필요가 없으며 대상 설명·이름으로 바인딩을 추정하지 않는다.
내보내기에서는 이 내부 필드를 제외하고 가져올 때 현재 설정으로 다시 계산한다.

내부 설정을 다시 저장하며 `target_bindings`를 전달한 경우에는 선택한 리소스 ID와 소문자 64자리 해시 형식만 받는다.
값은 현재 실제 대상으로 다시 계산하므로 대상을 바꾸어 저장해도 이전 대상의 기억을 새 대상에서 사용하지 못한다.
계산 자체가 리소스를 선택하거나 허용 값을 `true`로 바꾸지는 않는다.
리소스를 제거할 때는 `instance_ids`에서도 함께 제거하며 알 수 없는 필드·범주·미등록 ID·중복·잘못된 타입은 개정 저장 전에 거부한다.

기억 출처·장기 보존·정정·검색의 상세 조건은 [기억 명세](../tasks/memory.md)를 따른다.

## 관리 등록과 진단

사용자는 `/setup {profile명}`이라는 설정 진입 흐름으로 profile을 준비한다.
호스트별 실제 호출 표기는 [플러그인 지침](../hosts/plugins.md)에서 다룬다.
초기 선택·필드 입력·진행 확인은 [setup의 정형 질문](../hosts/plugins.md#setup의-정형-질문)으로 받고 비밀은 별도 보안 입력 경로로 전달한다.

1. profile 이름과 서비스·환경을 입력한다.
2. 필요한 리소스 범주와 범주별 어댑터·실제 대상을 선택한다.
3. 연결 위치와 인증 방식을 정한다.
4. 기본 맥락과 기억 정책을 설정한다.
5. 필요한 프로그램·버전·로컬 임베딩 준비 결과와 설치·로그인·진단 범위를 확인한다.
6. 확인한 범위에서 [환경 준비](../installation/environment.md)와 제공자 안내에 따른 사용자 로그인을 진행한다.
7. 실제 연결·사용 주체·접근 가능 대상·제공 기능을 확인하고 설정을 저장한다.
8. 준비 완료 항목과 사용자 조치가 필요한 항목·대상 profile의 이름과 식별자를 보고한다.

설정을 완료한 profile은 [선택 계약](#선택과-기본값)에 따라 해당 대화에서 새 업무의 기본 대상으로 사용한다.
연결되지 않은 항목은 별도로 알리며 등록 리소스 수나 접속 정보 준비만으로 실제 연결 성공을 선언하지 않는다.

선택한 연결에 필요한 프로그램만 준비하며 이미 호환되는 프로그램은 재사용한다.
설치·인증·진단에 대한 준비 동의와 실제 업무 계획의 승인은 별개다.
설정을 마쳤다는 이유로 업무 데이터 조회까지 허용하지 않는다.

진단은 연결과 권한을 확인하는 최소 범위로 수행한다.
업무 자료가 필요하면 제한된 탐색 계획을 먼저 승인받는다.
프로그램 누락·인증 필요·권한 부족·네트워크 실패·기능 미지원은 연결별로 구분한다.

자연어 업무 접수나 로컬 설정 확인이 숨은 설치·로그인·원격 탐색을 시작하지 않는다.
필요한 준비를 알리고 확인된 범위 안에서 진행한다.

### 준비 카탈로그와 개별 프로그램 설치

카탈로그는 [사용 예정 환경](../product.md#사용-예정-환경)의 첫 연결에 사용할 검증 대상 조합을 제공한다.
제품·패키지·버전·실행 이름은 카탈로그와 recipe 잠금 파일에서 관리하며 범용 기능 계약의 전제로 복제하지 않는다.
카탈로그 등록이 회사의 실제 연결 성공을 뜻하지 않는다.

설정안 출력은 선택한 recipe의 실행 경로·읽기 설정·인증 참조·기능을 제공한다.
`SET-ME`·빈 대상·빈 허용 목록은 사용자가 채워야 하는 자리이며 실행 가능한 설정으로 간주하지 않는다.
설정안의 자료 정책과 기억 정책은 기본 거부다.

개별 프로그램 준비는 profile·인스턴스·recipe를 명시적으로 선택한 경우만 진행한다.
선택한 인스턴스의 범주·어댑터·실행 파일 경로·인자와 고정된 안전 설정을 recipe와 대조한다.
다른 패키지명·버전·설치 명령을 모델이 전달해 실행할 수 없다.

프로그램은 사용자 저장소 `tools/` 아래 recipe·패키지 버전·잠금 지문별 격리 환경에 준비한다.
플러그인의 고정된 전용 uv를 절대 경로로 사용하고 [관리 Python과 환경 격리](../installation/environment.md#공통-실행-파일과-환경-격리) 기준을 적용한다.
새 후보를 잠긴 조합으로 설치하고 Python의 격리·패키지 버전·실행 파일을 확인한 뒤 공개한다.
같은 검증 설치는 재사용하며 기존 정상 조합이나 profile 개정·인증·업무 자료를 설치 과정에서 바꾸지 않는다.
실패·시간 초과·중복 준비는 해당 프로그램의 미완료 상태로 반환한다.

하위 MCP와 DAERI 실행기는 별도 환경을 사용하므로 서로 다른 SDK 주 버전도 섞지 않는다.
첫 DB recipe는 상위 패키지가 현재 배포되지 않는 SQL 파서 버전을 요구해 명시적인 호환 override를 둔다.
같은 recipe의 SDK 주 버전 제한도 삭제된 API를 사용하는 상위 패키지와 맞추기 위한 조건이다.
정확한 값과 잠금 조합은 `recipes/db-postgres/pyproject.toml`·`uv.lock`에서 관리하고 설치 시 임의로 완화하지 않는다.

프로그램 준비와 실제 연결 진단은 별개다.
진단은 현재 인증 참조·실제 대상 바인딩을 확인하고 하위 MCP의 초기화와 도구 목록을 읽어 선택한 기능의 계약을 등록한다.
실제 업무 도구 호출·원격 자료 조회는 진단에 포함하지 않는다.
인증 변경·대상 변경·계약 변경으로 기존 등록을 확인할 수 없으면 업무 실행 전에 재진단이 필요하다.

## 선택과 기본값

profile Skill은 기존 관리 CLI의 `profile list`·`profile show`로 저장 목록과 선택한 구성을 조회한다.
사용자가 지정한 등록 이름·식별자를 확인하고, 지정이 없거나 어느 대상인지 불명확하면 호스트의 [정형 질문](../hosts/plugins.md#setup의-정형-질문)으로 선택한다.
목록이 비어 있으면 setup을 안내하며 임의의 profile을 만들지 않는다.
구성 확인 오류·질문 취소·미응답이면 이전 선택을 유지한다.
선택 과정에서 구성 수정·로그인·연결 진단·설치를 시작하지 않는다.

확인한 `profile_id`·이름은 현재 대화에서 이후 새 업무에 사용할 기본 대상이다.
이 선택은 호스트의 대화 맥락이며 Python 실행기나 사용자 저장소에 전역 active·default profile을 새로 저장하지 않는다.
새 대화·문맥 압축·호스트 전환 후 선택 증거가 불확실하면 정형 질문으로 다시 선택한다.
최근 사용·목록 순서·이름의 유사성·접속 가능 여부만으로 대상을 추정하지 않는다.

work는 새 업무 접수 전에 `profile show`로 대상의 현재 이름·식별자와 등록을 확인한다.
사용자가 등록 profile 이름·식별자를 명확하게 지정하면 그 새 업무에 사용하고 대상을 안내한다.
대화의 기본 선택과 다르다는 이유만으로 다시 질문하지 않으며 이 지정은 해당 업무에만 적용한다.
명시한 대상이 없으면 현재 대화에서 확인한 기본 대상을 사용한다.
실제 profile을 특정할 수 없거나 대상 지시가 서로 모순되면 접수 전에 정형 질문으로 확인한다.
호스트는 확인한 `profile_id`를 업무 접수 입력에 전달한다.

list-profiles Skill은 저장한 profile을 이름순으로 읽어 이름·등록 리소스 범주를 최소한으로 요약한다.
대상을 구별할 때만 식별자를 덧붙이고 전체 설정·접속 정보·인증 참조는 출력하지 않는다.
자동 선택·전환·로그인·연결 진단·설치를 하지 않으며 리소스 수와 설정 유무를 연결 성공으로 표현하지 않는다.
조회 실패를 빈 목록으로 바꾸지 않는다.
profile 선택·목록 조회는 저장한 profile 구성·기존 업무·승인을 변경하지 않는다.
관리 CLI 시작 시 적용되는 일반 만료 정리 등 사용자 저장소 동작은 그대로 따른다.

profile의 설정·선택·전환은 업무 승인이나 리소스 접근 권한을 부여하지 않는다.
현재 권한과 각 업무의 계획·승인을 별도로 확인한다.

초기에는 업무당 하나의 DAERI profile을 적용한다.
한 profile에 둘 수 있는 리소스·제품·계정 수를 하나로 제한하는 조건은 아니다.
다른 profile의 리소스가 필요하면 사용할 묶음을 명시적으로 구성해 새 업무로 시작한다.

## 업무에 고정하는 스냅샷

업무를 시작할 때 선택한 profile 구성·리소스·대상·인증 문맥·정책·보존기간과 기억 정책을 기록한다.
비밀값은 업무 기록에 복사하지 않는다.
이 기록은 계획과 실행이 어느 환경을 대상으로 했는지 확인하는 기준이다.

승인한 업무에 다른 연결·계정·대상을 조용히 끼워 넣지 않는다.
같은 구성 안의 방법·허용 범위 변경은 [수정 계획](../tasks/approval.md)으로 처리한다.
승인 이후 profile의 대상·인증 주체 자체를 바꿔야 하면 새 업무로 시작한다.

대화의 기본 profile 선택이나 설정 변경은 기존 업무를 자동 전환하지 않는다.
work로 기존 업무를 재개하면 저장된 대상·스냅샷을 우선하고 대화 선택과 다른 점을 안내한다.
재개할 때에는 저장된 구성과 현재 권한·연결 상태를 함께 확인한다.
접근 철회·인증 실패는 새 호출을 막되 이미 수행한 호출과 미확인 실행 기록을 보존한다.
기억 조회에도 고정한 대상과 현재 접근·모델 제공 범위를 적용한다.
설정 변경으로 기존 기억의 수명이나 사용 범위를 자동 확대하지 않는다.

## 사용자 저장 위치

같은 OS 사용자의 Codex와 Claude Code는 같은 DAERI 설정·업무·기억 저장소를 사용한다.
설정·이력·산출물·기억 정본·검색 색인은 프로젝트 저장소와 플러그인 캐시 밖의 사용자 전용 영역에 보관한다.
아래 저장 역할을 채택하며 OS별 절대 경로·권한 설정은 구현 단계에서 검증한다.

설치 배포물·모델 파일과 사용자 원본 자료를 구분한다.
플러그인 업데이트·재설치·색인 재생성이 설정·업무 기록·유효한 기억을 초기화하지 않는다.
사용자·PC 사이의 기억 자동 동기화는 초기 범위에 포함하지 않는다.

## 로컬 저장 구조

설정 JSON 파일·사용자별 SQLite·관리 파일·인증 저장소의 책임을 나눈다.
SQLite는 DAERI 내부의 로컬 저장 엔진이며 profile이 연결할 DB 리소스의 제품을 제한하지 않는다.
별도 DB 서버나 벡터 DB 서버를 운영할 필요가 없는 구성을 기본으로 한다.

### 데이터별 정본과 형식

| 데이터 | 형식·저장 위치 | 정본과 수명 |
|---|---|---|
| 현재 profile·기본 맥락 | `profiles/`의 개정별 JSON 파일 | 설정 내용의 정본; SQLite는 활성 개정·파일 참조만 관리 |
| 업무 고정 구성 | SQLite의 구조화된 스냅샷 | 당시 대상·연결·정책·기간; 현재 설정을 덮어쓰지 않음 |
| 업무·계획·승인·호출 제어 | SQLite의 구조화된 행·JSON 필드 | 상태·소유권·예산·결정·출처·멱등 비교 정보의 정본 |
| 요청·답변·계획 설명·인수·조회 본문 | `records/`의 JSON·JSONL·텍스트 파일 | 비밀 제거·마스킹한 허용 본문; SQLite에는 참조·권한·기한 |
| 보고·검증한 표 | `records/`의 보고 JSON·표 JSON | 근거·계산·판단의 구조화된 본문; SQLite의 등록 참조로 연결 |
| 파일 산출물 | `artifacts/`의 등록 출력 형식 파일 | 허용 생성기가 만든 실제 파일; 사용자 출력 형식과 내부 저장 형식은 별개 |
| 선별한 기억 | SQLite의 본문 TEXT·구조화된 출처·개정·상태·기한 | 기억 정본; 최소 추적 이력과 분리해 기한 적용 |
| 키워드·벡터 색인 | SQLite의 FTS5·벡터 확장 영역 | 기억에서 재생성하는 파생 자료; 독립 보존 권한 없음 |
| 인증 비밀 | OS·제공자의 안전한 저장소 | profile·SQLite는 인증 참조만 보관 |
| 임베딩 모델·임시 자료 | `models/`의 모델 배포물, `staging/`의 준비 파일 | 모델은 재준비 가능; 미공개 준비 파일은 성공 전 조회 불가 |

표의 디렉터리는 사용자 저장 영역 안의 논리적 구분이며 호스트가 임의 경로를 지정하는 API가 아니다.
자료·메타데이터에는 profile·실제 대상·업무·기록·개정의 연결을 둔다.
같은 파일을 다른 profile과 자동 공유하거나 동일 본문이라는 이유로 접근 권한을 합치지 않는다.

SQLite 하나에 여러 profile을 두되 profile·실제 대상·현재 주체 조건을 모든 조회에 적용한다.
설정·상태·기억의 정본을 검색 색인이나 본문 파일 이름으로 추정하지 않는다.
스냅샷은 실행 바인딩·정책을 고정하고, 기본 맥락·자유 설명·자료 본문을 비만료 최소 이력으로 복제하지 않는다.

불변 계획의 설명·자료에도 선택한 보존 정책을 적용하고 비만료 식별·검증 정보와 분리한다.
불변은 보존 중 원문을 덮어쓰지 않는다는 뜻이며 기한 뒤 본문 정리를 막지 않는다.
본문이 만료되면 전체 원문을 복구하지 않고 업무 식별·결정·참조·비밀 없는 입력 비교 지문만 유지한다.

### 설정과 업무 기록의 저장

profile 변경은 새 JSON 개정을 검증·준비하고 SQLite 트랜잭션에서 활성 개정·등록 참조를 바꿔 공개한다.
JSON 내용이 설정의 정본이고 SQLite의 활성 개정은 사용할 불변 파일을 선택한다.
두 호스트의 설정 변경·업무 생성·현재 정책 검사는 같은 profile 개정의 일관된 경계에서 처리한다.

새 업무는 활성 JSON과 SQLite의 개정·무결성을 대조하고 실행에 필요한 스냅샷을 저장한다.
직접 수정되거나 손상된 파일은 이전 SQLite 내용으로 조용히 덮어쓰지 않는다.
개정 불일치는 관리 경로에서 해소하기 전 신규 승인·호출을 차단하며 기존 자료도 확인 가능한 권한 범위만 열람한다.

업무 상태·계획 연결·승인 결정·호출 의도·예약·멱등 기록은 SQLite 트랜잭션으로 보존한다.
실행 의도 보존을 확인한 뒤 원격 요청을 보내며 저장 실패·잠금 충돌을 원격 재시도로 해결하지 않는다.
네트워크 대기·모델 추론 동안 DB 쓰기 잠금을 계속 잡지 않는다.
동일 업무 소유권·개정·예산 검사는 [실행 제어](../tasks/workflow.md#실행-검사와-기록)를 따른다.

SQLite의 동시 접근은 같은 PC의 로컬 저장소를 대상으로 한다.
[WAL의 읽기·쓰기 동시성](https://sqlite.org/wal.html)을 검증하되 쓰기는 트랜잭션으로 직렬화하고 잠금 대기를 제한한다.
잠금을 우회하는 별도 파일 저장소나 동기화 폴더의 DB 사본을 실행 원본으로 사용하지 않는다.

### 본문과 파일의 공개

1. 현재 입력·권한·제공 필드·마스킹·보존 조건과 중복 요청을 검사한다.
2. SQLite에 준비 요청을 연결하고 사용자 전용 `staging/`에 비밀을 제외한 본문·파일을 쓴다.
3. 쓰기 완료·크기·형식·무결성을 확인하고 새 관리 위치에 준비한다.
4. 현재 업무 상태·권한을 다시 검사한 뒤 SQLite에서 준비 파일의 참조를 공개한다.
   보고·산출물·종료 상태·멱등 결과의 확정은 기존 결과 도구의 트랜잭션 단위를 따른다.
5. 공개 상태가 확인된 참조만 모델·사용자에게 반환한다.

파일 시스템과 SQLite 전체가 하나의 트랜잭션이라고 가정하지 않는다.
파일은 먼저 준비하고 SQLite의 공개 전에는 외부에 경로나 내용을 제공하지 않는다.
동일 이름의 파일을 덮어쓰지 않으며 ID와 요청의 연결을 확인한다.
준비·정리용 내부 기록만으로 공개 업무 개정을 바꾸지 않으며 도구별 상태 전이·개정 규칙을 유지한다.

중단 뒤에는 준비 기록을 대조해 미공개 파일을 정리하거나 같은 요청의 공개 여부를 확인한다.
이미 공개한 기록의 파일이 없거나 손상됐으면 `RECORD_UNAVAILABLE`로 반환한다.
본문·파일 유실을 이유로 외부 작업을 자동 반복하거나 성공한 호출을 새 호출로 만들지 않는다.

### 조회와 기억 검색

정확한 업무 복구는 SQLite의 상태·현재 개정·계획·호출 참조로 수행한다.
본문 조회는 등록 참조를 해소해 현재 권한·마스킹·기한·파일 무결성을 검사한 뒤 필요한 범위만 읽는다.
DB·파일의 직접 경로나 존재 여부를 접근 허가로 사용하지 않는다.

기억 검색은 현재 허용한 profile·실제 대상·기억 개정을 먼저 제한한다.
FTS5와 벡터 검색은 후보의 기억 ID·개정만 정본에 연결한다.
반환 직전에 활성 profile JSON의 현재 정책과 SQLite 정본의 개정·상태·기한을 다시 검사한다.
색인 결과의 오래된 본문·캐시를 정본 재검사 없이 제공하지 않는다.

SQLite와 [FTS5](https://sqlite.org/fts5.html)는 채택한다.
벡터도 SQLite 확장으로 저장·검색하며 [sqlite-vec](https://alexgarcia.xyz/sqlite-vec/)를 우선 검증 후보로 둔다.
확장 구현체·토크나이저·한국어 검색 품질·모델·지원 버전은 OS·실행 언어·배포 호환성을 확인한 뒤 확정한다.
선택한 확장이 준비되지 않았다고 외부 벡터 서버·클라우드 임베딩으로 자동 전환하지 않는다.

기억 변경은 정본 개정과 이전 개정 차단·색인 갱신 대기를 함께 보존한다.
색인 실패 시 정본은 유지하고 유효 개정에서 다시 만들며 제한 표시는 [기억 검색 계약](../tasks/memory.md#혼합-검색과-색인)을 따른다.
전체 대화·원문 파일·미승인 자료를 FTS5나 벡터 색인에 자동 수집하지 않는다.

### 삭제와 만료

자료의 기한은 [업무 보존](../tasks/workflow.md#이력과-완료-근거)과 [기억 보존](../tasks/memory.md#보존과-장기-운영지식)이 소유한다.
저장 위치나 파일 형식 변경으로 기한을 초기화하지 않는다.

| 삭제·만료 대상 | 사용 차단과 정리 |
|---|---|
| 현재 profile | 활성 등록을 해제해 새 업무·검색을 차단하고 불필요한 설정 JSON 정리; 기존 업무·공유 인증은 별도로 처리 |
| 기한 있는 업무 본문·산출물 | 기한 검사로 즉시 제공 차단, 다음 실행 때 파일·DB 본문 사본·캐시 정리 |
| 기억의 만료·정정·무효화 | 정본의 상태·현재 개정으로 즉시 차단, FTS5·벡터·캐시의 해당 항목 정리 |
| 사용자 삭제·보존 철회 자료 | 원출처와 영향받는 파생물의 사용 차단; 연결된 기억·파일·색인까지 정리 |
| 인증 비밀 | 선택한 인증 참조의 해소·사용 중단 후 OS·제공자 관리 경로에서 처리; 공유 연결 영향 확인 |
| 모델·미공개 임시 파일 | 참조·사용 중 여부 확인 후 관리 경로에서 정리; 설정·기억 정본은 유지 |

실행기는 시작할 때 만료·삭제 대기 자료를 정리하고 완료 여부를 기록한다.
파일이나 색인 삭제가 실패해도 사용 차단 상태를 유지하고 이후 실행에서 남은 정리만 재시도한다.
조회·캐시·재전달은 실제 파일이 아직 남아 있어도 차단을 적용한다.

최소 추적 정보와 미확인 외부 효과·중복 방지 정보는 본문과 함께 삭제하지 않는다.
삭제 상태에는 ID·기한·차단 이유·남은 정리 대상만 두고 원문·기억 문장을 복제하지 않는다.
원문 정기 만료에 따른 파일 정리는 별도 허용한 장기 운영지식의 기한을 취소하지 않는다.

삭제 완료는 DAERI의 관리 기록·파일 정리를 뜻하며 사용자가 따로 저장한 사본이나 저장장치 잔류 데이터의 완전 제거를 보장하지 않는다.
profile 삭제·비밀 삭제·원격 권한 철회는 서로 다른 관리 작업이며 하나가 다른 작업을 자동 수행하지 않는다.
기존 업무도 현재 profile 정책을 확인할 수 없으면 신규 호출을 차단하며 보존한 스냅샷만으로 계속 실행하지 않는다.

기본 맥락·자유 설명의 변경·삭제 조건은 이전 profile JSON 개정에도 적용한다.
필요한 과거 대상·정책·개정 연결은 업무 스냅샷으로 추적하고 오래된 JSON 전체를 무기한 보관하지 않는다.

### 이관·백업·복원

저장 스키마 이관은 같은 사용자 저장소의 실행기를 조정해 독점 처리한다.
이관·무결성 검사가 끝나기 전 신규 승인·리소스 호출을 시작하지 않는다.
실패하면 검증한 원본을 유지하고 빈 DB 생성이나 설정 초기화로 성공 처리하지 않는다.

현재 구현은 기존 기억 테이블의 보존기한 필드를 무기한 표현이 가능한 형식으로 전환한다.
정본·벡터·외래키 연결을 하나의 트랜잭션에서 보존하고 실패하면 원래 테이블로 되돌린다.
이 전환은 기존 profile이나 기억의 유한 기한을 바꾸지 않으며 범용 버전 이관·백업·다른 DB 변환을 제공한다는 뜻은 아니다.

백업을 제공할 때에는 SQLite의 [일관된 백업](https://sqlite.org/backup.html)과 등록된 설정·본문·산출물 파일을 연결한 목록을 함께 확보한다.
동시 파일 발행·정리가 목록을 바꾸지 않는 경계를 두며 실행 중인 SQLite 본체 파일 하나만 복사해 완전한 백업이라고 표시하지 않는다.
인증 비밀·세션은 일반 백업에서 제외하고 검색 색인·모델 파일은 재생성·재준비할 수 있어야 한다.
DAERI가 관리하는 백업 사본에도 원래의 기한·삭제 조건을 적용한다.

복원 자료는 사용 전 현재 정책·기한·삭제·철회 상태와 대조하고 색인은 유효 정본에서 다시 만든다.
현재 저장소의 삭제·차단 기록은 오래된 백업으로 덮어쓰지 않는다.
최신 삭제·권한 상태를 신뢰할 수 없으면 복원 본문·기억은 격리하고 제공·재사용하지 않는다.
포괄적인 새 승인으로 과거 삭제 여부를 대신하지 않으며 확인할 수 없으면 새 관찰·출처 검증으로 새 자료를 만든다.

과거 실행 소유권과 승인을 복원만으로 활성화하지 않는다.
백업 이후 누락됐을 수 있는 호출·효과를 확인하기 전 같은 작업을 반복하지 않으며 [중단·복구 계약](../tasks/workflow.md#중단재개와-외부-결과-확인)을 따른다.
다른 사용자·PC로의 이전은 자신의 인증·대상 진단을 다시 요구하고 기존 실행 권한을 복제하지 않는다.

## 인증 저장과 전달

profile은 비밀값 대신 로컬 인증 참조를 보관한다.
실행기는 등록된 연결을 위해서만 그 참조를 해소하고 필요한 인증 정보를 전달한다.
다른 연결의 인증이나 주변 환경의 자격 증명을 함께 사용하지 않는다.

비밀값은 OS 또는 제공자의 안전한 저장소를 사용한다.
잠김·만료·미지원이면 필요한 복구 조치를 안내하며 평문 저장으로 자동 대체하지 않는다.
macOS는 키체인, Windows는 자격 증명 보관 기능의 native backend를 선택한다.
지원하지 않는 OS나 잠긴 저장소를 평문 파일 backend로 대체하지 않는다.

비밀은 제공자 로그인 또는 안전한 로컬 입력 경로에서 처리한다.
채팅·모델 입력·소스 저장소·로그·오류·산출물에 비밀번호·토큰·인증 세션을 넣지 않는다.
원격 연결은 등록한 대상과 신뢰 조건을 확인하며 다른 곳으로 인증 정보를 임의 전달하지 않는다.

로컬 인증 등록은 실제 사용자 터미널의 숨김 입력 또는 사용자가 명시한 표준 입력으로만 받는다.
일반 자동 실행에서 터미널이 없으면 비밀 입력이 필요하다고 반환하며 채팅 입력으로 전환하지 않는다.
입력은 비어 있지 않은 한 줄·최대 16 KiB로 제한한다.
등록·상태·삭제 결과는 인증 참조와 처리 여부만 반환하고 비밀 본문을 출력하지 않는다.

인증 `status`는 지정 참조의 현재 해소 가능 여부를 확인한다.
참조를 찾지 못하거나 저장소가 잠기면 `available: false`이며 원격 권한이나 로그인 성공으로 대신 해석하지 않는다.
`env:` 참조는 상태 확인·연결에서만 읽고 로컬 인증 등록·삭제로 호스트 환경 변수를 변경하지 않는다.

제공자가 사용자 로그인을 요구하면 해당 안내에 따라 사용자가 인증한다.
계획 승인을 대화에서 받는 것과 제공자 인증 절차는 구분한다.
원격 권한이 있다는 사실도 업무 계획 승인을 대신하지 않는다.

### Infra 제공자의 최초 SSO 로그인

첫 Infra recipe는 자체 격리 환경의 제공자 SDK로 device authorization을 수행한다.
제공자 로그인 자식은 해당 recipe의 Python을 `-I`로 실행하고 [공통 환경 격리](../installation/environment.md#공통-실행-파일과-환경-격리)를 적용한다.
별도 제공자 CLI의 수동 설치를 필수로 요구하지 않는다.
이 흐름은 사용자가 명시한 관리 로그인에서만 시작하며 일반 MCP 시작·업무 접수·기억 조회가 로그인을 수행하지 않는다.

| 입력·조건 | 처리·결과 |
|---|---|
| profile·인스턴스 | 준비된 Infra recipe와 실제 대상의 제공자 profile·계정·지역 일치 확인 |
| 최초 연결의 시작 URL·SSO 지역·역할 | 선택한 제공자 profile의 초기 인증 설정 준비 |
| 기존 제공자 설정 | 해당 profile·SSO session을 읽어 같은 대상의 재로그인 준비 |
| 사용자 확인 | 제공자가 발급한 HTTPS 확인 URL·사용자 코드만 표시하고 브라우저 인증 대기 |
| 인증 완료 | 표준 제공자 인증 캐시에 토큰 보관, profile·계정·역할·만료 시각만 보고 |

이름이 같은 기존 제공자 설정이 다른 계정·시작 URL·역할을 가리키면 덮어쓰지 않는다.
다른 실제 대상으로 변경하려면 별도 profile이나 명시적인 구성 변경 경로로 처리한다.
기존 파일의 다른 profile 설정은 유지하고 로그인 대기 중 외부에서 파일이 바뀌면 덮어쓰지 않는다.

등록한 public client로 device authorization을 시작한 뒤 제공자가 정한 간격으로 확인한다.
사용자 인증 대기는 최대 10분이며 대기·속도 제한 응답에 맞춰 간격을 늘릴 수 있다.
거절·만료·인증 오류·시간 초과 뒤 새 authorization을 자동 발급하거나 무제한 반복하지 않는다.

인증 브라우저는 제공자의 실제 사용자 로그인이며 DAERI 업무 계획을 승인하는 UI가 아니다.
브라우저를 자동으로 열 수 없거나 사용자가 비활성화하면 표시한 URL로 직접 인증할 수 있다.
DAERI는 사용자 비밀번호·인증 토큰을 대화로 입력받지 않는다.

제공자 설정은 사용자 홈의 `.aws/config`, 인증 토큰은 표준 `.aws/sso/cache` 형식으로 보관한다.
새 파일은 사용자 전용 권한으로 쓰고 임시 파일을 완료 후 교체하며 심볼릭 링크 저장 위치는 거부한다.
access token·refresh token·client secret·device code는 호스트·DAERI 업무 저장소·로그·오류로 반환하지 않는다.
로그인 성공도 업무 승인을 부여하지 않으며 이후 연결 진단과 실행 시점의 대상·권한 검사를 거친다.

[제공자 SDK의 public client 등록](https://docs.aws.amazon.com/boto3/latest/reference/services/sso-oidc/client/register_client.html), [device authorization](https://docs.aws.amazon.com/boto3/latest/reference/services/sso-oidc/client/start_device_authorization.html), [토큰 확인](https://docs.aws.amazon.com/boto3/latest/reference/services/sso-oidc/client/create_token.html)을 사용한다.
가짜 응답의 대기·속도 제한·거절·만료와 네트워크를 차단한 실제 SDK의 요청·표준 캐시 읽기를 검증했다.
실제 회사 SSO 로그인·브라우저 UI·계정 권한은 검증하지 않았다.

## 만료·교체·철회와 재개

인증 만료·잠김·철회·참조 해소 실패 시 새 호출을 보류한다.
재인증 이후 실제 사용 주체·대상·권한과 업무 승인 범위를 다시 확인한다.
다른 계정·연결로 자동 대체하지 않는다.

현재 구현은 인증값·제공자 설정·인증 캐시 변경을 계약 변경으로 취급한다.
동일 주체의 단순 갱신인지 자동으로 증명하지 않으므로 갱신 후 연결을 다시 진단하고 새 계약으로 계획을 다시 승인받는다.
profile 구성까지 바뀌었다면 새 업무에서 변경된 profile을 선택한다.
진행 중인 원격 작업이 인증 해제만으로 종료되었다고 가정하지 않는다.

연결 해제·로컬 로그인 종료·제공자 권한 철회는 서로 다른 작업이다.
사용자가 선택한 범위를 처리하고 다른 연결의 공유 인증을 임의로 제거하지 않는다.

## 변경·공유·복구

profile 삭제·백업·복원의 저장 흐름은 위 [로컬 저장 구조](#로컬-저장-구조), 프로그램 갱신은 [환경 준비](../installation/environment.md#업데이트와-데이터-보존)를 따른다.

공유 템플릿에는 범주·역할·필요 입력·비밀을 제외한 연결 구조만 담는다.
인증 비밀·로그인 세션·업무 자료·개인 기억·승인 권한은 공유하지 않는다.
다른 사용자·PC는 자신의 인증을 연결하고 진단을 다시 수행한다.

## 검증과 사용자 환경 확인

복수 범주·복수 인스턴스, 기본값 변경 뒤 기존 업무 유지, 두 호스트 동시 접근을 확인한다.
인증 만료·주체 변경·권한 철회·비밀 노출 방지와 자료 만료·정리를 확인한다.
기억 정책의 업무 고정, profile·실제 대상별 검색 격리, 두 호스트의 기억 갱신 충돌도 확인한다.
로컬 profile·저장소의 구현·검증 범위는 [최초 구현 계획](../../plans/initial-implementation.md#현재-구현-단위와-검증-경계)을 따른다.
설정 가져오기·내보내기·비밀 거부·프로그램 준비 실패·멱등 재사용은 로컬 자동 테스트로 확인한다.
첫 연결의 잠금 조합은 macOS의 임시 격리 환경에 실제 설치해 확인하며 상세 도구 등록 결과는 리소스 명세에 구분한다.
실제 회사 로그인·운영 리소스 접근·OS 인증 저장소 UI·Windows 실행은 별도 검증이 필요하다.
