# 사용자 승인 UI와 검증

상태: 실제 사용자 확인 요구사항 확정 + 브라우저·WebAuthn 경로 선정; 상세 단순화 제안·실행 미검증

두 호스트의 승인 UI·키 등록·응답 검증을 정의한다.
업무 승인 의미는 [계획·승인](../tasks/approval.md), 공개 입출력은 [계획 MCP 규격](../mcp/plans.md)을 따른다.

## 선택한 경로와 이유

두 호스트 모두 **외부 OS 브라우저의 로컬 DAERI UI + WebAuthn 사용자 확인**을 사용하도록 설계한다.
사용자는 실행기가 보존한 계획을 읽고 승인할 때 등록한 passkey·인증기로 확인한다.
같은 유효 계획의 개별 호출은 재확인하지 않고 범위 변경·철회 등 새 승인이 필요할 때 계획을 다시 확인한다.

| 후보 | 장점 | 초기 판단 |
|---|---|---|
| 호스트 일반 도구 허용창 | 대화 안에서 이용 | 도구 호출 허용과 업무 계획 승인을 구분 |
| 호스트 native elicitation | form·URL 안내 가능 | 안내에 이용; 응답만으로 승인하지 않음 |
| OS별 native 계획 UI | OS 화면과 키 정책 활용 | 두 OS의 화면·등록 구현 비용이 큼 |
| 로컬 브라우저 + WebAuthn | 화면과 검증을 두 호스트·OS에서 공유 | 초기 경로 유지 |
| 별도 호스트 client·SDK 앱 | UI·통신을 직접 소유 | 초기 제품에 추가하지 않음 |

기존 인증기와 검증 라이브러리를 활용해 별도 서명 프로토콜을 만들지 않는다.
최초 등록도 같은 setup UI와 WebAuthn을 사용한다.

### 호스트별 차이

Codex의 [App-server](https://learn.chatgpt.com/docs/app-server)·[Auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review)와 Claude의 [Elicitation](https://code.claude.com/docs/en/hooks#elicitation)·[ElicitationResult](https://code.claude.com/docs/en/hooks#elicitationresult)는 안내에만 이용한다.
도구 허용·form `accept`·자동 변경 가능한 hook 응답은 특정 계획의 사용자 승인 증거가 아니다.

지원 UI·등록 키·검증 경로가 없으면 `APPROVAL_UNAVAILABLE`로 실행을 차단한다.
채팅의 승인 주장·`approved=true`·hook·unsigned callback으로 대체하지 않는다.

## 신뢰 경계와 최초 등록

승인 주체는 같은 OS 사용자가 로컬 setup에서 등록하며 리소스 로그인·모델 입력 사용자 이름과 구분한다.

신뢰한 배포물·setup·브라우저·검증기·사용자 저장소가 정상이라는 전제에서 동작한다.
같은 OS 사용자 권한의 악성 프로그램이 그 코드·저장소·브라우저를 바꾸는 상황을 완전히 격리하지 않는다.

1. 사용자가 로컬 setup을 직접 시작하고 승인 주체 등록을 선택한다.
2. setup이 OS 사용자·저장소·배포 출처를 확인하고 제한된 등록 세션을 연다.
3. UI가 등록 목적과 주체를 표시하고 `userVerification: required`로 WebAuthn 키를 만든다.
4. 검증기가 저장한 challenge·정확한 origin·RP ID·사용자 존재·사용자 검증과 공개키를 검사한다.
5. 같은 등록 세션·기한·사용자 문맥을 재검사하고 등록 근거와 활성 키를 원자적으로 보존한다.

공개 업무 MCP·일반 승인 UI에 키 활성화 API를 두지 않는다.
등록 세션·인증 응답·새 공개키를 모델 인수·파일 가져오기로 대신 받지 않는다.

내부 등록부에는 OS 소유 문맥·주체·credential ID·공개키·RP ID·현재 권한·키 개정을 보존한다.
승인 요청이 보낸 주체·공개키 대신 그 등록부에서 실제 주체와 권한을 찾는다.

등록의 `attestation: none`은 특정 제조사·하드웨어 키 증명을 요구하지 않는 선택이다.
가상 인증기·headless 등록·시험 자동 승인을 운영 경로에 넣지 않으며 attestation만으로 실제 인증기를 식별한다고 보장하지 않는다.
근거: [WebAuthn 등록](https://www.w3.org/TR/webauthn-3/#sctn-registering-a-new-credential).

## 화면과 사용자 흐름

화면은 모델 요약·HTML 대신 보존한 계획·현재 근거로 만든다.
전체 조건을 펼쳐 읽게 하고 표시 손실·누락이 있으면 승인을 막는다.

| 화면 영역 | 확인할 내용 |
|---|---|
| 요청·맥락 | 업무·계획·서비스 profile과 구성 개정 |
| 대상·방법 | DB·계정·리전·프로젝트, 읽기·변경·검증과 분기 |
| 범위·예산 | 조건·기간·필드·경로·부작용·한도·소비·예약·잔여량 |
| 결과·제한 | 모델 제공·내보내기·종료 후 보관 필드, 조회·보고·산출물의 공통 보존기간, 마스킹·전달 대상·제약 |
| 재계획 차이 | 늘어난 범위와 승계할 소비·근거·미확인 효과 |
| 결정 | 승인·수정 요청·거절·확인 취소 |

비밀값을 제외하고 설명은 이스케이프한 텍스트로 렌더링해 업무 자료의 스크립트·HTML·외부 코드를 실행하지 않는다.
큰 숫자·정밀한 조건을 브라우저 숫자 변환으로 반올림하지 않는다.

1. 호스트가 저장한 현재 계획으로 `daeri_approval_request`를 호출한다.
2. 실행기가 권한·UI 준비 상태를 검사하고 불변 확인 표시본을 만든다.
3. 실행기가 운영체제의 브라우저 열기 기능으로 검증한 로컬 UI를 직접 연다.
4. 사용자가 승인하면 해당 표시본에만 연결한 WebAuthn 확인을 수행한다.
5. 실행기가 응답과 현재 조건을 검증해 승인 기록을 보존한다.
6. 호스트가 기존 업무·계획 도구로 상태를 읽고 승인 안의 업무를 이어간다.

macOS는 Safari, Windows는 Edge를 최초 검증 대상으로 유지한다.
Touch ID·Windows Hello·FIDO2의 실제 동작을 조합별로 확인하고 브라우저·인증기 부재·사용자 검증 실패는 차단 사유로 안내한다.

진입 URL·토큰은 실행기 내부에서 전달하고 모델·공개 MCP에는 기존 요청의 상태만 제공한다.
열기 실패·화면 닫힘 뒤에는 사용자가 로컬 관리 경로에서 같은 유효 요청을 선택해 다시 연다.
재열기는 원 계획·요청·기한을 유지하고 새 제한 UI 세션으로 연결하며 만료·무효 요청을 재사용하지 않는다.
이전 UI 세션·미사용 challenge는 폐기해 이전 화면의 응답을 적용하지 않는다.
같은 MCP 요청의 재전달은 화면을 다시 여는 지시가 아니다.

### 결정별 처리

| 결정 | 확인 근거와 처리 |
|---|---|
| `approve` | WebAuthn 서명 검증과 현재 권한 검사를 통과해야 승인 발급 |
| `request_changes` | 제한된 UI 세션의 수정 설명을 기록; 승인 발급 없이 재계획 |
| `decline` | UI 세션의 거절을 기록; 승인 발급 없음 |
| `cancel` | UI 세션의 확인 요청만 취소; 업무 취소와 구분 |

권한을 늘리지 않는 세 결정은 인증기 서명 없이 UI 세션의 제어 이벤트로 보존하며 검증된 사용자 승인으로 표시하지 않는다.
수정 설명은 데이터로 보존하고 새 계획이나 실행 지시로 자동 적용하지 않는다.

브라우저 닫기·인증 대화 취소·연결 손실은 결정 제출이 아니다.
승인을 부여하지 않고 기한 만료 또는 세션 종료 시 미완료 요청을 무효화한다.

## 승인 응답 검증

WebAuthn 파서·알고리즘은 검증된 라이브러리를 재사용한다.
Python 코어의 후보는 [`python-fido2`의 `Fido2Server`](https://developers.yubico.com/python-fido2/API_Documentation/autoapi/fido2/server/index.html)이며 선택·호환 조건은 [의존성 관리](../installation/environment.md#버전과-재현-가능한-환경)를 따른다.

실행기는 매 시도의 암호학적 난수 challenge를 요청·주체·원 호스트 세션·업무·불변 계획·`approve` 결정·표시본 digest에 연결해 보존한다.
표시본은 profile 대상·권한·계획 조건·누적 예산·승인 유효조건을 포함한다.

digest는 실행기가 보존한 원본 바이트에서 계산하며 브라우저가 제출한 계획·digest·검증 state로 교체하지 않는다.
사용자 확인과 관련 없는 내부 UI 준비가 스스로 업무 개정을 바꾸어 확인 근거를 무효화하지 않게 한다.

| 검사 | 필수 조건 |
|---|---|
| UI 접근 | 현재 제한 세션·요청 연결·CSRF·입력 크기와 타입 |
| 현재 근거 | 같은 저장소·주체·원 세션·현재 계획·profile·권한·소유권·예산 |
| challenge | 보존한 원 값과 일치, 미사용, 유한 기한 안 |
| WebAuthn | 등록 credential·정확한 origin·RP ID hash·UP·required UV·원본 서명 |
| 추가 조건 | 일치하는 userHandle, cross-origin·iframe 거부, 허용한 키·알고리즘·키 상태 |
| 보존 | 현재 조건 재검사 뒤 증거·승인·challenge 소비·업무 개정을 함께 저장 |

`clientDataJSON.type`은 `webauthn.get`이며 서명은 재직렬화 없이 원본 authenticatorData와 clientDataJSON의 hash로 검사한다.
근거: [WebAuthn assertion 검증](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion).

카운터·backup flags의 라이브러리 보장을 확인하며 정상적인 0 카운터를 무조건 거부하거나 복제 의심을 단일 사용 challenge의 대안으로 쓰지 않는다.
필수 검사를 제공하지 못하거나 기록을 신뢰할 수 없으면 승인 발급을 차단한다.

### 중복·교체·기한

같은 요청·증거 재전달은 현재 열람·철회·만료 정책에 따라 보존한 결정을 반환하며 승인·개정·예산을 다시 만들지 않는다.
같은 키·challenge에 다른 증거·결정이 오면 충돌로 거부한다.

실행기는 유한 기한을 검사하며 서명 시도는 원 요청 기한을 넘지 않고 화면 열기·조회도 기한을 연장하지 않는다.
초기 실행 승인은 해당 계획이 활성이고 현재 권한·정책이 유효한 동안 유지한다.

업무 일시중지·계획 교체·취소·철회·권한 변경이나 표시한 소비·예약·외부 효과 변경은 오래된 응답을 무효화한다.
화면을 자동 갱신하고 이전 서명을 적용하지 않으며 최신 근거로 다시 확인한다.
저장 직전 재검사로 동시 응답·계획 교체가 승인 상태를 되돌리지 못하게 한다.

발급된 승인도 [업무 실행 검사](../tasks/workflow.md#실행-검사와-기록)를 통과해야 호출할 수 있다.
일시중지·재개와 누적 소비·예약·미확인 효과는 [업무 흐름](../tasks/workflow.md)을 따른다.

## 로컬 서비스와 키 복구

UI는 필요한 동안 `http://localhost:<실제 포트>`의 loopback에서 실행한다.
RP ID는 `localhost`로 두고 정확한 scheme·host·port origin을 검사하며 다른 주소로 fallback하지 않는다.

제한된 UI cookie·세션, 정확한 Host·Origin, CSRF·외부 프레이밍 차단을 적용한다.
진입 토큰·challenge·서명 원문은 공개 MCP·모델·로그·호스트 설정에 넣지 않는다.
URL 열기·HTTP callback 성공이 승인 증거는 아니다.

근거인 [localhost RP 허용](https://www.w3.org/TR/webauthn-3/#relying-party-identifier)이 실제 Safari·Edge 호환성을 보장하지는 않는다.
호스트 종료와 UI 세션 손실은 미완료 요청을 무효화하고 이미 보존한 기록은 유지한다.

키 추가·교체는 사용자가 시작한 setup에서 기존 키로 확인하고 분실은 수동 재등록으로 처리한다.
파일 복구·새 사용자·새 PC가 과거 권한을 자동 승계하지 않는다.

키·등록 정책 변경은 기존 요청·challenge·승인 효력을 철회하고 현재 계획의 재확인을 요구한다.
과거 승인 근거·업무·호출·사용량·외부 효과는 삭제하거나 새 사실로 덮어쓰지 않는다.
신뢰한 재등록 경로도 사용할 수 없으면 실행을 차단하고 복구 조치를 안내한다.

## 구현 시 검증

[초기 호환성 단계](../../plans/initial-implementation.md#1-호환성과-스택)에서 Mac의 실제 등록·승인·브라우저 열기를 먼저 확인하고 Windows에서 같은 계약을 검증한다.
잘못된 키·origin·RP·UP/UV·표시본·계획·profile·예산·기한과 unsigned 승인을 거부해야 한다.
동시 응답·재전달·계획 교체·키 분실·철회·저장 실패에서 승인과 소비가 중복되지 않아야 한다.

WebAuthn은 키의 challenge 서명·사용자 확인을 입증하며 계획 이해·화면 무결성·특정 하드웨어 보유까지 입증하지 않는다.
실제 UI·등록·서명·브라우저 동작은 미검증이며 검증 전에는 준비 완료로 표시하지 않는다.
