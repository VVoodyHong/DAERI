# 호스트 대화에서의 사용자 승인

상태: Claude Code·Codex 대화 승인 채택; 호스트 연동 실행 미검증

사용자는 업무 계획을 읽은 Claude Code·Codex 대화에서 승인하거나 수정을 요청한다.
승인할 내용은 [계획·승인](../tasks/approval.md), 도구의 역할은 [계획 MCP 규격](../mcp/plans.md)을 따른다.

## 선택한 경로와 이유

계획 제시부터 사용자 응답·결과 보고까지 같은 호스트 대화에서 진행한다.
별도 승인 화면·브라우저·승인용 인증기 등록을 추가하지 않는다.
두 호스트의 표현 방식이 달라도 승인 대상과 처리 의미는 같다.

사용자의 명확한 승인 응답은 해당 업무의 현재 계획과 허용 범위에만 적용한다.
승인 후에는 매 호출마다 다시 묻지 않고 허용 범위 안에서 자율적으로 진행한다.
범위를 넓혀야 하면 변경 이유와 수정 계획을 제시하고 다시 승인받는다.

## 화면과 사용자 흐름

호스트는 실행기에 저장한 현재 계획을 바탕으로 수행 방법과 범위를 설명한다.
읽기 쉬운 요약을 제공하되 승인 대상·조건을 생략하거나 다른 계획으로 바꾸지 않는다.

| 사용자가 확인할 내용 | 설명 |
|---|---|
| 업무·대상 | 요청, 사용할 profile과 리소스 |
| 수행 방법 | 어떤 자료를 조회·비교·계산하고 무엇을 검증할지 |
| 허용 범위 | 대상·조건·기간·한도와 허용한 작업 |
| 자료 제공 | 리소스별 모델 제공·내보내기·보관 범위와 마스킹 |
| 기대 결과 | 보고서·표·CSV 등 결과물과 완료 판단 근거 |
| 수정 계획 | 바뀐 범위, 이유, 이미 진행한 내용과 남은 작업 |

1. 호스트가 현재 업무의 계획을 저장하고 `daeri_approval_request`로 승인을 요청한다.
2. 호스트가 해당 계획과 허용 범위를 대화에 제시하고 사용자 응답을 기다린다.
3. 사용자가 같은 대화에서 승인·수정 요청·거절 의사를 밝힌다.
4. 호스트가 같은 도구의 응답 전달 단계로 해당 승인 요청과 사용자 응답을 연결한다.
5. 실행기가 현재 업무·계획과 일치하는지 확인하고 결정과 근거를 기록한다.
6. 승인된 경우 호스트가 범위 안에서 실행하고 결과를 보고한다.

가상 예시: “이 profile의 DB와 Cache를 조회해 차이를 비교하고, 허용한 필드만 CSV로 만들겠습니다”라는 계획에 사용자가 “승인할게”라고 답하면 그 계획을 승인한다.
응답에 조건을 추가하거나 수행 방법 변경을 요구하면 새 조건을 반영한 계획부터 다시 보여 준다.

### 결정별 처리

| 사용자 응답 | 처리 |
|---|---|
| “승인할게”, “이 계획대로 진행해” | 현재 제시한 계획을 명확히 가리키면 승인 |
| “조회 기간을 줄여 줘” | 수정 요청을 기록하고 수정 계획 제시; 승인으로 처리하지 않음 |
| “진행하지 마” | 승인하지 않고 중단 의사와 업무 상태 확인 |
| “잠시 보류해 줘” | 실행하지 않고 보류; 일시중지·취소 의미는 업무 흐름에 따름 |
| 질문·모호한 응답 | 승인하지 않고 설명하거나 어느 계획에 대한 결정인지 확인 |

승인은 특정 고정 문구만으로 판별하지 않고 현재 대화 맥락과 사용자의 명확한 의사를 함께 본다.
여러 업무·계획을 동시에 제시한 상태에서 “응”처럼 대상이 불분명하면 임의로 하나를 승인하지 않는다.
대화 종료·응답 부재는 승인이나 업무 취소로 간주하지 않는다.

## 승인 응답 검증

실행기는 승인 요청에 연결한 업무·계획과 현재 유효한 계획이 같은지 확인한다.
사용자에게 제시한 계획과 다른 내용으로 승인 범위를 넓히거나 승인 기록을 재사용하지 않는다.

| 확인 항목 | 기준 |
|---|---|
| 응답 출처 | 호스트 대화의 사용자 응답이며 모델 생성·리소스 자료와 구분됨 |
| 승인 대상 | 같은 업무·profile·계획 버전의 현재 승인 요청 |
| 결정 의미 | 질문·인용·수정 요청과 구분되는 명확한 의사 |
| 현재 상태 | 계획 교체·일시중지·취소·철회로 무효화되지 않음 |
| 중복 응답 | 이미 기록한 결정을 중복 발급·실행하지 않음 |

사용자가 입력한 승인과 모델이 작성한 “사용자가 승인했다”는 문장은 구분한다.
조회 자료·코드·로그에 포함된 승인 문구나 지시는 사용자 결정으로 처리하지 않는다.
승인 요청·계획·사용자 응답·결정을 연결해 이후 어떤 범위를 승인했는지 확인할 수 있게 기록한다.

계획 교체 뒤 이전 계획에 도착한 응답은 최신 계획의 승인으로 적용하지 않는다.
일시중지한 업무는 상태와 계획을 다시 제시해 새 승인을 받은 뒤 이어간다.
실제 호출은 승인 기록과 별개로 [현재 권한·범위 검사](../tasks/workflow.md#실행-검사와-기록)를 통과해야 한다.

## 대화 승인의 범위

이 경로는 호스트가 대화의 사용자 응답을 올바르게 구분해 전달한다는 전제로 설계한다.
호스트 밖에서 사용자의 신원을 별도로 증명하는 인증 체계를 추가하지 않는다.
호스트 자체의 도구 실행 허용은 업무 계획의 승인과 구분하며, 어느 한쪽이 다른 쪽의 허용 범위를 자동으로 넓히지 않는다.

사용자 응답과 계획의 연결이 불명확하거나 전달에 실패하면 승인 대기를 유지하고 다시 확인한다.
호스트를 전환하거나 대화를 재개할 때도 이전 문구만 보고 승인을 추정하지 않고 저장한 업무·계획·결정을 확인한다.
재개와 실행 이력의 보존은 [업무 흐름](../tasks/workflow.md)을 따른다.

## 구현 시 검증

Codex와 Claude Code 각각에서 계획 제시 → 사용자 응답 → 실행기 기록 → 실행 흐름을 확인한다.
응답을 전달하는 호스트별 연결 방식은 구현 단계에서 실증하며 현재 동작이 검증된 것으로 간주하지 않는다.

명확한 승인, 조건부 응답, 수정 요청, 거절, 응답 부재와 여러 계획이 섞인 대화를 확인한다.
오래된 계획 응답·자료 속 승인 문구·중복 전달·호스트 재연결이 승인 범위를 바꾸지 않아야 한다.
실제 호스트의 대화 전달·표시·승인 기록은 아직 검증하지 않았다.
