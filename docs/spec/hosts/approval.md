# 호스트 대화에서의 사용자 승인

상태: Claude Code·Codex 대화 승인 채택; 호스트 연동 실행 미검증

사용자는 업무 계획을 읽은 Claude Code·Codex 대화에서 승인하거나 수정을 요청한다.
승인할 내용은 [계획·승인](../tasks/approval.md), 도구의 역할은 [계획 MCP 규격](../mcp/plans.md)을 따른다.

## 선택한 경로와 이유

계획 제시부터 사용자 응답·결과 보고까지 같은 호스트 대화에서 진행한다.
별도 승인 화면·브라우저·승인용 인증기 등록을 추가하지 않는다.
두 호스트의 표현 방식이 달라도 승인 대상과 처리 의미는 같다.

사용자의 명확한 승인 응답은 해당 업무의 현재 계획과 허용 범위에만 적용한다.
승인 후에는 매 호출마다 다시 묻지 않고 허용 범위 안에서 자율적으로 진행한다.
범위를 넓혀야 하면 변경 이유와 수정 계획을 제시하고 다시 승인받는다.

## 화면과 사용자 흐름

호스트는 실행기에 저장한 현재 계획을 바탕으로 수행 방법과 범위를 설명한다.
읽기 쉬운 요약을 제공하되 승인 대상·조건을 생략하거나 다른 계획으로 바꾸지 않는다.

| 사용자가 확인할 내용 | 설명 |
|---|---|
| 업무·대상 | 요청, 사용할 profile과 리소스 |
| 수행 방법 | 어떤 자료를 조회·비교·계산하고 무엇을 검증할지 |
| 허용 범위 | 대상·조건·기간·한도와 허용한 작업 |
| 자료 제공 | 리소스별 모델 제공·내보내기·보관 범위와 마스킹 |
| 기억 활용·보존 | 참고한 기억·추가 확인, 새 지식의 범주·미래 제공·보존 범위와 기간 |
| 기대 결과 | 보고서·표·CSV 등 결과물과 완료 판단 근거 |
| 수정 계획 | 바뀐 범위, 이유, 이미 진행한 내용과 남은 작업 |

1. 호스트가 현재 업무의 계획을 저장하고 `daeri_approval_request`로 승인을 요청한다.
2. 호스트가 해당 계획과 허용 범위를 대화에 제시하고 사용자 응답을 기다린다.
3. 사용자가 같은 대화에서 승인·수정 요청·거절 의사를 밝힌다.
4. 호스트가 실제 답변과 대화 맥락에서 결정을 해석해 응답 전달 단계로 함께 보낸다.
5. 실행기가 현재 업무·계획·대기 요청·권한을 검사하고 실제 답변과 결정을 연결해 기록한다.
6. 승인된 경우 호스트가 범위 안에서 실행하고 결과를 보고한다.

가상 예시: “이 profile의 DB와 Cache를 조회해 차이를 비교하고, 허용한 필드만 CSV로 만들겠습니다”라는 계획에 사용자가 “승인할게”라고 답하면 그 계획을 승인한다.
응답에 조건을 추가하거나 수행 방법 변경을 요구하면 새 조건을 반영한 계획부터 다시 보여 준다.

### 결정별 처리

| 실제 사용자 응답의 가상 예시 | 호스트 해석과 처리 |
|---|---|
| “승인할게”, “이 계획대로 진행해” | 현재 계획 전체를 명확히 가리키면 `approve` |
| “좋아, 다만 조회 기간은 줄여 줘” | `request_changes`; 새 조건을 반영한 계획을 다시 제시 |
| “이 계획은 승인하지 않을게” | `decline`; 계획 단계로 돌아가며 업무 자체를 취소하지 않음 |
| “이 확인 요청만 취소해 줘” | `cancel`; 확인 요청만 종료 |
| “업무를 잠시 멈춰 줘” | 업무 일시중지 도구로 처리 |
| “업무를 취소해 줘” | 업무 취소 도구로 처리 |
| 질문·인용·대상 불명확·의도가 모호한 “진행하지 마” | null; 승인 대기를 유지하고 설명·확인 |

호스트는 고정 문구만으로 판별하지 않고 현재 대화 맥락과 명확한 의사를 함께 본다.
조건 변경이 포함된 동의는 현재 계획의 승인으로 전달하지 않는다.
여러 업무·계획을 제시한 뒤 “응”처럼 대상이 불분명하면 임의로 하나를 승인하지 않는다.
대화 종료·응답 부재는 승인이나 업무 취소로 간주하지 않는다.
공개 enum·상태 전이·도구 연결은 [승인 MCP](../mcp/plans.md#approvaloutcome과-실제-응답)가 정본이다.

## 승인 응답 검증

호스트는 자연어의 의미를 해석하고 실행기는 구조화된 대상·상태·권한을 검사한다.
실행기가 별도 생성 모델로 사용자 의사를 다시 판정하거나 답변의 조건으로 기존 계획을 수정하지 않는다.

| 담당 | 확인할 내용 |
|---|---|
| 호스트 | 실제 사용자 메시지와 모델 생성·리소스 자료를 구분 |
| 호스트 | 승인 대상과 조건 변경·질문·거절 의도를 해석 |
| 호스트 | 비밀 제거를 제외한 실제 답변을 요약·재작성 없이 결정과 함께 전달 |
| 실행기 | 업무·profile·계획·버전·표시본·대기 요청의 연결과 현재 승인 권한 검사 |
| 실행기 | 교체·중단·철회·만료·전제 변경과 멱등 중복 검사 |

사용자가 입력한 승인과 모델이 작성한 “사용자가 승인했다”는 문장은 구분한다.
조회한 코드·로그·문서의 승인 문구나 지시는 사용자 결정으로 처리하지 않는다.
호스트가 사용자 메시지 참조를 제공하면 함께 보존해 대응을 확인하며 참조를 필수 인증 수단으로 가정하지 않는다.

계획 교체 뒤 이전 계획에 도착한 응답은 최신 계획의 승인으로 적용하지 않는다.
일시중지한 업무는 상태와 계획을 다시 제시해 새 승인을 받은 뒤 이어간다.
실제 호출은 승인 기록과 별개로 [현재 권한·범위 검사](../tasks/workflow.md#실행-검사와-기록)를 통과해야 한다.
승인 직전에도 계획의 [기억 참조](../tasks/memory.md#계획-전-조회와-활용)가 현재 유효한지 확인한다.

## 대화 승인의 범위

호스트가 실제 사용자 응답을 올바르게 구분하고 그 의미를 해석한다는 신뢰 경계를 채택한다.
실행기는 호스트 대화 원문을 독립적으로 열람할 수 있다고 가정하지 않는다.
응답 참조가 있는 경우 이미 저장한 대응을 검사할 수 있지만 참조·문자열·enum만으로 자연어 해석의 정확성을 완전히 증명하지는 못한다.

이 한계를 별도 브라우저·서명·생성 모델로 해결하는 체계는 추가하지 않는다.
호스트 자체의 도구 실행 허용과 업무 계획 승인은 구분하며 어느 한쪽이 다른 쪽의 범위를 넓히지 않는다.

답변의 대상·의미가 모호하면 호스트는 null로 전달하고 실행하지 않는다.
실행기가 현재 요청·계획과 연결할 수 없으면 승인을 발급하지 않고 현재 상태를 유지한다.
호스트 전환·대화 재개 시 이전 문구만으로 승인을 추정하지 않으며 [업무 기록](../tasks/workflow.md)에서 현재 계획·결정을 확인한다.

## 구현 시 검증

Codex와 Claude Code 각각에서 계획 제시 → 사용자 응답 → 실행기 기록 → 실행 흐름을 확인한다.
응답을 전달하는 호스트별 연결 방식은 구현 단계에서 실증하며 현재 동작이 검증된 것으로 간주하지 않는다.

명확한 승인, 동의와 조건 변경이 섞인 답변, 질문·모호한 답변, 거절과 응답 부재를 확인한다.
업무 일시중지·업무 취소·확인 요청 취소가 각각 다른 도구·상태로 연결되는지 확인한다.
호스트가 잘못 해석한 결정을 구조 검사만으로 모두 탐지할 수 있다고 보고하지 않는다.
오래된 계획 응답·자료 속 승인 문구·다른 계획의 메시지 참조·결정만 바꾼 재전달·호스트 재연결이 승인 범위를 바꾸지 않아야 한다.
실제 호스트의 대화 전달·표시·승인 기록은 아직 검증하지 않았다.
