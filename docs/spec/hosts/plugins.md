# 호스트 플러그인과 로컬 실행

상태: 두 호스트·플러그인·로컬 실행 구조 채택; 공통 오프라인 진입 구현, 실제 호스트 설치·대화 연동 미검증

Codex·Claude Code에 DAERI를 배포하고 사용자의 PC에서 실행하는 흐름을 정의한다.
환경 준비는 [설치·배포](../installation/environment.md), 사용자 확인은 [대화 승인](approval.md)이 정본이다.

## 공통 구성

호스트가 요청을 해석하고 필요한 자료·수행 방법·다음 행동을 판단한다.
플러그인은 setup·profile·work·list-profiles Skill과 로컬 DAERI MCP 실행기를 연결한다.
실행기는 profile·승인·범위·이력·기억을 관리하고 필요한 리소스의 연결을 사용한다.

| 구성 | 역할 |
|---|---|
| 호스트별 플러그인 | 마켓플레이스 등록·설치와 Skill·실행기 연결 |
| setup Skill | 환경 준비·profile·리소스 연결 관리 진입 |
| profile Skill | 현재 대화에서 새 업무의 기본 대상 선택·전환과 확인한 profile 삭제 |
| work Skill | 계획 전 기억 조회·계획·승인·실행·보고·기억 갱신 지침 |
| list-profiles Skill | 저장한 profile 목록 요약 |
| 공통 참조 문서 | 업무·승인·리소스 계약을 필요할 때 읽는 자료 |
| 로컬 실행 진입점 | 필요한 환경을 준비하고 설치된 DAERI MCP 실행 |

공통 Skill·참조는 같은 제품 명세를 따르고 호스트별 차이만 플러그인 구성에서 처리한다.
첫 안내부터 setup 질문·계획·승인·진행·결과 보고까지 기본 응답 언어는 한국어다.
사용자가 다른 언어를 명시하면 그 언어를 사용하며 명령·설정 키·제품명은 원래 표기를 유지한다.
개발용 AGENTS·CLAUDE 지침을 사용자 프로젝트에 복사하지 않는다.
별도 모델 판단 루프나 개발자가 운영할 중앙 서버는 추가하지 않는다.
호스트가 기억의 필요성과 갱신 후보를 판단하며 로컬 임베딩 모델은 검색용 벡터를 만든다.
별도 생성 LLM이나 에이전트 프레임워크를 필수 구성으로 두지 않는다.

## 배포와 최초 사용

1. 배포자가 저장소에 DAERI 소스와 호스트별 마켓플레이스 배포 구성을 제공한다.
2. 사용자가 해당 저장소의 마켓플레이스를 Codex 또는 Claude Code에 추가하고 DAERI 플러그인을 설치한다.
3. 사용자가 `/setup {profile명}`에 해당하는 호스트 진입점으로 준비를 시작한다.
4. 해당 profile에서 사용할 리소스 범주·어댑터·대상·연결·인증 방식을 정한다.
5. 선택한 연결과 로컬 임베딩에 필요한 프로그램·의존성을 검사하고 필요한 준비·설치를 진행한다.
6. 준비한 profile과 리소스별 실제 확인 결과·남은 조치를 안내한다.
7. 해당 대화에서 확인한 profile을 대상으로 work 또는 자연어로 업무를 요청한다.

`/setup {profile명}`은 공통 사용 흐름을 설명하는 논리적 이름이다.
실제 호출 이름과 설치 방식은 아래 호스트별 구성을 따른다.
저장소에 소스를 올리는 것만으로 마켓플레이스 등록·설치가 완료되지는 않는다.

배포 저장소와 profile이 접근할 Source 리소스는 서로 다른 역할이다.
구체적인 첫 배포·사용 대상은 [사용 예정 환경](../product.md#사용-예정-환경)에 모아 관리한다.

### 호스트별 구성

| 항목 | Codex | Claude Code |
|---|---|---|
| 마켓플레이스 | `.agents/plugins/marketplace.json` | `.claude-plugin/marketplace.json` |
| 플러그인 정의 | `.codex-plugin/plugin.json` 호환 형식 | `.claude-plugin/plugin.json` |
| MCP 구성 | 플러그인 정의 안의 `mcpServers.daeri` | 루트 `.mcp.json`의 `mcpServers.daeri` |
| 공유 Skill | `skills/<Skill명>/SKILL.md`의 setup·profile·work·list-profiles | 같은 네 Skill |
| 사용자 진입 | `$daeri:setup`, `$daeri:profile`, `$daeri:work`, `$daeri:list-profiles` 또는 Skill 선택 화면 | `/daeri:setup`, `/daeri:profile`, `/daeri:work`, `/daeri:list-profiles` |
| 준비 동작 | 선택한 Skill이 설치된 플러그인 루트에서 OS별 준비 실행 | 같은 방식 |

두 카탈로그의 이름은 `daeri-marketplace`, 플러그인 이름은 `daeri`다.
각 카탈로그는 저장소 루트의 플러그인을 가리키며 호스트는 설치한 사본에서 Skill과 프로그램을 읽는다.
마켓플레이스를 추가할 때는 두 호스트의 카탈로그를 포함한 저장소 전체를 제공한다.

아래 URL은 사내 저장소를 가정한 예시다.
실제 clone URL로 바꾸고 지정한 브랜치를 먼저 원격에 배포해야 한다.
첫 설치는 호스트를 종료한 상태에서 OS 터미널로 수행하고 설치 성공 뒤 호스트를 시작한다.
Codex는 [공식 CLI 규격](https://learn.chatgpt.com/docs/cli/reference)에 따라 다음 명령을 사용한다.

```shell
codex plugin marketplace add https://gitlab.example.com/team/DAERI.git --ref main
codex plugin add daeri@daeri-marketplace
codex
```

시작한 Codex의 새 대화에서 `$daeri:setup service-prod`로 준비한다.
준비 후에는 `$daeri:profile service-prod`, `$daeri:work 요청 내용`, `$daeri:list-profiles`로 호출한다.
삭제는 `$daeri:profile delete service-prod`로 요청한다.
Codex 플러그인의 Skill 이름은 [공식 구현](https://github.com/openai/codex/blob/rust-v0.147.0/codex-rs/core-skills/src/loader/namespace.rs#L175-L180)의 `플러그인명:Skill명`이며 `$`는 호스트의 Skill 호출 표시다.
`/skills`·`$` 선택기 또는 앱의 Skill 선택 화면에서도 DAERI의 같은 Skill을 선택할 수 있다.

Claude Code는 [터미널 설치 규격](https://code.claude.com/docs/en/discover-plugins#manage-plugins-from-your-shell)에 따라 아래를 순서대로 실행한다.
브랜치 지정은 URL의 `#ref`이며 Codex 터미널 명령의 `--ref`와 구분한다.

```shell
claude plugin marketplace add 'https://gitlab.example.com/team/DAERI.git#main'
claude plugin install daeri@daeri-marketplace --scope user
claude
```

Claude Code 플러그인은 위 명령에서 사용자 범위로 설치하고 시작한 대화에서 사용한다.
이미 실행 중인 호스트에서 설치·업데이트한 경우의 새로고침은 복구 절차로만 안내한다.
이 경우 `/reload-plugins`로 플러그인 변경을 반영한다.
활성화한 플러그인의 `/daeri:setup`이 목록에 없으면 `/reload-skills`로 Skill·명령 디렉터리를 다시 읽고 `/skills` 또는 `/` 메뉴에서 확인한다.
그래도 없으면 `/plugin`의 Installed에서 활성화 상태를, Errors에서 로딩 실패를 확인한다.
새로고침 명령을 지원하지 않거나 문제가 계속되면 Claude Code 프로세스를 종료하고 다시 실행한다.
두 새로고침의 역할은 [공식 명령 안내](https://code.claude.com/docs/en/commands)를 따른다.
Skill 목록의 노출과 로컬 MCP 연결 상태는 각각 확인하며 `/reload-skills`가 MCP 설정·프로세스까지 다시 연결한다고 해석하지 않는다.
그다음 `/daeri:setup service-prod`로 준비하고 `/daeri:work` 또는 자연어로 업무를 요청한다.
대화의 기본 대상을 고를 때는 `/daeri:profile`, 저장한 목록만 볼 때는 `/daeri:list-profiles`를 사용한다.
삭제는 `/daeri:profile delete service-prod`로 요청하며 같은 profile Skill에서 대상·범위를 확인한다.
플러그인 Skill은 [공식 이름 규칙](https://code.claude.com/docs/en/skills#choose-where-skills-load)에 따라 `/플러그인명:Skill명`으로 노출된다.
업무 진입 Skill명은 work이며 이전 업무 Skill의 별칭은 제공하지 않는다.

이미 pull한 로컬 사본을 쓰려면 두 호스트 모두 마켓플레이스 추가의 URL 대신 해당 저장소 루트 경로를 받는다.
공백이 있는 경로는 터미널에서 한 인자로 인용한다.
로컬 경로 추가에는 Git 브랜치 선택 인자를 붙이지 않고 준비한 checkout을 사용한다.
비공개 저장소는 사용자의 Git 인증·회사 접근 정책이 먼저 충족되어야 하며 DAERI profile 인증으로 대신하지 않는다.

공식 [Codex 플러그인 안내](https://developers.openai.com/plugins/build/plugins)와 [Claude Code 플러그인 안내](https://code.claude.com/docs/en/plugins)를 기준으로 실제 패키징을 확인한다.
준비 프로그램과 실행기의 책임·연결은 [개발 안내](../../development/dependencies.md#실행-진입점과-모듈)를 따른다.
macOS와 Windows는 같은 전용 Python stdio 진입 구성을 사용한다.
Codex의 command는 `${PLUGIN_ROOT}/.venv/bin/python.exe`, Claude Code는 `${CLAUDE_PLUGIN_ROOT}/.venv/bin/python.exe`이며 args는 `-I`, `-m`, `daeri.server`다.
공통 실행 파일의 OS별 준비는 [환경 격리](../installation/environment.md#공통-실행-파일과-환경-격리)를 따른다.
사용자 OS별 shell은 명시적인 setup에서만 선택하며 일반 MCP 시작에는 uv·PATH 검색·shell을 사용하지 않는다.
실행기는 설치한 플러그인 루트의 전용 환경으로 고정하고 사용자 작업 디렉토리나 외부 가상환경을 사용하지 않는다.
설치가 setup 실행·프로그램 다운로드·업무 승인까지 자동 허용하지 않으며 호스트의 명령 실행 권한도 별도로 적용한다.
위 설치 문법과 파일 구성은 공식 문서·호스트 소스·로컬 CLI 정의 검토로 확인했고 실제 마켓플레이스 추가·설치·Skill 호출은 검증하지 않았다.

### 설치한 플러그인 업데이트

배포자는 새 코드가 캐시에 반영되도록 플러그인·실행 패키지 버전을 함께 올린다.
사용자는 처음 등록한 Git 브랜치를 갱신하므로 다른 브랜치나 고정된 태그로 설치했으면 배포 대상을 먼저 확인한다.
기본 배포 대상은 `main`이며 이전 릴리즈 브랜치로 등록한 마켓플레이스는 `main`을 보도록 다시 등록한다.
마켓플레이스 목록 갱신과 설치한 플러그인 갱신은 구분하며 아래 명령은 호스트 대화가 아닌 터미널에서 실행한다.

```shell
claude plugin marketplace update daeri-marketplace
claude plugin update daeri@daeri-marketplace
```

```shell
codex plugin marketplace upgrade daeri-marketplace
codex plugin add daeri@daeri-marketplace
```

명령은 [Claude Code 업데이트](https://code.claude.com/docs/en/discover-plugins#update-plugins-now)와 [Codex 플러그인 관리](https://learn.chatgpt.com/docs/developer-commands#codex-plugin-marketplace)를 따른다.
업데이트 뒤 호스트를 다시 시작하고 setup으로 플러그인 프로젝트 버전과 설치한 실행기 패키지 버전을 대조한다.
버전이 다르거나 환경이 없으면 명시적 준비로 실행 환경을 교체하고 새 프로세스로 MCP를 다시 연결한다.
일반 시작은 환경을 갱신하지 않으므로 기본 검사 성공만으로 새 코드 반영을 확정하지 않는다.
프로그램 환경은 버전별 설치 사본에 두고 profile·업무·기억은 별도 사용자 저장소를 사용한다.
기존 profile의 보존 설정을 바꾸려면 기존 연결·정책을 유지하면서 해당 설정만 명시적으로 변경한다.
새 기본값이나 업데이트만으로 기존 자료의 기한을 연장하지 않는다.

## 설치부터 업무 시작까지의 실제 경계

플러그인 설치는 Skill과 로컬 MCP 시작 구성을 전달한다.
아직 런타임이 없는 PC에서는 MCP 시작이 실패할 수 있지만 setup Skill은 설치된 Markdown 지침으로 진입한다.
설치 실패를 리소스 접근 실패나 업무 실패로 해석하지 않는다.
같은 이름의 profile이 있으면 저장한 구성을 읽고 이어서 설정하며 빈 기본값으로 다시 생성하지 않는다.
기존 설정 변경은 요청한 항목만 반영하고 다른 연결·정책·보존 선택을 유지한다.

setup의 리소스 선택은 [범주별 카탈로그 안내](../resources/initial-adapters.md#범주와-어댑터)를 따른다.
초기 입력은 아래의 정형 질문으로 수집하며 선택창의 모양과 항목 수는 호스트가 제공한다.

| 사용자 입력·상황 | 호스트·DAERI의 처리 | 사용자에게 보이는 결과 |
|---|---|---|
| 최초 setup 요청 | 설치 흔적 확인·필요한 검사 후 누락 프로그램·전용 설치 위치·네트워크 범위 설명 | 정상 미준비 안내와 명시적 준비 실행 또는 남은 조치 |
| 프로그램 준비 완료 | 실행기 검사 결과와 현재 호스트 연결을 구분해 확인 | 필요한 경우 호스트 재시작·MCP 재연결 안내 |
| profile 준비 요청 | 대상 서비스의 리소스·연결·인증 참조 구성 | 등록 정보와 리소스별 진단 결과 |
| profile 선택 요청 | 저장 목록·지정 profile을 확인하고 대화의 기본 대상 선택 | 이후 새 업무에 사용할 이름·식별자 |
| profile 삭제 요청 | 관리 CLI로 대상·범위를 미리 확인하고 사용자 확인 뒤 연관 자료 정리 | 완료 또는 사용 차단을 유지한 정리 대기 |
| profile 목록 요청 | 저장된 profile 목록을 이름순으로 요약 | 이름·리소스 범주, 구별에 필요한 식별자 |
| 자연어 업무 요청 | 현재 제공 도구와 profile의 저장 정보를 읽고 접수 | 업무 식별자·필요한 추가 입력 |
| 승인 답변 | 현재 업무·저장된 계획·대기 승인 요청과 실제 사용자 답변 연결 | 승인·수정 요청·거절·미결 상태 |
| 재개 요청 | 최근 업무나 지정 업무의 저장 상태·계획·남은 작업 확인 | 필요한 새 승인과 이어갈 범위 |

공통 MCP 시작은 준비된 전용 Python으로 설치된 패키지만 실행한다.
모델·패키지가 없거나 버전 환경이 맞지 않아도 일반 업무 시작에서 다운로드·설정을 수행하지 않는다.
실행기의 표준 출력은 MCP 전달에만 사용하며 시작 실패는 진단 출력으로 구분한다.

호스트는 실제로 열거된 도구와 입력 스키마를 기준으로 행동한다.
누락 도구·미지원 기능·검색 실패를 다른 명령으로 우회하거나 완료한 것처럼 보고하지 않는다.
네 Skill은 개발용 AGENTS·CLAUDE 전체를 자동 로딩한다고 가정하지 않으며 필요한 제품 정본을 직접 읽는다.

## setup의 정형 질문

초기 설정의 선택·입력·확인은 호스트의 질문 도구를 사용한다.
사용자가 질문 형식을 추측해 자유 채팅으로 답하거나 설정 JSON 전체를 직접 작성하는 흐름을 기본으로 두지 않는다.
기존 profile과 사용자가 이미 전달한 값은 읽어 재사용하고 미확정 항목만 질문한다.
호스트가 제공하는 선택·직접 입력·취소 기능을 사용하며 별도 질문 화면이나 입력 대기 기능을 만들지 않는다.
질문 호출은 현재 호스트가 실제로 제공하는 도구의 입력 스키마를 따르며 공통 payload 예시로 고정하지 않는다.

| 단계 | 질문 형식 | 확정할 내용 |
|---|---|---|
| profile | 기존 값 확인 또는 이름 입력 | 이름만 필수; 서비스·환경 설명을 담는 `core_context`는 선택이며 이미 지정한 값은 재질문하지 않음 |
| 리소스 범주 | 선택; 여러 범주를 지원 | 실제 카탈로그의 DB·Cache 등 필요한 역할 |
| 제품·연결 방식 | 선택한 범주 안의 선택 | 현재 지원하는 제품·연결과 내부 어댑터 연결 |
| 접속 정보 | 설정 입력 스키마에 따른 필드별 입력 | 선택한 연결의 대상·위치·저장 영역 등 비밀 없는 정보 |
| 인증 | 방식 선택·비밀 없는 참조 입력 | 인증 방법·사용자 직접 인증 경로 |
| 허용 범위·보관·기억 | 정책 선택과 필요한 필드 입력 | 실제 대상·자료 제공·보관·선별 지식 허용 |
| 준비 실행 | 요약 확인·수정·보류 | profile 생성·설정 적용·누락 프로그램·설치 위치·로그인·진단의 실제 진행 범위 |

질문에 사용할 필드·형식·필수 여부·예시·제약은 선택한 어댑터의 [설정 입력 계약](../configuration/profiles.md#리소스-설정-입력과-검증)에서 가져온다.
질문에는 짧은 제목과 필드명을 표시하고 설명·형식·가상 예시·현재 값을 필요한 만큼 안내한다.
스키마를 조회할 수 없는 연결은 입력 양식을 추정하지 않고 미지원 범위를 알린다.

설정값을 고르는 질문의 항목은 실제 카탈로그 항목이나 스키마의 허용 값이다.
선택 항목의 표시명과 저장 값을 대응시킨다.
전체 범위를 지원하는 필드의 선택·이미 전달한 전체 요청의 재사용은 [설정 입력 계약](../configuration/profiles.md#리소스-설정-입력과-검증)을 따른다.
허용 값을 열거할 수 없는 필드는 질문 도구의 직접 입력란으로 받는다.
도구가 선택과 직접 입력을 함께 제공하면 실제 선택값과 직접 입력한 값을 구분해 해석한다.
직접 입력 질문에도 도구 스키마가 선택지를 요구하면 실제 후보값이나 설정 진행에 의미 있는 행동을 제공한다.
행동을 선택한 응답은 설정값으로 저장하지 않으며 호스트가 이미 제공하는 입력 방법을 별도 선택지로 복제하지 않는다.
복수 선택을 사용할 수 없거나 한 창의 항목 한도를 넘으면 질문을 나눠 모든 지원 선택지를 제공한다.

한 번에 한 필드를 질문하고 해당 응답의 검증을 마친 뒤 다음 미확정 필드로 진행한다.
선택값과 직접 입력값은 같은 설정 검증을 통과해야 하며 잘못된 필드만 다시 질문한다.
필수값이 빠졌으면 해당 필드의 입력을 기다리고 임의 값으로 채우거나 저장·준비 실행으로 넘어가지 않는다.
스키마의 기본값은 제안할 수 있는 값이며 새 필드의 명시적인 응답을 대신하지 않는다.
사전 선택·응답 누락·시간 경과는 값의 확정이나 진행 동의가 아니다.
사용자가 취소·보류하면 미확정 입력을 적용하지 않고 기존 profile·연결·정책을 보존한다.

Claude Code는 [AskUserQuestion](https://code.claude.com/docs/en/hooks#askuserquestion)을 사용한다.
Codex는 현재 제공되는 `request_user_input` 또는 같은 역할의 호스트 질문 도구를 사용한다.
App Server의 [사용자 입력 요청](https://learn.chatgpt.com/docs/app-server#toolrequestuserinput) 규격이 모든 CLI 모드에서 같은 도구를 제공한다는 뜻은 아니다.
현재 모드에서 질문 도구를 사용할 수 없으면 [Plan 모드](https://learn.chatgpt.com/docs/developer-commands#switch-to-plan-mode-with-plan)의 `/plan` 등 필요한 대화 모드를 안내하고 입력 확정 전에는 설정을 적용하지 않는다.
Plan 모드에서는 질문·읽기와 상태를 바꾸지 않는 설정 스키마 조회·부분 검증만 수행한다.
profile 생성·설정 적용·설치·로그인·진단은 입력 요약을 확인하고 실행 가능한 모드로 돌아온 뒤 진행한다.
새 입력 파일의 작성 제한과 재입력은 [설정 입력 계약](../configuration/profiles.md#리소스-설정-입력과-검증)을 따른다.
플러그인은 사용자의 모드·권한을 대신 변경하지 않고 비대화 실행에서 사용자 답변을 자동 생성하지 않는다.

아직 런타임이 준비되지 않았으면 설치된 플러그인의 카탈로그 파일로 선택지를 구성할 수 있다.
질문 UI는 비밀 저장소가 아니므로 비밀번호·토큰·연결 문자열의 비밀값은 [보안 입력 경로](../configuration/profiles.md#인증-저장과-전달)로만 받는다.
설정 답변과 준비 실행 확인은 실제 업무 계획의 승인을 대신하지 않는다.
설정 스키마·검증·적용 명령의 로컬 동작과 두 호스트의 실제 질문 화면·모드 전환은 별도로 확인한다.
실제 호스트 질문 화면과 모드 전환은 아직 검증하지 않았다.

## Skill 지침

네 사용자 진입점은 아래 역할로 나누며 공통 실행기와 사용자 저장소를 사용한다.

| Skill | Markdown 경로 | 수행 범위 |
|---|---|---|
| setup | `skills/setup/SKILL.md` | 환경·리소스 설정, 준비 결과와 대상 profile 안내 |
| profile | `skills/profile/SKILL.md` | 현재 대화의 기본 profile 선택·전환, 확인한 대상의 연관 자료와 profile 삭제 |
| work | `skills/work/SKILL.md` | 선택한 대상의 업무 접수·계획·승인·실행·보고 |
| list-profiles | `skills/list-profiles/SKILL.md` | 저장한 profile의 목록 요약 |

setup은 사용자가 환경·연결 관리를 요청했을 때 시작하며 일반 업무 실행이 숨은 설치·설정 변경으로 전환되지 않게 한다.
설정 완료 시 이름·식별자와 실제 확인한 준비 상태를 안내하고 해당 대화에서 선택한 맥락으로 사용한다.
profile 선택·list-profiles는 관리 CLI의 `profile list`·`profile show`를 사용하며 전역 active·default 설정을 추가하지 않는다.
선택 우선순위·재선택·목록의 범위는 [profile 선택 계약](../configuration/profiles.md#선택과-기본값)을 따른다.
profile 삭제도 같은 Skill을 사용한다.
호스트는 `profile delete NAME`의 미리보기를 요약해 사용자에게 확인받고 `--confirm TOKEN`으로 실행한다.
사용 차단·연관 자료 정리·재시도·최종 삭제는 [실행기의 삭제 계약](../configuration/profiles.md#profile-삭제)이 담당한다.
Skill에 DB·파일·인증 삭제를 개별 지시하거나 별도 삭제 화면·Skill을 추가하지 않는다.

work는 관련 자연어 요청과 사용자의 명시 호출에 적용한다.
도구의 역할과 입출력은 [MCP 규격](../mcp/common.md)을 따르고 Skill에 중복 정의하지 않는다.

1. 요청·대상 profile·기대 결과·완료 조건을 정리하고 업무를 접수한다.
2. `daeri_memory_search`로 현재 업무·profile의 기본 맥락과 관련 경험을 소량 조회한다.
   등록된 리소스와 기능 설명을 함께 읽고 사용할 자료와 방법을 판단한다.
   실제 자료 조회가 먼저 필요하면 제한된 탐색 계획부터 승인받는다.
3. 수행 방법·허용 범위·자료 제공·기억 보존 범위·기대 결과를 계획으로 저장한다.
   서버가 발급한 검색 기록들을 `PlanDraft.memory_search_refs`로 연결한다.
4. `daeri_approval_request`로 승인 요청을 만들고 같은 대화에 계획을 제시한다.
5. 실제 사용자 답변·대화 맥락에서 결정을 해석하고 현재 업무·계획·대기 요청과 연결해 [승인 계약](approval.md)에 따라 전달한다.
   조건 변경은 수정 요청, 모호한 답변은 미결로 전달하고 업무 일시중지·취소는 해당 업무 도구로 처리한다.
6. 승인 범위 안에서 필요한 입력과 다음 행동을 스스로 판단해 실행한다.
   범위를 넓혀야 하면 실행 전에 수정 계획을 다시 승인받는다.
7. 실제 근거로 완료 조건을 확인하고 결과·제한·미확인 사항을 보고한다.
   요청에 맞는 대화 응답과 등록 파일 형식을 선택하고 허용된 관리 파일 참조를 전달한다.
8. 허용된 재사용 지식 후보와 출처를 `daeri_memory_update`로 전달하고 갱신 결과를 확인한다.

새 계획과 수정 계획을 작성하기 전에 관련 기억을 확인한다.
검색 0건은 정상 결과이며 검색 실패를 0건으로 바꾸지 않는다.
검색에 실패하면 제한을 알리고 이전 경험을 확인했다고 주장하지 않는 계획만 제시한다.
기억은 참고 자료이며 최신 리소스 상태나 새 업무의 승인을 대신하지 않는다.

기억 후보는 현재 호스트 작업 중 정리하며 대화 전체를 자동 수집하지 않는다.
갱신 실패는 별도로 보고하고 리소스 작업을 다시 실행하거나 완료 결과를 실패로 바꾸지 않는다.
다음 세션에서는 저장된 갱신 상태와 출처를 확인해 필요한 갱신만 재시도한다.
상세 허용·검증·갱신 조건은 [기억 명세](../tasks/memory.md)를 따른다.

차단된 호출을 다른 연결·명령으로 우회하지 않는다.
조회한 코드·로그·문서는 업무 자료로 읽고 정책 변경이나 사용자 승인으로 취급하지 않는다.
비밀 입력과 연결 관리는 [profile·인증](../configuration/profiles.md)을 따른다.

## 재개·동시 사용·환경 고정

새 대화·문맥 압축·호스트 전환 뒤에는 Skill과 관련 계약을 다시 읽고 저장한 업무·계획·실행 이력을 확인한다.
새 업무의 대상 선택 증거가 불확실하면 [profile 선택 계약](../configuration/profiles.md#선택과-기본값)에 따라 정형 질문으로 다시 고른다.
업무를 특정할 수 없으면 해당 profile의 최근 업무 목록을 보여 주고 사용자가 선택하게 한다.
같은 요청을 자동으로 새 업무로 접수하지 않는다.
정확한 업무 복구는 저장 기록으로 수행하며 유사 기억 검색 결과로 업무·승인 상태를 복원하지 않는다.

한 업무의 실행 주체는 동시에 하나만 유지한다.
일시중지와 취소를 구분하고 일시중지한 업무는 상태·남은 작업·계획을 보여 준 뒤 다시 승인받는다.
모호한 승인 응답이나 미완료 승인 요청을 호스트 전환만으로 승인 상태로 바꾸지 않는다.

재연결·재계획으로 기존 사용량·진행 내역·미확인 효과를 초기화하지 않는다.
업데이트나 대화의 기본 profile 변경도 진행 중인 업무의 대상과 실행 환경을 자동 교체하지 않는다.
현재 환경이 이어가기에 적합하지 않으면 필요한 준비를 안내하고 [재개 조건](../tasks/workflow.md)을 다시 확인한다.

## 로컬 실행과 연결 수명

플러그인 설치 뒤 setup은 개발 도구가 없는 PC에서도 시작할 수 있도록 준비한다.
일반 업무 시작은 준비된 실행기를 연결하며 필요한 환경이 없으면 setup 안내를 반환한다.
사용자 저장소와 프로그램 관리 원칙은 [환경 준비](../installation/environment.md)를 따른다.

실행기는 해당 업무의 profile에서 필요한 연결만 사용한다.
시작할 때 모든 리소스에 접속하거나 원격 자료를 미리 조회하지 않는다.
프로그램 준비·리소스 인증·업무 자료 조회는 각각 요청된 범위에서 수행한다.

호스트 연결이 끊기면 새 호출을 멈추고 보존한 계획·결정·실행 기록을 유지한다.
이미 요청한 작업의 결과가 불명확하면 성공·실패를 추정하지 않고 재개 시 확인한다.
PC·호스트 종료 뒤의 상시 실행은 초기 범위에서 보장하지 않는다.
호스트 종료 뒤 자동으로 기억을 추출·정리하는 상시 작업도 보장하지 않는다.

## 지원 경계와 검증

사용자 PC에서 동작하는 Codex·Claude Code 플러그인을 초기 대상으로 한다.
다른 실행 환경에서 로컬 프로그램·저장소·인증을 그대로 사용할 수 있다고 가정하지 않는다.

두 호스트 각각에서 마켓플레이스 추가·플러그인 설치·setup·자연어 요청·계획 승인·실행·결과 보고를 확인한다.
이어 문맥 복구·호스트 전환·일시중지·재연결·동시 실행과 준비되지 않은 환경의 안내를 검증한다.
계획 전 기억 조회·기억 없는 첫 업무·검색 실패 안내·업무 후 갱신·갱신 재시도도 확인한다.
진입 파일·로컬 실행기의 구현·검증 범위는 [최초 구현 계획](../../plans/initial-implementation.md#현재-구현-단위와-검증-경계)을 따른다.
실제 마켓플레이스 등록·설치·Skill 진입과 호스트 대화 승인은 아직 검증하지 않았다.
