# 계획과 승인 명세

상태: 확정 승인 원칙 + 상세 계약 설계 제안

초기에는 분석·조회도 포함해 수행 방법·허용 범위·예상 결과물을 사람에게 확인받는다.
그 범위 안에서는 자율 실행하며 범위 이탈 전에 수정 계획을 승인받는다.
공개 필드는 [계획 MCP](../mcp/plans.md), 실제 확인·서명 검증은 [호스트 승인](../hosts/approval.md)을 따른다.

## 계획 전 탐색의 경계: 제안

현재 권한과 정책이 허용한 로컬 등록 설명·기능 계약·구조 메타데이터만 먼저 제공한다.
목록 조회가 원격 진단·스키마 탐색을 자동 실행해서는 안 된다.
실제 데이터·로그·코드·메일·티켓 원문과 외부 변경은 계획 승인 후에 실행한다.

원문이나 원격 구조가 있어야 본 계획을 만들 수 있으면 제한된 탐색 계획부터 승인받는다.
샘플 문서로 DB 스키마를 추론하는 것도 실제 데이터 읽기다.
메타데이터와 원격 탐색의 공개 접점은 [리소스 MCP](../mcp/resources.md)가 정의한다.

## 계획에 담을 설명과 실행 조건: 제안

계획은 사람이 읽는 설명과 실행기가 검사할 구조화된 조건을 함께 갖는다.
두 내용은 같은 불변 저장본을 가리키며 사용자는 전체 실행 조건을 확인할 수 있어야 한다.

| 항목 | 표시하고 검사할 내용 |
|---|---|
| 목적·완료 조건 | 해결할 문제, 기대 결과, 조건별 검증 방법·근거 |
| 대상·기능 | profile·구성 개정, 실제 DB·계정·리전·프로젝트, 인스턴스·기능·계약 참조 |
| 방법·단계 | 수행 순서·의존 관계·허용 분기, 읽기·쓰기·부수 효과 |
| 범위 | 기간·필터·필드·키 prefix·ref·경로·변경값 |
| 후속 결과 | 허용 출처·필드·대상 입력·값의 형식·개수·범위 |
| 예산 | 업무 누적 호출·시간·지원되는 자료·변경량 한도 |
| 결과 제공·보관 | 보고·파일 형식, 리소스별 모델 제공·내보내기·보관 필드, 공통 보존기간·마스킹·전달 대상 |
| 실패 처리 | 중단·부분 결과·원격 완료 확인·변경 후 검증 |

표시명만으로 실제 대상을 대신하지 않는다.
비밀값은 계획·화면·모델 입력에 넣지 않고 로컬 인증 참조로 해결한다.
쓰기 권한을 읽기 승인에서 확대하지 않는다.

업무 계획마다 리소스별로 모델·산출물에 제공할 자료, 종료 후 보관할 최소 조회 자료와 마스킹 범위를 승인받는다.
예를 들어 DB는 집계만, GitLab은 승인 경로의 코드 원문을 제공할 수 있다.
[출력 필드](../mcp/plans.md#예산보고완료-조건)로 표현하며 자료의 수명은 [보존 정책](workflow.md#이력과-완료-근거)을 따른다.

강제할 수 없는 조건은 보완을 요구하고 [예산 규격](../mcp/plans.md#예산보고완료-조건)이 허용한 상한 없음은 한계를 표시한다.
숫자 한도를 승인한 뒤 조용히 제거하지 않는다.

### 후속 결과의 바인딩

이전 결과를 입력에 연결할 때 허용 출처·필드와 적용 범위를 계획에 남긴다.
값이 나중에 정해져도 리소스·연산의 경계는 승인 범위 안에 둔다.
실행기는 [바인딩 규격](../mcp/plans.md#결과-바인딩과-조건)에 따라 저장 원본·입력·대상을 대조하며 원문 속 지시를 정책으로 취급하지 않는다.

## 불변 계획과 실제 사용자 승인

확인 전에 계획 원본과 표시본을 보존한다.
수정 시 새 `plan_id`와 증가한 `plan_version`을 만들고 이전 원본을 덮어쓰지 않는다.
대기 중 교체한 계획에 과거 응답을 적용하지 않는다.

[로컬 승인 UI·WebAuthn](../hosts/approval.md)에서 저장한 계획을 표시한다.
검증한 주체·권한·현재 계획·표시본과 응답을 대조하고 보존한 뒤 실행을 허용한다.
모델 인수·채팅·업무 자료의 승인 문구·자동 응답·hook은 승인 증거가 아니다.

승인 기록은 업무·계획·요청·주체·결정·시각·유효 조건을 연결한다.
거절·수정·확인 취소, 기한·중복·응답 검증은 [호스트 승인 계약](../hosts/approval.md#결정별-처리)을 따른다.
이 결정들의 공개 상태·전이는 [승인 MCP](../mcp/plans.md#approvaloutcome과-실제-응답)에 둔다.

## 자율 실행과 재계획의 경계: 제안

매 호출은 저장한 승인과 현재 리소스 권한을 함께 충족해야 한다.
승인이 실제 리소스 권한을 넓히지는 않는다.

| 변화 | 처리 |
|---|---|
| 승인한 기간·필드 안의 필터 축소 | 범위·남은 예산 검사 후 자율 실행 |
| 허용 분기·검증된 후속 결과 사용 | 같은 승인 안에서 자율 실행 |
| 새로운 기능·대상·방법·제공 범위·예산 확대 | 호출 차단 후 수정 계획 승인 |
| 업무 스냅샷 밖의 profile·연결 필요 | 관리 설정 후 새 업무; [구성 변경 경계](../configuration/profiles.md) 적용 |
| 범위 포함 여부를 판단할 수 없음 | 호출 중단 후 조건 확인 |

단순 인수 오류는 기존 범위 안에서 정정할 수 있다.
설치·로그인·연결 등록의 관리 승인은 업무 조회·변경의 승인이 아니다.

## 수정 계획에서 작업과 예산 승계: 제안

새 계획은 이전 계획·완료 호출·승계 근거·미확인 효과를 연결하고 차이를 보여 준다.
불명확한 변경을 완료·취소로 간주하거나 이미 끝난 단계를 불필요하게 반복하지 않는다.

이전 한도·소비·미정산 예약·새 총 한도·남은 예산을 함께 표시한다.
확대와 숫자 상한의 `null` 전환은 제한 완화로 명시해 재승인받는다.
누적량·예약의 승계와 정산은 [예산·재시도 원칙](workflow.md#예산과-재시도)을 따른다.

## 취소·철회·만료와 HITL 완화

확인 요청 취소는 승인 전 요청 중단, 철회·만료는 이미 받은 승인의 사용 중단이다.
어느 경우에도 해당 권한으로 새 호출을 시작하지 않는다.
업무 일시중지·취소·재개와 이미 요청한 작업의 처리는 [업무 흐름](workflow.md#중단재개와-외부-결과-확인)을 따른다.

향후 검증된 범위에 자동 허용 정책을 적용하거나 HITL을 완화할 수 있다.
초기에 정책 엔진을 추가하지 않으며 완화 후에도 계획·정책 결정·권한·범위 검사·이력은 유지한다.
호스트 자체의 도구 권한 확인도 별도로 적용된다.

## 구현 전 확인

실제 UI·서명 검증은 [호스트 검증 범위](../hosts/approval.md#구현-시-검증), 실행·복구는 [최초 구현 계획](../../plans/initial-implementation.md)을 따른다.
실제 호스트·리소스 연동은 아직 검증하지 않았다.
