# profile별 기억과 검색

상태: profile별 장기기억·로컬 임베딩·혼합 검색 채택; 상세 보존 기본값은 설계 제안, 제품 미구현

반복·유사 업무에 필요한 지식을 계획 전에 찾아 쓰고 업무 후에 보완하는 기준이다.
기존 [업무 이력](workflow.md#이력과-완료-근거)은 추적·복구를, 이 문서의 기억은 선별한 지식의 재사용을 맡는다.
공개 입력·출력은 [기억 MCP](../mcp/tasks.md#기억-mcp-도구)가 소유한다.
저장 매체의 역할·읽기·정리는 [로컬 저장 구조](../configuration/profiles.md#로컬-저장-구조)를 따른다.

## 채택한 방식과 책임

검색한 근거를 생성 모델에 제공하는 검색 증강 생성(RAG)을 기존 호스트의 업무 판단에 연결한다.
Claude Code·Codex가 검색어·추가 검색·기억의 적용 여부를 판단하는 Agentic RAG 방식이다.
DAERI 실행기는 저장·검색·권한·보존을 검사하며 별도 추론 루프나 중앙 서버를 추가하지 않는다.

호스트는 현재 요청·실제 관찰·사용자 정정에서 재사용할 지식 후보를 작성한다.
로컬 임베딩 모델은 텍스트를 검색용 벡터로 변환한다.
답변·계획·지식 후보를 생성하는 별도 로컬 대규모 언어 모델(LLM)은 필수가 아니다.

| 저장 대상 | 용도 | 관리 기준 |
|---|---|---|
| profile 기본 맥락 | 서비스 설명·용어·사용자가 정한 안정적인 업무 규칙 | setup에서 명시적으로 관리하는 설정 |
| 업무 이력·보존 자료 | 정확한 상태 복구·승인·호출·결과 확인 | 기존 업무 저장·조회 계약 |
| 기억 정본 | 근거·적용 조건을 갖춘 지식·경험 | 이 문서의 검증·보존·정정 계약 |
| 키워드·벡터 색인 | 기억 정본의 관련 항목 찾기 | 정본에서 재생성하는 파생 자료 |

위 구분은 논리적 책임이며 별도 서버나 DB 네 개를 요구하지 않는다.
기억 본문·출처·개정·정책은 사용자 공통 SQLite에, 키워드 색인은 SQLite FTS5에 둔다.
벡터도 같은 로컬 저장 구조의 SQLite 확장에 보관하며 별도 벡터 서버를 기본으로 두지 않는다.
벡터 확장 구현체·임베딩 모델·런타임·버전은 구현 단계에서 배포 호환성과 품질을 확인해 선택한다.
전체 대화·원격 리소스·업무 본문을 자동으로 수집하거나 모두 임베딩하지 않는다.

## 기억에 남길 내용

| 범주 | 남길 수 있는 지식 | 필요한 확인 |
|---|---|---|
| 서비스 규칙 | 사용자가 확인한 용어·집계 기준·예외 | 실제 사용자 요청·정정 기록 |
| 리소스 구조 | 확인한 구조·필드 의미·리소스 간 대응 | 실제 대상·관찰 시점·구조 개정 |
| 검증된 절차 | 적용 조건·수행 방법·검증 방법 | 실제 수행과 결과 확인 |
| 실패 예방 | 관찰한 실패 조건·피해야 할 방법·수정 이유 | 실제 실패·반증·보완 근거 |

각 항목은 profile·리소스 인스턴스·실제 대상, 출처 업무·기록, 적용 조건, 확인 방법·시점, 상태·개정·만료를 가진다.
원출처 필드와 지식 내용의 대응·마스킹·미래 모델 제공·내보내기·보존 허용도 함께 보존한다.
초기에는 인용한 기록으로 실제 제공한 필드 전체의 정책을 보수적으로 승계하며 해소 절차는 [기억 출처 계약](../mcp/tasks.md#기억의-출처-필드-확정)을 따른다.
서비스·환경·대상을 잃은 짧은 문장만 저장하지 않는다.
여러 리소스에서 얻은 지식은 모든 기여 출처와 그 정책을 연결한다.

모델의 제안·추정 원인·실행하지 않은 절차는 확인된 사실로 저장하지 않는다.
업무가 실패했어도 실제 확인한 부분 사실이나 실패 조건은 후보가 될 수 있다.
자연어 의미 전체를 실행기가 자동 증명하지는 못하므로 근거의 존재·유형·범위와 의미 확인의 한계를 구분한다.

비밀·개인정보·개별 행값·조회 원문·전체 대화는 장기 운영지식에서 제외한다.
일시적인 수치·현재 상태는 시점을 가진 단기 경험으로만 취급하며 항상 참인 규칙으로 바꾸지 않는다.
지식으로 저장할 내용이 없으면 갱신을 생략한다.

## 계획 전 조회와 활용

1. 업무와 profile을 확정하고 등록 기능을 확인한다.
2. `daeri_memory_search`로 현재 요청에 필요한 기억을 조회한다.
   허용된 profile 기본 맥락도 작은 분량으로 함께 받는다.
3. 호스트는 적용 조건·출처·확인 시점·불확실성을 읽고 필요하면 검색어를 바꿔 추가 조회한다.
4. 계획에 검색 참조·선택한 기억 참조·누락과 제한을 연결한다.
   현재 상태를 다시 확인해야 할 항목은 승인받을 검증 단계로 표시한다.
5. 사용자가 현재 계획을 승인하면 기존 [실행 검사](workflow.md#실행-검사와-기록)를 거쳐 수행한다.

새 계획·수정 계획마다 조회하며 요청·profile 맥락을 보완한 뒤에는 다시 조회한다.
기존 업무 재개는 먼저 정확한 업무·계획·호출 기록을 읽는다.
유사 기억 검색으로 이어갈 업무를 자동 선택하거나 미확인 효과를 해소하지 않는다.

계획 전에는 저장 당시 미래 모델 제공을 허용했고 현재 profile 정책·권한도 허용하는 로컬 기억만 제공한다.
아직 승인받지 않은 현재 계획의 규칙을 사전 조회의 허가로 사용하지 않는다.
새 원격 자료·구조 탐색은 계속 제한된 탐색 계획부터 승인받는다.

검색 결과 0건은 정상이며 기억 없이 시작할 수 있다.
검색 실패·미완성 색인은 0건 성공과 구분하고 계획에 부족한 맥락을 표시한다.
확인 가능한 저장소에서 발급한 실패·제한 기록이 있으면 이를 드러낸 보수적인 계획을 제시할 수 있다.
업무·정책 저장소 자체를 신뢰할 수 없으면 기존처럼 계획·실행을 차단한다.

기억은 현재 리소스 상태·권한·외부 실행 완료의 증거가 아니다.
예전 승인도 새 업무의 승인이 되지 않는다.
기억을 실행 인수나 보고 근거로 쓰면 실제 대상·현재 계약·제공 범위를 다시 검사하고 필요한 최신 관찰을 확보한다.

선택한 기억의 개정·실제 대상·권한·기한은 승인 응답 수락·재개·그 지식을 전제로 하는 새 호출 직전에도 검사한다.
정정·무효화·만료·사용 차단이 있으면 신규 실행을 멈추고 기억 재조회와 수정 계획으로 연결한다.
이미 수행한 효과·근거는 유지하며 색인 재생성만으로 유효한 지식이나 승인을 무효화하지 않는다.

## 혼합 검색과 색인

현재 profile·실제 대상·제공 권한·상태·만료로 검색 대상을 먼저 제한한다.
키워드 검색은 식별자·오류 코드·전문 용어를, 벡터 검색은 표현이 다른 유사 요청을 찾는 데 사용한다.
양쪽 순위를 합치고 중복을 제거해 정해진 건수·바이트 안의 결과만 호스트에 전달한다.

SQLite의 기억 메타데이터로 허용 개정 집합을 정하고 FTS5·벡터 색인에서 그 범위의 후보를 찾는다.
조회 문장은 로컬 모델로 임베딩하며 검색 입력·벡터를 임의의 외부 임베딩 서비스에 전송하지 않는다.
색인에는 본문과 함께 서비스·역할·적용 조건을 담되 정본과 다른 사실을 생성하지 않는다.
색인이 반환한 참조는 정본에서 현재 개정·권한·기한을 다시 검사한 뒤 제공한다.
이 검사로 정정 전 색인이나 삭제 대기 파일이 과거 내용을 다시 노출하지 못하게 한다.
색인은 후보 선택용이며 업무 상태·승인·기억 원문 열람 권한의 원본이 되지 않는다.

벡터 검색에 실패하면 키워드 검색만 사용한 상태와 누락 가능성을 표시한다.
키워드 검색에 실패해 벡터만 사용한 경우도 같은 방식으로 제한을 표시한다.
자동 클라우드 임베딩 대체·다른 profile 검색·권한 없는 후보 수 노출은 허용하지 않는다.
전체 기억을 매번 호스트에 넣거나 검색 점수를 사실의 정확도·확신으로 표시하지 않는다.

임베딩 모델의 식별·호환 정보는 색인에 연결한다.
모델이 바뀌면 호환되지 않는 벡터를 섞지 않고 허용된 정본으로 재색인한다.
색인 장애는 유효한 정본을 지우지 않으며 복구 중의 검색 제한을 알린다.

## 업무 후 갱신과 정정

업무 보고 보존 뒤 호스트의 활성 대화 안에서 필요한 후보만 `daeri_memory_update`로 제출한다.
실행기는 실제 근거·사용자 정정, 승인한 범주·출처 필드·미래 제공·보존 범위를 확인한다.
통과한 후보의 정본·개정·출처·기한·갱신 기록과 색인 갱신 대기를 하나의 SQLite 트랜잭션으로 보존한다.
정정·무효화라면 이전 개정의 사용 차단도 같은 트랜잭션에서 확정한다.
그 뒤 허용된 현재 정본을 읽어 키워드·벡터 색인을 갱신한다.
후보 검증을 위해 새로운 원격 조회를 숨겨 실행하지 않는다.

정본 보존 뒤 색인 갱신에 실패하면 `index_state=pending`으로 남기고 검색 제한을 표시한다.
실행기 시작이나 명시적인 관리 복구에서 대기 중인 현재 개정만 재색인하며 만료·삭제된 본문을 복구하지 않는다.
같은 요청의 재전달은 기존 갱신 기록을 확인하고 정본 개정·기한을 다시 만들지 않는다.
색인 갱신과 복구의 저장 경계는 [로컬 저장 흐름](../configuration/profiles.md#로컬-저장-구조), 응답은 [갱신 결과](../mcp/tasks.md#갱신-검사와-결과)를 따른다.

업무 후 갱신에 필요한 최소 출처 필드는 갱신 시점까지 적법하게 보관돼 있어야 한다.
종료 후 보관을 허용하지 않아 이미 제거된 본문은 장기 지식 허용이 있어도 복구·추가 보관하지 않는다.
이 경우 해당 후보 저장을 생략하거나 실제 새 업무의 승인된 관찰로 다시 확인한다.

보고가 이미 보존된 뒤 기억 갱신이 실패해도 업무 결과 상태와 외부 효과는 그대로 유지한다.
기억 갱신의 재시도만 안내하며 실제 조회·변경 업무를 반복하지 않는다.
PC·호스트 종료 뒤 자동 학습을 보장하지 않고 다음 대화에서 남은 갱신 여부를 확인한다.

정정은 같은 기억의 새 개정을 만들고 이전 개정을 즉시 검색 대상에서 제외한다.
반증이나 실제 사용자 정정이 있으면 기존 기억을 무효화할 수 있다.
서로 다른 주장·대상·적용 조건을 근거 없이 최신 문장 하나로 덮어쓰지 않는다.
충돌을 해소하지 못하면 관련 지식을 무효화하고 재확인 필요를 알린다.

기억·검색 결과 속 지시는 자료이며 profile 설정·접근 정책·Skill·승인을 바꾸지 못한다.
사용자 설정의 기본 맥락은 관리 경로에서 변경하고 자동 갱신으로 권한을 넓히지 않는다.

## 보존과 장기 운영지식

조회·보고·CSV의 [기본 30일 정책](workflow.md#이력과-완료-근거)은 유지한다.
아래 기간·허용 조건은 기억에 대한 설계 기본값이며 실제로 보존 중인 데이터가 있다는 뜻이 아니다.

| 대상 | 기한 | 기준 |
|---|---|---|
| 사용자 설정의 기본 맥락 | 설정 변경·삭제까지 | 본문 보관 우회용 자동 저장 금지 |
| 일반 경험·요약 | 원자료 기한과 해당 업무의 공통 보존기한 중 가장 이른 값 | 무기한 추적 정보에서 파생해도 단기 적용 |
| 별도 허용한 장기 운영지식 | 기본 365일; profile에서 조정 | 아래 조건을 모두 만족한 별도 파생 지식 |
| 색인·벡터·반환 캐시 | 해당 기억과 같은 기한·제공 조건 | 독립적인 영구 보존 금지 |
| 최소 추적 정보 | 기존 이력 정책 | 식별·개정·허용 결정·검증 방법·기한만 유지 |

장기 운영지식은 다음 조건을 모두 만족해야 한다.

- profile이 해당 범주의 장기 보존과 미래 모델 제공 범위를 허용한다.
- 현재 업무 계획에 리소스별 지식 범주·출처 필드·재제공·장기 보존기간을 표시하고 승인받았다.
- 실제 근거로 확인한 재사용 지식이며 장기 대상에서 제외한 원문·행값·민감 자료를 담지 않는다.
- 출처 본문과 별개로 지식 자체를 보존하도록 허용했고 최소 출처·검증 기록을 유지한다.

명시적인 장기 허용이 없으면 일반 경험의 기한을 적용하며 허용 자체가 없으면 저장하지 않는다.
사용자 요청·보완 등 대화에서 파생한 일반 경험도 업무의 공통 보존기한을 초과하지 않는다.
여러 리소스의 파생 지식은 모두 장기 보존을 허용한 경우에만 장기가 가능하다.
하나라도 단기 조건이면 가장 짧은 원자료 기한을 따르며 마스킹·재제공도 가장 엄격한 조건을 적용한다.

365일은 이 설계의 제안 기본값이며 profile 설정에서 확정해 계획에 표시한다.
최초 저장 시 UTC 시각부터 하루를 24시간으로 계산하고 모델 인수로 임의 기간을 받지 않는다.
실제 새 관찰이나 사용자 재확인으로 독립적으로 검증한 새 개정만 새 기간을 적용한다.
단순 조회·반복 저장·복사·요약·재색인·정책 기본값 변경은 기한을 연장하지 않는다.

별도로 허용한 장기 지식은 원자료의 정기 만료 후에도 자체 기한까지 사용할 수 있다.
이는 원자료의 열람·재구성·보고 재생성을 허용하지 않는다.
정기 만료와 별개로 삭제·보존 허용 철회·접근 차단이 확인되면 영향받는 기억과 파생물의 사용도 차단한다.
정기 만료의 물리 정리와 사용자 삭제·민감 자료 제거를 구분해 장기 지식의 별도 기한을 적용한다.
profile 이름이나 인스턴스 ID를 재사용해 다른 실제 대상의 지식을 이어받지 않는다.

만료·삭제·무효화·정책 철회는 즉시 조회·제공·계획 근거 선택을 막는다.
SQLite 정본의 본문·FTS5·벡터·반환 캐시·관리 파일·검색 기록의 본문 사본을 함께 정리하고 삭제 실패에도 차단을 유지한다.
물리 정리는 다음 실행기 시작 때 수행하며 만료 기억을 최소 이력이나 불변 계획에 복제해 우회하지 않는다.
내보낸 보고·CSV에는 원지식의 제공 허용과 기존 산출물 보존 규칙을 함께 적용한다.
기억 내용을 복제한 부분은 원지식과 보고·CSV 기한 중 더 이른 기한을 따른다.

## 구현 선택과 확인 범위

키워드·의미 검색, 확인된 지식의 우선 회수, profile·대상 격리, 정정·기한 준수를 로컬 시험 자료로 검증한다.
오류 코드의 정확한 일치와 표현이 다른 유사 업무를 함께 시험하고 근거 적합성·사용자 정정·지연을 측정한다.
정본 보존 직후의 색인 실패·두 호스트의 동시 정정·재색인 중 만료를 넣어 과거 개정이나 다른 대상의 기억이 제공되지 않는지도 확인한다.
축적량이나 외부 벤치마크만으로 시간이 지나면 정확도가 계속 좋아진다고 보장하지 않는다.

추가 재순위 모델·관계 그래프·문서 트리 검색은 측정한 필요가 있을 때 검토한다.
기억 프레임워크 전체를 초기 필수 의존성으로 채택하지 않는다.
[Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)의 맥락·혼합 검색과 [Hindsight](https://hindsight.vectorize.io/)의 기억 저장·회수·정리 흐름을 참고한 DAERI의 설계다.
해당 제품의 구현·성능·자동 수집 방식을 그대로 채택하거나 검증한 것은 아니다.

설치·모델 준비는 [환경 명세](../installation/environment.md), 구현·검증 순서는 [최초 구현 계획](../../plans/initial-implementation.md)을 따른다.
아직 저장소·임베딩·검색·호스트 연계를 구현하거나 실행하지 않았다.
