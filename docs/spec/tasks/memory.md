# profile별 기억과 검색

상태: profile별 선별 기억·선택형 임베딩·혼합 검색과 업무 후 갱신 구현; 실제 회사 API 호환·접속은 별도 검증

반복·유사 업무에 필요한 지식을 계획 전에 찾아 쓰고 업무 후에 보완하는 기준이다.
기존 [업무 이력](workflow.md#이력과-완료-근거)은 추적·복구를, 이 문서의 기억은 선별한 지식의 재사용을 맡는다.
공개 입력·출력은 [기억 MCP](../mcp/tasks.md#기억-mcp-도구)가 소유한다.
저장 매체의 역할·읽기·정리는 [로컬 저장 구조](../configuration/profiles.md#로컬-저장-구조)를 따른다.

## 채택한 방식과 책임

검색한 근거를 생성 모델에 제공하는 검색 증강 생성(RAG)을 기존 호스트의 업무 판단에 연결한다.
Claude Code·Codex가 검색어·추가 검색·기억의 적용 여부를 판단하는 Agentic RAG 방식이다.
DAERI 실행기는 사용자 PC에서 저장·검색·권한·보존을 검사한다.

호스트는 현재 요청·실제 관찰·사용자 정정에서 재사용할 지식 후보를 작성한다.
선택한 임베딩 제공자는 허용 텍스트를 검색용 벡터로 변환한다.
답변·계획·지식 후보 생성은 호스트 모델이 담당한다.

| 저장 대상 | 용도 | 관리 기준 |
|---|---|---|
| profile 기본 맥락 | 서비스 설명·용어·사용자가 정한 안정적인 업무 규칙 | profile 관리 경로에서 입력한 설정 |
| 업무 이력·보존 자료 | 정확한 상태 복구·승인·호출·결과 확인 | 기존 업무 저장·조회 계약 |
| 기억 정본 | 근거·적용 조건을 갖춘 지식·경험 | 이 문서의 검증·보존·정정 계약 |
| 키워드·벡터 색인 | 기억 정본의 관련 항목 찾기 | 정본에서 재생성하는 파생 자료 |

위 구분은 같은 로컬 저장 구조 안의 논리적 책임이다.
기억 본문·출처·개정·정책은 사용자 공통 SQLite에, 키워드 색인은 SQLite FTS5에 둔다.
벡터는 같은 로컬 저장 구조의 SQLite 확장에 보관한다.
임베딩은 profile별로 로컬 다국어 모델·회사 API·키워드 전용 중에서 선택한다.
기존 profile에 선택이 없으면 로컬 제공자를 해소하며 패키지·모델은 관리 준비 경로에서 설치한다.
구현 의존성과 잠금 버전은 [개발 의존성](../../development/dependencies.md)에서 관리한다.
검색·임베딩 입력은 아래 기준으로 선별·검증한 기억 정본과 현재 검색 질의다.

## 기억에 남길 내용

| 범주 | 남길 수 있는 지식 | 필요한 확인 |
|---|---|---|
| 서비스 규칙 | 사용자가 확인한 용어·집계 기준·예외 | 실제 사용자 요청·정정 기록 |
| 리소스 구조 | 확인한 구조·필드 의미·리소스 간 대응 | 실제 대상·관찰 시점·구조 개정 |
| 검증된 절차 | 적용 조건·수행 방법·검증 방법 | 실제 수행과 결과 확인 |
| 실패 예방 | 관찰한 실패 조건·피해야 할 방법·수정 이유 | 실제 실패·반증·보완 근거 |

각 항목은 profile·리소스 인스턴스·실제 대상, 출처 업무·기록, 적용 조건, 확인 방법·시점, 상태·개정·보존기한을 가진다.
원출처 필드와 지식 내용의 대응·마스킹·미래 모델 제공·내보내기·보존 허용도 함께 보존한다.
초기에는 인용한 기록으로 실제 제공한 필드 전체의 정책을 보수적으로 승계하며 해소 절차는 [기억 출처 계약](../mcp/tasks.md#기억의-출처-필드-확정)을 따른다.
저장 후보는 서비스·환경·실제 대상과 적용 조건을 갖춰야 한다.
여러 리소스에서 얻은 지식은 모든 기여 출처와 그 정책을 연결한다.

확인된 지식은 실제 관찰·사용자 확인을 출처로 가지며 제안·가설·미실행 절차는 추가 확인 대상으로 구분한다.
업무가 실패했어도 실제 확인한 부분 사실이나 실패 조건은 후보가 될 수 있다.
실행기는 근거의 존재·유형·범위를 검사하고 호스트는 그 근거와 지식 문장의 의미를 대조한다.

장기 운영지식의 허용 본문은 비밀·개인정보·개별 행값·조회 원문·전체 대화를 제거한 재사용 규칙·구조·검증 절차·실패 조건이다.
호스트는 출처에서 이 내용을 선별·정제하고 해당 본문 기준과 근거의 의미가 일치하는지 확인한다.
실행기는 등록 범주·출처 필드·권한·알려진 비밀 패턴을 검사한다.
일시적인 수치·현재 상태는 관찰 시점과 적용 조건을 가진 경험으로 관리한다.
지식으로 저장할 내용이 없으면 갱신을 생략한다.

## 계획 전 조회와 활용

1. 업무와 profile을 확정하고 등록 기능을 확인한다.
2. `daeri_memory_search`로 현재 요청에 필요한 기억을 조회한다.
   허용된 profile 기본 맥락도 작은 분량으로 함께 받는다.
3. 호스트는 적용 조건·출처·확인 시점·불확실성을 읽고 필요하면 검색어를 바꿔 추가 조회한다.
4. 계획에 검색 참조·선택한 기억 참조·누락과 제한을 연결한다.
   현재 상태를 다시 확인해야 할 항목은 승인받을 검증 단계로 표시한다.
5. 사용자가 현재 계획을 승인하면 기존 [실행 검사](workflow.md#실행-검사와-기록)를 거쳐 수행한다.

새 계획·수정 계획마다 조회하며 요청·profile 맥락을 보완한 뒤에는 다시 조회한다.
기존 업무 재개는 먼저 정확한 업무·계획·호출 기록을 읽는다.
이어갈 업무는 최근 목록에서 사용자가 선택하고 미확인 효과는 원 호출의 실행·확인 기록으로 해소한다.

계획 전에는 저장 당시 미래 모델 제공을 허용했고 현재 profile 정책·권한도 허용하는 로컬 기억만 제공한다.
사전 조회의 권한은 이미 저장된 제공 허용과 현재 profile 정책에서 해소한다.
새 원격 자료·구조 탐색은 계속 제한된 탐색 계획부터 승인받는다.

검색 결과 0건은 정상이며 기억 없이 시작할 수 있다.
검색 실패·미완성 색인은 0건 성공과 구분하고 계획에 부족한 맥락을 표시한다.
확인 가능한 저장소에서 발급한 실패·제한 기록이 있으면 이를 드러낸 보수적인 계획을 제시할 수 있다.
업무·정책 저장소 자체를 신뢰할 수 없으면 기존처럼 계획·실행을 차단한다.

현재 리소스 상태·권한·외부 실행 완료는 해당 업무의 최신 관찰·검사로 확인한다.
실행 승인은 현재 업무·계획의 실제 응답으로 해소한다.
기억을 실행 인수나 보고 근거로 쓰면 실제 대상·현재 계약·제공 범위를 다시 검사하고 필요한 최신 관찰을 확보한다.

선택한 기억의 개정·실제 대상·권한·기한은 승인 응답 수락·재개·그 지식을 전제로 하는 새 호출 직전에도 검사한다.
정정·무효화·만료·사용 차단이 있으면 신규 실행을 멈추고 기억 재조회와 수정 계획으로 연결한다.
이미 수행한 효과·근거는 유지한다.
색인 재생성은 검색용 파생 자료를 갱신하고 지식·승인의 유효성은 정본 상태로 판정한다.

## 혼합 검색과 색인

현재 profile·실제 대상·제공 권한·상태·만료로 검색 대상을 먼저 제한한다.
키워드 검색은 식별자·오류 코드·전문 용어를, 벡터 검색은 표현이 다른 유사 요청을 찾는 데 사용한다.
양쪽 순위를 합치고 중복을 제거해 정해진 건수·바이트 안의 결과만 호스트에 전달한다.

SQLite의 기억 메타데이터로 허용 개정 집합을 정하고 FTS5·벡터 색인에서 그 범위의 후보를 찾는다.
조회 문장은 해당 profile의 선택한 제공자로 임베딩한다.
회사 API는 명시한 전송 허용과 현재 기억 권한을 검사한 뒤 등록한 endpoint에만 필요한 텍스트를 전송한다.
색인용 텍스트는 정본의 기억 범주·지식 문장·적용 조건에서 구성한다.
색인이 반환한 참조는 정본에서 현재 개정·권한·기한을 다시 검사한 뒤 제공한다.
질의 임베딩은 DB 쓰기 잠금 밖에서 계산하고 검색 결과를 제공하기 전에 현재 업무·profile·기억을 다시 확인한다.
정정 전 색인·삭제 대기 파일이 있더라도 제공 여부는 현재 정본의 개정·상태·정책으로 결정한다.

벡터 검색에 실패하면 키워드 검색만 사용한 상태와 누락 가능성을 표시한다.
키워드 검색에 실패해 벡터만 사용한 경우도 같은 방식으로 제한을 표시한다.
응답은 선택한 profile에서 현재 제공이 허용된 후보·건수·제한을 담는다.
검색 점수는 관련도 순위 계산에 사용하고 사실의 확인 상태는 출처·검증 기록으로 표시한다.

임베딩 제공자·모델의 식별·호환 정보와 차원은 색인에 연결한다.
제공자·API 주소·모델·차원이 바뀌면 호환되지 않는 벡터를 검색에서 제외한다.
재색인은 명시적인 관리 경로에서 허용된 현재 정본을 읽어 수행한다.
색인 장애 시 정본은 유지하고 복구 중 검색 제한을 알린다.

### 임베딩 API 계약

회사 정책으로 모델을 설치할 수 없으면 profile의 [임베딩 설정](../configuration/profiles.md#임베딩-제공자-선택)을 `openai_compatible`로 선택한다.
현재는 HTTPS endpoint로 OpenAI 호환 embeddings 요청을 보내는 어댑터를 제공한다.
다른 요청·인증·응답 규격은 해당 계약을 구현한 어댑터와 호환성 검증으로 추가한다.

| 경계 | 처리 |
|---|---|
| 인증 | 설정한 참조를 로컬에서 해소해 Bearer 인증으로 전달; 공개 기록은 비밀 없는 인증 참조·준비 상태로 구성 |
| 요청 | `model`·`input`·`encoding_format: float`; `dimensions`를 설정한 경우만 함께 전달 |
| 입력 | 검색 질의 또는 허용 기억의 색인용 텍스트 하나; UTF-8 최대 64KiB |
| 응답 | 최대 1MiB; `data` 한 항목·`index: 0`·1~8192차원의 유한 숫자 벡터 검사, 영벡터 거부 |
| 전송 | 명시한 HTTPS 주소·인증서 검사·네트워크 단계별 시간 제한 적용; 지정 주소로 한 번 요청하며 실패는 검색 제한으로 반환 |
| 보관 | 기억 정본·벡터는 기존 로컬 SQLite에 유지; API 응답의 벡터를 해당 정본의 파생 색인으로 연결 |

요청·응답의 기준은 [공식 embeddings API](https://developers.openai.com/api/reference/resources/embeddings/methods/create)이며 이 규격을 회사 API에 적용한 선택이다.
회사의 실제 주소·모델 또는 배포 이름·인증 방식·지원 차원은 사용자가 확인하고 회사 환경에서 진단해야 한다.
API 서버의 자체 보관·감사 정책은 회사가 확인·관리한다.
모델 호환성은 설정·응답 식별자로 검사하므로 식별자가 유지된 서버 내부 교체는 회사의 변경 통지·재진단으로 확인한다.
회사의 모델 변경 안내를 받으면 설정·배포 식별을 확인하고 유효 정본을 명시적으로 재색인한다.

`allow_remote`는 호스트 모델 제공과 별도로 지정한 API로 기억·검색 질의를 전송하는 허용이다.
이 값이 참이어도 현재 profile·리소스·실제 대상·기억 범주·출처·기한·미래 모델 제공 조건을 통과한 기억만 색인에 사용한다.
검색 질의를 보내기 전에도 현재 업무·profile 접근과 기억 제공 허용을 확인한다.
제공 가능한 기억이 있을 때 검색 질의를 임베딩 API에 보낸다.
전송을 시작하기 직전에 현재 profile의 선택과 전송 허용을 다시 확인하고 계산 뒤 결과 발행 전에도 재검사한다.
권한 철회가 확인되면 이후 새 전송·결과 발행을 차단한다.
이미 전송한 텍스트의 원격 처리는 해당 API의 정책을 따른다.

API 요청은 텍스트 하나씩 처리하며 재색인은 현재 허용한 기억마다 벡터를 다시 생성한다.
임베딩 호출은 운영 리소스 기능 실행이 아니므로 업무의 리소스 호출 예산과 구분한다.
API 토큰·과금 관리는 현재 제공자 정책과 조직의 사용량 관리가 담당한다.

`keyword_only`는 FTS5 키워드 검색을 사용한다.
키워드 색인이 완성되면 `index_state=ready`로 기록한다.
명시적인 키워드 전용 선택에서 검색이 정상 완료되고 제한이 없으면 결과 0건을 포함해 `status=ok`다.
벡터 제공자의 장애로 키워드만 사용했거나 색인 누락이 있으면 `status=partial`과 제한을 반환한다.
API 장애·인증 누락·전송 미허용·색인 미준비도 사용 가능한 키워드 결과와 검색 제한을 반환한다.
제공자 변경·추론 패키지 설치는 사용자가 선택한 관리 경로에서 수행한다.

## 업무 후 갱신과 정정

업무 보고 보존 뒤 호스트의 활성 대화 안에서 필요한 후보만 `daeri_memory_update`로 제출한다.
실행기는 실제 근거·사용자 정정, 승인한 범주·출처 필드·미래 제공·보존 범위를 확인한다.
통과한 후보의 정본·개정·출처·기한·갱신 기록과 색인 갱신 대기를 하나의 SQLite 트랜잭션으로 보존한다.
정정·무효화라면 이전 개정의 사용 차단도 같은 트랜잭션에서 확정한다.
그 뒤 허용된 현재 정본을 읽어 키워드·벡터 색인을 갱신한다.
색인용 임베딩도 정본·갱신 기록의 트랜잭션을 확정한 뒤 계산한다.
계산 뒤 현재 개정·허용을 재검사하고 일치하는 벡터를 발행하며 응답도 현재 상태를 반영한다.
새 관찰이 필요한 후보는 승인받은 업무의 조회로 확인한다.

첫 구현은 같은 실행 소유자가 보고를 보존한 종료 업무에서 새 지식을 저장한다.
사용자가 실제 승인한 현재 계획의 기억 범위와 profile의 상한을 모두 적용한다.
보고·파일을 출처로 지정하면 실제 호출·사용자 확인까지 출처를 해소한다.
실제 근거의 유형·연결·현재 제공 조건이 확인돼야 후보 검증을 통과한다.

조회에서 모델에 제공한 필드 전체가 기억 출처·현재 제공·보관 허용을 충족해야 한다.
검사 범위는 실제 제공한 전체 필드로 결정한다.
사용자 요청·보완은 리소스별로 별도 허용한 확인 자료일 때만 사용한다.
저장 후보에 알려진 비밀 문자열 패턴이 있으면 저장을 거부한다.

무효화는 새 지식 저장 권한이 없는 업무에서도 실제 사용자 정정·반증으로 처리할 수 있다.
반증은 같은 실제 대상의 출처로 확인한다.
무효화는 현재 소유권과 실제 정정·반증을 확인한 활성·종료 업무에서 처리한다.
갱신 확인 기록은 개정·출처 참조·처리 상태를 담고 후보 본문은 기억 정본에서 관리한다.

정본 보존 뒤 색인 갱신에 실패하면 `index_state=pending`으로 남기고 검색 제한을 표시한다.
명시적인 관리 복구는 현재 유효한 개정의 대기 색인을 다시 만든다.
같은 요청의 재전달은 기존 갱신 기록과 그 개정·기한을 반환한다.
색인 갱신과 복구의 저장 경계는 [로컬 저장 흐름](../configuration/profiles.md#로컬-저장-구조), 응답은 [갱신 결과](../mcp/tasks.md#갱신-검사와-결과)를 따른다.

업무 후 갱신에 필요한 최소 출처 필드는 갱신 시점까지 적법하게 보관돼 있어야 한다.
필요한 본문이 이미 정리됐으면 해당 후보 저장을 생략하거나 새 업무의 승인된 관찰로 다시 확인한다.

보고가 이미 보존된 뒤 기억 갱신이 실패해도 업무 결과 상태와 외부 효과는 그대로 유지한다.
기억 갱신의 재시도를 안내하고 실제 업무의 완료 상태·호출 이력을 유지한다.
대화가 종료되면 다음 대화에서 남은 갱신 여부를 확인한다.

정정은 같은 기억의 새 개정을 만들고 이전 개정을 즉시 검색 대상에서 제외한다.
반증이나 실제 사용자 정정이 있으면 기존 기억을 무효화할 수 있다.
서로 다른 주장·대상·적용 조건은 각각의 출처·개정으로 추적한다.
충돌을 해소하지 못하면 관련 지식을 무효화하고 재확인 필요를 알린다.

기억·검색 결과는 적용 여부를 판단할 자료다.
profile 설정·기본 맥락·접근 정책은 관리 경로, 승인은 실제 사용자 응답 경로에서 변경한다.

## 보존과 장기 운영지식

업무 본문·조회 자료·보고·산출물에는 [profile의 업무 보존 정책](workflow.md#이력과-완료-근거)을 적용한다.
장기 축적의 대상은 근거와 허용 조건을 갖춘 선별 지식이다.

| 대상 | 기한 | 기준 |
|---|---|---|
| 사용자 설정의 기본 맥락 | 설정 변경·삭제까지 | 사용자가 관리 입력으로 등록한 맥락·규칙 |
| 일반 경험·요약 (`source_bound`) | 기여 출처·업무의 가장 이른 유한 기한; 모두 없으면 무기한 | 선별한 지식의 저장 허용은 별도 검사 |
| 별도 허용한 장기 운영지식 | 새 profile의 기본은 무기한; 양의 정수로 유한 기간 설정 가능 | 아래 조건을 모두 만족한 별도 파생 지식 |
| 색인·벡터·반환 캐시 | 해당 기억과 같은 기한·제공 조건 | 기억 정본의 기한·현재 제공 조건 승계 |
| 최소 추적 정보 | 기존 이력 정책 | 식별·개정·허용 결정·검증 방법·기한만 유지 |

장기 운영지식은 다음 조건을 모두 만족해야 한다.

- profile이 해당 범주의 장기 보존과 미래 모델 제공 범위를 허용한다.
- 현재 업무 계획에 리소스별 지식 범주·출처 필드·재제공·장기 보존기간 또는 무기한 여부를 표시하고 승인받았다.
- 실제 근거로 확인한 지식이며 위 [장기 운영지식의 허용 본문](#기억에-남길-내용) 기준을 충족한다.
- 출처 본문과 별개로 지식 자체를 보존하도록 허용했고 최소 출처·검증 기록을 유지한다.

저장 허용을 먼저 검사하고 보존 유형에 따라 일반 경험 또는 장기 지식의 기한을 적용한다.
사용자 요청·보완에서 파생한 일반 경험도 업무·기여 출처의 기한을 승계한다.
모든 출처와 업무가 무기한이면 `source_bound` 기억도 무기한으로 해소한다.
여러 리소스의 파생 지식을 `long_term` 유형으로 저장하려면 모든 기여 출처가 독립적인 장기 지식 보존을 허용해야 한다.
하나라도 출처 기한을 승계해야 하면 업무·모든 기여 출처의 유한 기한 중 가장 이른 값을 따른다.
마스킹·재제공도 가장 엄격한 조건을 적용한다.

새 profile의 `long_term_memory_days` 기본값 null은 별도 허용한 장기 지식의 무기한 보존을 뜻한다.
양의 정수를 설정하면 최초 저장의 UTC 시각부터 하루를 24시간으로 계산한 유한 기한을 적용한다.
저장·정정 시 실행기가 profile·계획·출처에서 기간을 해소한다.
기존 profile의 명시적 기간과 기억의 확정 기한은 그대로 유지한다.

실제 새 관찰이나 사용자 재확인으로 독립적으로 검증한 새 개정만 새 기간을 해소한다.
동일 출처의 재저장·문장 정정·복사·요약·재색인·정책 기본값 변경·조회·재사용은 기존 기한을 승계한다.

검색·제공은 정본의 활성 상태와 현재 권한을 먼저 확인하고, 유한 기한이 있으면 만료 여부도 검사한다.
`expires_at=null`은 시간 제한이 없다는 뜻일 수 있지만 무효화 결과에서도 쓰므로 상태와 함께 판정한다.
무기한 지식도 적용 전에 현재 상태·구조·권한에 필요한 최신 관찰을 확보한다.

별도로 허용한 장기 지식은 원자료의 정기 만료 후에도 자체 보존 조건 안에서 사용할 수 있다.
원자료 열람·보고 재생성은 해당 자료의 현재 제공·보존 조건으로 별도 검사한다.
무기한 여부와 관계없이 권한 철회·원출처 명시 삭제·정정·실제 대상 변경·보존 허용 취소가 확인되면 영향받는 기억과 파생물의 사용을 즉시 차단한다.
무효화·본문 정리한 지식의 새 저장에는 독립적으로 확인한 새 자료를 요구한다.
출처 목록의 일부만 제출하거나 재조합해도 개별 출처의 연결과 차단 상태를 검사한다.
기존 출처만 다시 사용하면 기존 유한 기한을 유지한다.
새 기간·복원에는 최초 저장·명시 차단·만료의 해당 기준 시점 이후 독립적으로 확인한 새 출처가 필요하다.
새 출처의 기준 시각은 논리적인 만료·차단 시각으로 고정한다.
정기 만료의 물리 정리는 이러한 삭제·차단과 구분한다.
기억의 연결은 profile·인스턴스 ID와 실제 대상 식별자를 함께 대조한다.

만료·삭제·무효화·정책 철회는 즉시 조회·제공·계획 근거 선택을 막는다.
SQLite 정본의 본문·FTS5·벡터·반환 캐시·관리 파일·검색 기록의 본문 사본을 함께 정리하고 삭제 실패에도 차단을 유지한다.
물리 정리는 다음 실행기 시작 때 수행한다.
최소 이력·불변 계획의 본문 사본도 원지식의 기한·차단 상태를 승계한다.
내보낸 보고·CSV에는 원지식의 제공 허용과 기존 산출물 보존 규칙을 함께 적용한다.
기억 내용을 복제한 부분은 업무·원지식·다른 기여 출처의 가장 이른 유한 기한을 승계하며 모두 무기한일 때만 null을 사용한다.
기존 보고·파일의 확정 유한 기한은 지식 인용 뒤에도 유지한다.

## 구현 선택과 확인 범위

### 첫 버전의 실제 처리

공개 동작은 위 [조회·활용](#계획-전-조회와-활용)과 [갱신·정정](#업무-후-갱신과-정정), 기한·차단은 [보존 기준](#보존과-장기-운영지식)을 따른다.
이 절은 그 계약의 구체적인 검색·내보내기 처리와 구현 한도를 정의한다.

기억 본문 제공에는 현재 공통 정책과 리소스별 실제 대상·범주·출처 필드·마스킹의 일치가 필요하다.
사용자가 관리 입력으로 등록한 기본 맥락도 계획 전 검색에서 함께 제공한다.

모델에 제공할 수 있는 기억과 파일로 내보낼 수 있는 기억을 구분한다.
최초 갱신 때 기여 필드 전체의 내보내기를 확인한 증명이 없으면 모델 전용 지식으로 보존한다.
파일 제공은 이 증명과 저장 당시의 허용, 현재 공통 설정·리소스별 내보내기 범위·마스킹을 모두 충족해야 한다.
원문이 정기 만료됐어도 보존한 필드·대상·허용 증명으로 검사하며 불명확하면 내보내기를 거부한다.
과거 업무 참조는 기억의 출처 설명으로 유지하고 현재 업무는 해당 기억의 유효성·제공 증명을 검사한다.

검색은 현재 profile·실제 대상·정책·기한을 통과한 정본에서 후보를 찾는다.
FTS5 키워드 순위와 로컬에 보관한 벡터의 코사인 거리 순위를 RRF(각 검색 순위를 결합하는 방식)로 합친다.
제공 전 현재 개정·허용을 다시 검사하고 확인 상태는 출처·검증 기록으로 반환한다.
검색 결과는 기본 10건, 최대 50건·본문 합계 64KiB 안으로 제한한다.

현재 검색은 profile의 본문이 있는 활성·미만료 개정을 참조 순으로 최대 10,000개 읽고 현재 정책·대상으로 제한한다.
이 상한을 넘으면 일부 항목 미검색을 `limitations`에 표시한다.
검색어는 UTF-8 4KiB까지 받으며 비밀 제거 뒤 단어를 최대 64개 추출해 OR 키워드 질의로 구성한다.
각 검색에서 요청 건수의 최대 4배 후보를 읽고 순위마다 `1 / (60 + 순위)`를 합산한다.
점수가 같으면 기억 참조 순으로 정렬하고 최종 건수·본문 바이트 상한을 적용한다.

로컬 제공자는 명시적인 패키지·모델 준비 뒤 이미 준비된 파일만 읽는다.
색인의 로컬 모델 식별자는 모델·토크나이저 관련 캐시 파일 바이트의 지문을 포함한다.
이 지문은 변경된 파일의 벡터 혼용을 막는 비교값이며 배포자가 제공한 고정 해시와의 진위 검증은 별도 확장 범위다.
회사 API 제공자는 위 [전송 계약](#임베딩-api-계약)에 따라 검색·색인에서 API를 사용한다.
키워드 전용은 FTS5 결과와 `retrieval_state=keyword_only`를 반환한다.
키워드 검색은 `unicode61` 토큰 단위를 사용한다.
표기·띄어쓰기가 다른 한국어 지식의 회수 품질은 벡터 검색과 함께 평가한다.

벡터 검색을 선택한 경우 정본 저장 뒤 벡터 색인이 준비되지 않았거나 갱신에 실패하면 `index_state=pending`으로 보고한다.
정본과 `pending` 상태를 유지하고 명시적인 재색인에서 현재 허용 개정을 처리한다.
벡터 검색은 현재 모델·토크나이저 식별과 호환되는 벡터를 사용한다.
모델 입력 한도를 넘는 후보는 제한 상태로 남기고 원래 본문을 유지한다.

### 실제 확인과 남은 경계

로컬 SQLite 시험으로 profile 격리, 정책 철회·실제 대상 변경, 정정·무효화·만료, 가장 이른 기한과 반복 저장의 기한 고정을 확인했다.
실제 SQLite 벡터 확장으로 코사인 거리·혼합 순위·모델 변경 후 재색인도 확인했다.
별도로 준비한 실제 다국어 모델을 DNS 차단 상태로 다시 읽어 한국어 요청에서 관련 영문 지식을 검색했다.
두 하위 MCP 프로세스를 실제 호출해 승인 → 결과 비교·표·CSV 보고 → 출처 해소·기억 갱신 → 다음 업무의 기억 조회까지 확인했다.
기억을 선택한 새 계획에서도 과거 승인으로 실행할 수 없으며 새 사용자 승인이 필요함을 확인했다.
원 업무의 보존기한을 만료·정리한 뒤 별도 장기 지식을 회수하고 원문 열람이 차단되는 경계도 확인했다.
이 확인의 범위는 소수 시험 문장의 기능 동작이다.
실운영 정확도·장기간 누적 품질·Windows 실행은 별도 검증 대상이다.

회사 API 경로는 실제 HTTP 어댑터에 모의 응답을 연결해 색인·검색·장애 시 키워드 제한·모델 변경·재색인과 전송 직전 권한 철회를 확인했다.
실제 회사 네트워크·인증·API 배포 호환성은 별도 검증 대상이다.

키워드·의미 검색, 확인된 지식의 우선 회수, profile·대상 격리, 정정·기한 준수를 로컬 시험 자료로 검증한다.
오류 코드의 정확한 일치와 표현이 다른 유사 업무를 함께 시험하고 근거 적합성·사용자 정정·지연을 측정한다.
정본 보존 직후 색인 실패·두 호스트의 동시 정정·재색인 중 만료에서 현재 개정·실제 대상·제공 권한 검사가 유지되는지도 확인한다.
장기간 품질은 근거 적합성·사용자 정정·지연의 실제 측정으로 평가한다.

추가 재순위 모델·관계 그래프·문서 트리 검색은 측정한 필요가 있을 때 검토한다.
현재 구현은 선택한 검색·저장 기능과 해당 의존성으로 구성한다.
[Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)의 맥락·혼합 검색과 [Hindsight](https://hindsight.vectorize.io/)의 기억 저장·회수·정리 흐름을 참고한 DAERI의 설계다.
참고 자료의 사실과 DAERI가 실제 구현·검증한 범위는 위 구현·확인 절에서 구분한다.

설치·모델 준비는 [환경 명세](../installation/environment.md), 구현·검증 순서는 [최초 구현 계획](../../plans/initial-implementation.md)을 따른다.
현재 업무·승인·호스트와의 통합 완료 범위는 최초 구현 계획에서 확인한다.

로컬 실행에는 [FastEmbed의 CPU ONNX 방식](https://github.com/qdrant/fastembed), 벡터 연산에는 [sqlite-vec의 Python 연결](https://alexgarcia.xyz/sqlite-vec/python.html)을 사용한다.
모델 품질의 배경은 [다국어 E5 기술 보고서](https://arxiv.org/abs/2402.05672)를 참고하되 DAERI 운영 품질은 위 실제 검증 경계로 평가한다.
