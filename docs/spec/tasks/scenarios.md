## 실패 주문 원인 분석

“지난주 실패 주문 원인을 분석해줘.”라는 요청을 받는다.
계획에는 승인받을 PostgreSQL의 기간·필드·조회량을 제시한다.
GitLab의 프로젝트·commit·경로 분석도 제시한다.

원인별 집계와 코드 근거 보고서를 예상 결과로 설명한다.
승인 전에 실제 주문이나 코드 원문을 읽지 않는다.

## 승인 범위 안의 후속 집계

결과를 보고 승인한 기간 안에서 원인별 후속 집계가 필요해진다.
승인된 방법·대상·총량 안에서 후속 조회를 자율 실행한다.
개별 조회마다 DAERI 승인을 새로 요구하지 않는다.

## 새 리소스가 필요한 경우

AWS 인스턴스 상태도 확인해야 한다는 가설이 나온다.
기존 계획에 AWS가 없으면 호출을 차단한다.
계정·리전·기능·목적을 추가한 수정 계획을 제시한다.

## 사용자 확인 기능 오류

호스트의 사용자 확인 기능이 동작하지 않으면 승인 대기로 남긴다.
확인 경로의 오류를 설명한다.
모델의 추정 승인을 대신 쓰지 않는다.

## 누락 또는 결과 한도 도달

일부 기간의 데이터가 누락되거나 결과 한도에 걸린다.
확보한 근거와 제외 범위를 표시하고 부분 결과로 보고한다.
필요한 범위 확장은 새 계획으로 확인받는다.

## 변경 성공 여부가 불명확한 경우

변경 요청이 타임아웃되어 성공 여부를 알 수 없으면 외부 상태부터 확인한다.
중복 방지 근거가 없으면 즉시 같은 변경을 반복하지 않는다.
