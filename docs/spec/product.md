# DAERI 제품 명세

상태: 확정 요구·읽기·분석 기능 구현; 실제 회사 환경 검증은 별도

DAERI의 목적과 확정 요구를 정의한다.

## 목적

DAERI는 자연어로 운영 업무를 맡기고 수행 과정·결과·재사용 지식을 관리하는 호스트 기반 멀티 오케스트레이션 에이전트다.
Codex·Claude Code의 총괄 에이전트가 업무를 조율하고 필요한 하위 작업을 호스트의 하위 에이전트에 배정한다.
구성별 책임과 연결은 [멀티 오케스트레이션 에이전트 구조](../architecture/overview.md)에서 정의한다.

이름에는 숙련된 대리급 직원의 역할과 업무를 대리 수행한다는 의미가 있다.

사용자 목표와 승인 범위에 맞춰 등록된 리소스·도구·분석 방법을 조합한다.
호스트는 조회·분석·보고·내용 검증을 수행하고 DAERI runtime은 승인·실행 이력·자료 조건·보존을 검사한다.
현재 지원과 확장 조건은 [제공 범위](#현재-제공-범위)를 따른다.

| ID | 요구사항 | 상세 계약 |
|---|---|---|
| P-01 | 자연어로 요청을 받고 수행 과정·결과·업무 이력을 관리한다. | [흐름](tasks/workflow.md), [결과](tasks/workflow.md#이력과-완료-근거) |
| P-02 | 에이전트가 연결된 기능을 참고해 필요한 리소스와 수행 방법을 판단한다. | [리소스 계약](resources/contract.md) |
| P-03 | 여러 부처의 리소스를 확장하고 포트·어댑터로 구현을 교체한다. | [리소스 계약](resources/contract.md) |
| P-04 | 환경 설정 후 업무 계획에서 조회·분석·보고·파일·선별 기억의 범위를 Codex·Claude Code 대화에서 함께 승인받는다. | [계획·승인](tasks/approval.md) |
| P-05 | 승인한 대상·읽기 권한·명시적 범위 안에서 도구·질의·후속 수행을 자율 선택하고, 범위 확대에는 수정 계획을 승인받는다. | [계획·승인](tasks/approval.md) |
| P-07 | 사용자 PC에서 runtime·설정·업무 저장소를 운영한다. | [구조](../architecture/overview.md) |
| P-08 | 기존 호스트의 총괄 에이전트·네이티브 하위 에이전트 + Skill + 로컬 MCP runtime으로 멀티 오케스트레이션 에이전트를 구성한다. | [개발 방식과 근거](../architecture/overview.md#오케스트레이션과-자율-수행) |
| P-09 | 프로젝트를 사내외 Git 저장소에 올려 호스트 마켓플레이스 등록·플러그인 설치로 배포할 수 있어야 한다. | [배포](installation/environment.md#배포-출처와-최초-전달) |
| P-10 | 필요한 프로그램·버전을 확인하고 누락·비호환 환경을 설치 기능으로 준비한다. | [환경 준비](installation/environment.md) |
| P-11 | Windows·macOS에서 같은 설치·업무 흐름을 제공하며 OS별 실제 실행 범위를 구분해 검증한다. | [환경 준비](installation/environment.md) |
| P-12 | DB·Cache·Infra·Source·Document·Issue 등 필요한 리소스 범주를 어댑터로 연결하고 추가 범주로 확장한다. | [리소스 범주](resources/adapters.md) |
| P-13 | 리소스 연결은 기존 MCP와 호스트 도구를 재사용하고 필요한 연결·기록 기능만 보완한다. | [연결 구조](resources/contract.md#연결-구조) |
| P-14 | 서비스별 profile에 여러 연결을 관리하고 같은 PC의 Codex·Claude Code에서 설정·기억·기록을 재사용해 업무를 이어간다. | [profile 구성](configuration/profiles.md), [호스트 전환](hosts/plugins.md#재개동시-사용환경-고정) |
| P-15 | profile별 기억을 계획 전에 조회하고 보고와 선별 지식의 자동 저장·색인을 연결해 다음 업무에 활용한다. | [기억·검색·보존](tasks/memory.md) |
| P-16 | setup에서 리소스 종류·제품·개수를 선택하고 접속·인증 YAML을 편집한다. 검증·확인 뒤 인증 등록과 설정 적용을 수행하며 업무별 조회 대상은 계획에서 승인받는다. | [setup YAML 설계](configuration/profiles.md#사용자용-setup-yaml) |
| P-17 | profile별로 로컬·회사 임베딩 API·키워드 전용을 선택하고 그 선택·확인한 설정에 따라 검색·색인을 수행한다. | [임베딩 선택](configuration/profiles.md#임베딩-제공자-선택) |
| P-18 | 총괄 에이전트가 하나의 업무·계획·사용자 승인·실행 이력 아래 작업을 분해·배정하고 하위 에이전트의 실제 근거를 통합한다. | [구조](../architecture/overview.md), [하위 에이전트 실행](tasks/workflow.md#하위-에이전트-위임과-병렬-실행) |

같은 profile에 여러 제품·계정·같은 종류의 연결을 등록하고 하위 에이전트가 필요한 범주의 기능을 조합한다.
결과는 요청에 맞는 대화 응답과 호스트 도구가 생성·검증한 파일로 제공한다.
보고에 선별한 지식은 [기억 계약](tasks/memory.md)에 따라 자동 저장·색인하며 유용한 후보가 없으면 갱신을 생략한다.

## 사용 예정 환경

아래는 사용자가 처음 사용할 예정인 환경이다.
현재 제공하는 연결과 검증 범위는 [리소스 사양](resources/adapters.md)에서 확인한다.

| 역할 | 사용 예정 환경 |
|---|---|
| DAERI 소스·마켓플레이스 배포 저장소 | 사내외 Git 저장소 |
| 사용자 호스트 | Codex 또는 Claude Code |
| profile의 Source | 사용자 PC의 로컬 소스 코드 디렉터리; 복수 등록 |
| profile의 Infra | AWS |
| profile의 DB | PostgreSQL |
| profile의 Cache | Redis |
| profile의 Document | Confluence |
| profile의 Issue | 도메인이 다른 여러 Jira |

배포 저장소와 profile에서 분석할 Source는 별개다.
Source의 [경로 등록·진단·호스트 관찰 등록](resources/adapters.md#로컬-소스-코드)은 기존 파일·검색·Git 도구와 그 실행 권한을 사용한다.

## 현재 제공 범위

profile 설정·계획·대화 승인·등록된 읽기 실행·근거 보고·선별 기억 갱신을 제공한다.
복수 리소스의 결과 비교·계산·파일 작성은 호스트의 기존 도구를 사용하고 runtime은 결과의 근거·권한·보존과 파일 등록을 처리한다.
총괄 에이전트는 같은 승인 범위의 독립적인 작업을 하위 에이전트에 위임하며 runtime은 배정 범위·실제 승인과 실행 이력을 연결한다.
선택한 모델·API·벡터 색인을 사용할 수 없으면 실제 검색 상태와 키워드 검색 결과를 바탕으로 계획한다.
업무 수행 가능성은 제품별 기능·자료 의미·실제 권한에 따르며 부족한 기능은 필요한 연결·계약과 가능한 대안으로 안내한다.
호스트는 조회의 전체성·제한·목표를 대조해 추가 수행과 완료 상태를 판단한다.

변경 실행·무인 업무로 확장하려면 효과·권한·복구·완료 확인 계약과 구현·검증이 필요하다.
담당 코드·대표 회귀와 실제 호스트·회사 리소스·Windows의 확인 경계는 [구현과 검증](../development/dependencies.md#구현과-대표-검증)이 소유한다.
