# DAERI 제품 명세

상태: 확정 요구사항 정리 + 세부 범위 설계 중

## 목적

DAERI는 관리자가 직원에게 업무를 지시하듯 자연어로 서버 운영 업무를 맡기는 AI 에이전트다.
수행 과정과 결과도 관리한다.

이름에는 숙련된 대리급 직원의 역할과 업무를 대리 수행한다는 의미가 있다.

데이터 추출, 코드 기반 사양 확인, 인프라·보안 작업은 업무 예시다.
정기 데이터 업데이트, 비정기 변경 개발, 서비스 이슈 처리도 포함한다.
이 예시를 고정 작업 유형이나 전용 워크플로의 목록으로 사용하지 않는다.

|---|---|---|

| P-02 | 에이전트가 연결된 기능을 참고해 필요한 리소스와 수행 방법을 판단한다. | [리소스 계약](resources/contract.md) |
| P-03 | 여러 부처의 리소스를 확장하고 포트·어댑터로 구현을 교체한다. | [리소스 계약](resources/contract.md) |
| P-04 | 초기에는 실행 전 방법·범위·예상 결과물을 사람에게 확인받는다. | [계획·승인](tasks/approval.md) |
| P-05 | 승인한 방법·범위 안에서 자율 실행하고, 범위 이탈 전에 수정 계획을 승인받는다. | [계획·승인](tasks/approval.md) |
| P-06 | 검증 후 HITL을 완화하거나 해제할 수 있도록 승인 정책과 실행 구조를 분리한다. | [계획·승인](tasks/approval.md) |
| P-07 | 사용자 PC의 실행기를 사용하며 개발자의 중앙 서버 운영을 전제로 하지 않는다. | [구조](../architecture/overview.md) |
| P-08 | 초기 개발 방식은 기존 호스트 에이전트 + Skill + 로컬 MCP 실행기인 1안이다. | [ADR-0001](../architecture/decisions/0001-host-agent-local-runtime.md) |
| P-09 | 프로젝트를 사내 GitLab·GitHub 등의 저장소에 올려 배포할 수 있어야 한다. | [배포](installation/distribution.md) |
| P-10 | 필요한 프로그램·버전을 확인하고 누락·비호환 환경을 설치 기능으로 준비한다. | [환경 준비](installation/environment.md) |
| P-11 | Windows·macOS 지원을 설계하고 최초 구현·실행 검증은 사용자의 Mac에서 진행한다. | [환경 준비](installation/environment.md) |
| P-12 | 최초 어댑터 연동 대상은 PostgreSQL, Redis, AWS, GitLab이다. | [최초 어댑터](resources/initial-adapters.md) |

업무 종류는 사전에 모두 정의하지 않는다.
확장 가능한 리소스에는 DB·Cache·Infra·Log·티켓·메일·소스 등이 있다.

초기 계획 확인에는 분석·조회도 포함한다.

사용자 PC에는 Codex 또는 Claude Code만 준비되어 있다고 가정한다.

## 범용성의 의미와 한계

업무 수행 가능성은 연결된 기능, 데이터 의미, 실제 접근 권한에 따른다.
필요한 리소스가 연결되지 않았거나 연산을 지원하지 않으면 부족한 기능을 설명한다.
이때 다른 방법 또는 추가 정보를 제시한다.

실행하지 않은 일을 완료한 것처럼 보고하지 않는다.

DB 어댑터를 PostgreSQL에서 MongoDB로 바꿀 수 있는 구조를 설계한다.
그렇다고 SQL과 문서 쿼리가 자동으로 같은 의미가 되는 것은 아니다.
공통 실행 계약 안에서 현재 제품의 기능과 제약을 확인해 계획을 구성한다.

## 최초 범위 제안과 미결 사항

초기에는 제한된 읽기 기능으로 연결, 계획 확인, 범위 준수, 근거 보존을 검증하는 것을 제안한다.
전체 제품을 조회 전용으로 제한하는 요구는 아니다.
변경 실행은 권한·완료 확인·중복 방지 계약을 정해 추가한다.

Python 3.12 계열, 공식 MCP SDK, uv, SQLite, 최초 AWS EC2 조회는 기술·기능 제안이다.
사용자 승인이나 실제 환경 검증이 끝난 확정 사항으로 취급하지 않는다.

운영 UI의 상세 구성, 무인 정기 실행, 상시 감시, 다중 에이전트는 최초 구현 범위를 별도로 정해야 한다.

정기 업무도 공통 업무 계약을 재사용한다.
호스트가 종료된 뒤의 실행 방식은 별도 설계가 필요하다.
미결 항목의 진행 상황은 [현재 상태](../current-state.md)에 있다.

## 초기 검증이 답해야 하는 질문

- 리소스 기능만으로 새 요청에 맞는 수행 방법을 구성할 수 있는가?
- 사람이 방법과 범위·예상 결과를 이해하고 확인할 수 있는가?
- 승인 전 실행과 범위 밖 실행을 실제 실행기가 차단하는가?
- 승인 범위 안의 후속 판단을 불필요한 재승인 없이 수행하는가?
- 실패·부분 결과·재개를 완료와 구분하고 근거로 설명하는가?

이는 향후 검증 기준이며 현재 제품이 구현 또는 검증되었다는 뜻이 아니다.
