# DAERI 제품 명세

상태: 확정 요구·첫 버전의 읽기·분석 기능 구현; 실제 회사 환경 검증은 별도

DAERI의 목적과 확정 요구를 정의한다.

## 목적

DAERI는 자연어로 운영 업무를 맡기고 수행 과정·결과·재사용 지식을 관리하는 호스트 기반 멀티 오케스트레이션 에이전트다.
Codex·Claude Code의 총괄 에이전트가 업무를 조율하고 필요한 하위 작업을 호스트의 하위 에이전트에 배정한다.
구성별 책임과 연결은 [멀티 오케스트레이션 에이전트 구조](../architecture/overview.md)에서 정의한다.

이름에는 숙련된 대리급 직원의 역할과 업무를 대리 수행한다는 의미가 있다.

데이터 추출·사양 확인·인프라·보안·정기 업데이트·변경 개발·이슈 처리는 장기적으로 다룰 업무 예시다.
사용자 목표와 승인 범위에 맞춰 등록된 리소스·도구·분석 방법을 조합한다.
에이전트는 그 안에서 승인한 단계의 의존 관계를 지키며 읽기 도구·질의·수행 순서·후속 페이지·재시도를 자율적으로 판단한다.
분석·계산·보고·표·파일의 작성과 내용 검증은 호스트 모델과 기존 도구가 담당한다.
DAERI runtime은 승인·호출 범위·근거·자료 권한·보존·무결성을 검사한다.

사용자 PC에는 Codex 또는 Claude Code만 준비되어 있다고 가정한다.
DAERI profile 안에 동일 종류의 리소스를 여러 개 등록할 수 있어야 한다.
리소스 범주는 역할을, 등록한 어댑터는 현재 사용할 제품·연결 방식을 나타낸다.
하위 에이전트는 필요한 여러 범주의 기능을 조합하고, 추가 제품은 같은 리소스·승인 계약에 맞춰 연결한다.

호스트는 실제 관찰·사용자 확인에서 재사용할 규칙·구조·절차·실패 예방 지식을 선별해 보고에 기억 후보를 연결한다.
runtime은 [기억 계약](tasks/memory.md)에 따라 출처·대상·권한·보존기한을 검사하고 자동 저장·색인하며, 유용한 후보가 없으면 갱신을 생략한다.

사용자 결과는 요청에 맞는 대화 응답과 파일로 제공한다.
텍스트·표·JSON·CSV·DB 파일 등은 결과 형식의 예시이며 실제 생성 가능한 형식은 호스트의 도구·실행 환경에 따른다.
호스트는 업무별 작업 경로에 파일을 작성하고 [결과 제출](mcp/tasks.md#daeri_result_submit)로 등록한다.
runtime은 기여 자료의 현재 내보내기 허용·기한과 파일 경로·해시를 확인해 관리 사본을 제공한다.
실제 서비스의 데이터 변경은 [후속 변경 실행 범위](#최초-구현과-후속-범위)에 해당한다.

## 사용 예정 환경

아래는 사용자가 처음 사용할 예정인 환경이다.
현재 제공하는 연결과 검증 범위는 [리소스 사양](resources/initial-adapters.md)에서 확인한다.

| 역할 | 사용 예정 환경 |
|---|---|
| DAERI 소스·마켓플레이스 배포 저장소 | 사내외 Git 저장소 |
| 사용자 호스트 | Codex 또는 Claude Code |
| profile의 Source | 사용자 PC의 로컬 소스 코드 디렉터리; 복수 등록 |
| profile의 Infra | AWS |
| profile의 DB | PostgreSQL |
| profile의 Cache | Redis |
| profile의 Document | Confluence |
| profile의 Issue | 도메인이 다른 여러 Jira |

DAERI 자체의 배포 저장소와 profile에서 분석할 Source 리소스는 서로 다른 설정이다.
배포 위치를 바꾸거나 리소스 제품을 교체해도 공통 업무·승인 계약을 유지한다.
Source는 등록한 로컬 경로에서 호스트의 기존 도구로 조사하고 확인한 관찰을 업무·보고·기억의 근거로 연결한다.
로컬 파일 편집·프로그램 실행·Git 작업과 그 인증·권한은 Codex·Claude Code의 실행 환경을 따른다.
현재 DAERI의 Source 기능은 [경로 등록·진단과 호스트 관찰 등록](resources/initial-adapters.md#로컬-소스-코드)이다.

## 범용성의 의미와 한계

업무 수행 가능성은 연결된 기능·데이터 의미·실제 권한에 따른다.
같은 DB 범주라도 조회 방식·데이터 구조·보장 범위가 다를 수 있다.
제품별 기능·제약을 확인하는 기준은 [기능 설계 단위](resources/contract.md#기능-설계-단위)를 따른다.
기능이 부족하면 필요한 연결·계약과 가능한 대안을 설명한다.
완료 보고에는 실제 수행 기록과 조건별 검증 근거를 연결한다.
호스트는 조회의 전체성·제한·사용자 목표를 대조해 추가 수행과 업무 완료를 판단한다.

## 최초 구현과 후속 범위

[최초 구현 계획](../plans/initial-implementation.md)이 구현 범위·개발 순서·완료 기준을 소유한다.
첫 버전은 profile 설정·계획·대화 승인·등록된 읽기 실행·근거 보고·선별 기억 갱신을 연결한다.
복수 리소스의 결과 비교·계산·파일 작성은 호스트의 기존 도구를 사용하고 runtime은 결과의 근거·권한·보존과 파일 등록을 처리한다.
총괄 에이전트는 같은 승인 범위의 독립적인 작업을 하위 에이전트에 위임하며 runtime은 배정 범위·실제 승인과 실행 이력을 연결한다.
선택한 모델·API·벡터 색인을 사용할 수 없으면 실제 검색 상태와 키워드 검색 결과를 바탕으로 계획한다.

변경 실행·무인 업무는 효과·권한·복구·완료 확인 계약을 갖춰 후속으로 추가한다.
실제 호스트 설치·회사 리소스와 Windows 실행은 구현된 코드와 구분해 검증한다.
