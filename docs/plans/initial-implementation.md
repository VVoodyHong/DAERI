# 최초 구현 범위와 개발 순서

상태: 읽기·분석과 선택형 기억 검색 구현; YAML setup 구현, 실제 회사 PC·호스트 사용 검증 필요

구현 범위·개발 의존 순서·완료 근거를 정의한다.
프로그램·실행·모듈은 [개발 의존성과 실행](../development/dependencies.md), 상세 동작은 각 사양이 소유한다.
구현된 코드·로컬 검증·실제 회사 환경의 검증을 구분한다.

## 목표와 첫 완료 지점

사용자가 배포 저장소를 마켓플레이스에 추가하고 플러그인을 설치한 뒤 profile을 준비한다.
자연어 요청 → 관련 기억 조회 → 계획 제시 → 호스트 대화 승인 → 리소스 조회 → 근거 검증·보고 → 선별 기억 갱신을 제공한다.
여러 리소스의 결과를 비교·계산한 표와 허용된 파일도 같은 승인 범위에서 생성한다.

첫 버전은 등록된 읽기 기능과 분석을 대상으로 한다.
에이전트는 사용자 목표·승인 범위 안에서 등록 계약을 조합해 수행 방법·순서·후속 조회를 판단한다.
자료를 읽는 범위와 모델 제공·내보내기·보관·기억 범위는 각각 검사한다.

이 표는 사양에서 대표 검증으로 가는 읽기 경로다.

Skill·호스트 설정의 존재와 로컬 MCP 통합은 실제 호스트 UI의 동작 확인과 구분한다.

지원 기능의 목적은 등록 계약의 `collect`·`verify`다.
현재 어댑터는 읽기·검증 계약과 논리 호출·실행기 시간 예산을 제공한다.
추가 실행 목적·제품별 측정 상한은 실제 효과·강제 수단을 등록하는 후속 개발 대상이다.
계획의 필수 한도를 강제할 수 없으면 `PLAN_INVALID`로 입력 보완을 요청한다.
원격 쓰기·배포·외부 게시·무인 실행·HITL 완화와 추가 파일 형식은 후속 범위다.
조회 성공과 원본 완전성 입증은 구분한다.
현재 어댑터의 완전성 판정과 완료 보고의 제한은 [실제 지원 경계](../spec/resources/initial-adapters.md#어댑터별-실제-지원-경계)를 따른다.

로컬·회사 API 임베딩을 선택하고 모델·벡터 검색이 준비되면 혼합 검색을 수행한다.
선택한 검색 경로의 준비·색인이 부족하면 가능한 검색만 수행한 `partial` 상태와 제한을 보존한다.
키워드 전용 선택은 FTS5가 정상 완료되면 `ok`로 반환한다.
기억 0건과 검색 불가는 각각의 조회 상태로 보고한다.
제공자 준비는 관리 경로에서 수행하고 업무 검색은 선택한 profile을 대상으로 한다.

실제 Codex·Claude Code의 마켓플레이스 추가·설치·Skill 진입과 사용자 답변의 의미 해석은 미검증이다.
Windows의 준비 스크립트·공통 MCP 구성은 있으나 실제 Windows 실행·정책·인증 UI는 미검증이다.
회사의 실제 리소스·SSO 로그인·권한·조직 네트워크와 Python·패키지 캐시가 전혀 없는 PC의 전체 온라인 준비도 별도로 확인해야 한다.
회사 임베딩 API의 실제 주소·인증·모델 배포와 응답 호환성도 별도로 확인해야 한다.
setup Skill은 회사 API·키워드 전용·로컬 선택의 가상 요청으로 설치·전송 허용·준비 분기를 별도 검토했다.
로컬 통합 테스트의 리소스는 시험 프로세스이며 운영 환경 확인은 별도로 기록한다.

## 최초 구현 범위

자연어 요청의 해석·계획·보고 표현은 기존 호스트가 맡는다.
실행기는 해당 profile의 현재 구성과 저장 상태를 읽고 승인·대상·기능·자료 정책·예산을 강제한다.
업무 방법은 요청과 등록 기능에서 구성하고 완료 여부는 실제 실행·검증 기록으로 보고한다.

파일 생성기는 처음에 텍스트·JSON·CSV를 제공한다.
표는 실제 출처·유일키 결합·셀 계산을 검증하며 생성 파일의 보존은 원출처와 승인 범위를 따른다.
다른 형식은 계약을 갖춘 생성기로 추가한다.
파일 생성과 원격 DB 변경은 각각의 실행 효과·승인 계약을 갖는다.

기억은 검증된 규칙·구조·절차·실패 예방 지식만 선별한다.
계획 전 검색 기록을 현재 계획에 연결하고 보고 후 허용된 출처·필드·범주만 갱신한다.
저장 대상은 출처·적용 조건·현재 권한을 확인한 지식 후보이며 품질은 실제 검색·사용자 정정 사례로 평가한다.

## 개발 순서

| 단계 | 개발·검증 목표 | 의존 관계 |
|---|---|---|
| 1 | 두 호스트 패키징·setup 진입·대화 승인 연결 | 호스트 기능·배포 접근 |
| 2 | profile·인증·환경·업무·기억 저장과 검색 | 재현 가능한 로컬 환경 |
| 3 | 모의 리소스의 요청부터 보고·기억 갱신까지 연결 | 상태·승인·공통 실행·출처 검사 |
| 4 | 실제 리소스 하나의 전체 사용자 흐름 | 시험용 연결·최소 권한·호스트 설치 |
| 5 | 여러 범주의 실제 연결·결과 조합 | 제품별 계약·실제 대상·완전성 확인 |
| 6 | macOS의 최초 전달·업데이트·중단·복구 | 호스트만 있는 PC·조직 환경 |
| 7 | Windows의 동일 흐름·설치 정책·인증·복구 | 공통 코어와 OS별 실행 확인 |

이 순서는 개발 기능의 의존 관계를 나타낸다.
실제 업무의 리소스 선택·수행 순서는 승인 범위 안에서 호스트가 정한다.
패키징·코어와 실제 사용자 환경의 설치·업무 검증은 각각의 근거로 기록한다.

## YAML setup의 구현과 확인

기본 setup은 [YAML 입력 계약](../spec/configuration/profiles.md#사용자용-setup-yaml)을 따른다.
대화는 시작·리소스 선택·적용을 확인하고 접속값은 선택한 제품의 YAML 입력으로 받는다.
세부 조회 대상은 업무 계획에서 정하고 연결 정보 갱신은 기존 조회 상한·자료 정책을 보존한다.
모든 리소스 범주의 선택지·파일 항목은 실제 카탈로그·스키마에서 생성한다.

| 순서 | 구현·검증 대상 |
|---|---|
| 1 | 카탈로그 범주·제품의 동적 선택과 선택한 인스턴스의 접속·공개 인증 YAML 생성 |
| 2 | 제한된 YAML 읽기·전체 입력 검증·한국어 오류와 기존 편집 보존 |
| 3 | 파일·기준 개정·변경 요약 연결, 확인 뒤 단일 개정의 일괄 저장 |
| 4 | 충돌·재시도·인증 및 준비 실패 후 재개, 관리 초안의 profile 삭제 연동 |
| 5 | setup Skill·사용자 안내·관련 정본 통합과 실제 호스트 확인 |

의존성은 잠금 환경에서 관리하며 사용자 파일은 선택한 연결의 입력을 담는다.
시작 질문의 문구·선택지는 [호스트 setup 계약](../spec/hosts/plugins.md#setup의-정형-질문)을 따른다.
실제 Codex·Claude Code의 CLI·앱 선택 화면과 파일 편집 안내는 별도 검증이 필요하다.
자동 검증의 실제 근거는 위 [현재 검증 경계](#현재-구현-단위와-검증-경계)에 기록한다.

## 선택형 임베딩 구현 순서

회사 API를 사용해야 하거나 로컬 모델 설치가 제한된 환경을 위해 profile별 임베딩 제공자를 선택한다.
기억·질의의 외부 전송은 기존 호스트 모델 제공 허용과 구분해 명시적으로 설정한다.
설정·인증 계약은 [profile 구성](../spec/configuration/profiles.md), 검색·색인 동작은 [기억 사양](../spec/tasks/memory.md)이 소유한다.

| 순서 | 개발·검증 목표 |
|---|---|
| 1 | 로컬·회사 API·키워드 전용 선택의 입력 검증, 비밀 참조와 profile 개정 보호 |
| 2 | OpenAI 호환 API 어댑터의 요청·응답·시간 제한·비밀 제거와 잘못된 응답 거부 |
| 3 | 검색·색인의 선택 제공자 연결, 전송 전 권한 재검사·실패 시 제한·모델 변경 후 재색인 |
| 4 | 로컬 추론 패키지의 선택 설치, 네트워크 없는 상태 조회와 고정 시험 문장의 명시적 진단 |
| 5 | 회사 API·키워드 전용·로컬 준비의 Skill 분기, 전체 회귀와 문서 계약 검토 |

회사 API의 실제 주소·인증·네트워크·모델 배포 호환성은 회사 환경에서 별도로 확인한다.
임베딩 설정은 YAML setup과 개별 JSON 관리 경로가 같은 검증 계약을 사용한다.

## 완료 조건과 검증 범위

로컬 구현 완료에는 공개 계약과 실제 동작의 정합성, 허용·거부·실패·부분 결과·충돌·복구 회귀의 확인이 필요하다.
전체 릴리즈 완료는 변경 범위와 발견된 결함의 검증 근거를 모두 확보했을 때 기록한다.

macOS의 실제 사용 검증은 배포 저장소 → 마켓플레이스 → 설치 → setup → 자연어 요청 → 대화 승인 → 실제 조회 → 보고·기억 갱신의 근거가 필요하다.
재개·일시중지·취소·기한·업데이트 뒤에도 권한·누적 사용량·미확인 결과의 보존·검사 유지를 확인한다.
Windows 완료는 같은 범위의 별도 OS 근거가 필요하다.

실연동 환경이 없으면 모의 연결·코어·설치 조합까지 확인한 범위만 보고하고 회사 PC에서 확인할 경계를 남긴다.
로컬 전체 회귀와 별도로 준비한 실제 모델의 검증 근거를 구분한다.
실제 모델 검사는 준비한 모델 경로가 있는 환경에서, Windows 전용 실행 검사는 해당 OS에서 수행한다.
작업 품질과 문서 동기화는 [개발 원칙](../rules/development.md)·[문서 규칙](../rules/documentation.md)을 따른다.
