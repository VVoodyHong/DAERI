# ADR-0001: 기존 호스트 에이전트와 로컬 MCP 실행기 사용

상태: 채택 · 근거: 사용자의 1안 선택

## 배경

DAERI는 사전에 모두 정의할 수 없는 운영 업무를 처리해야 한다.
사용자는 Codex 또는 Claude Code를 사용한다.
개발자가 중앙 DAERI 서버를 운영할 수는 없다.

연결과 승인·실행 이력은 호스트가 바뀌어도 공통으로 관리할 필요가 있다.

## 검토한 대안

| 대안 | 동작 | 영향 |
|---|---|---|
| 1안: 호스트 판단 + 로컬 MCP | 호스트가 계획·도구 선택, 실행기가 범위 검사·어댑터 실행 | 기존 계정·에이전트 활용, 호스트별 기능 검증 필요 |
| 2안: 별도 판단 루프 + 플러그인 | DAERI가 자체 계획·반복 실행, 플러그인이 입구 역할 | 직접 판단·상태 전이 통제, 별도 모델·실행 루프 관리 필요 |

1안은 호스트가 계획하고 DAERI 도구를 호출하는 방식이다.
호스트별 도구·승인 기능을 검증해야 한다.

2안은 LangGraph 등으로 DAERI 자체의 판단 루프를 구성하는 방식이다.
별도 모델 인증·호출·실행 루프를 관리해야 한다.

## 선택

1안을 채택한다.
Codex·Claude Code가 판단과 후속 실행 선택을 맡는다.
DAERI는 Skill과 사용자 PC의 로컬 MCP 실행기로 제공한다.

초기에는 별도 프레임워크나 자체 모델 호출을 추가하지 않는다.
사내 GitLab·GitHub 등의 저장소에서 배포할 수 있는 구조로 개발한다.

## 영향

연결 계약과 승인 검사를 호스트의 자연어 지침에서 분리할 수 있다.
호스트가 실제 사용자 확인과 로컬 프로세스 실행을 어떻게 지원하는지 각각 검증해야 한다.
호스트 종료 후 무인 실행은 이 결정만으로 해결되지 않는다.

향후 자체 판단 루프가 필요해지면 이 선택을 새 ADR로 재검토한다.

현재 책임 경계는 [구조 설명](../overview.md)을 따른다.
승인 행동은 [계획·승인 명세](../../spec/tasks/approval.md)를 따른다.
배포 계약은 [전달·업데이트 명세](../../spec/installation/distribution.md)를 따른다.
