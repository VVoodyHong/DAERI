# 문서와 설계 검토 원칙

상태: 설계 단계의 작업 기준

문서와 설계를 검토하고 결과를 확인하는 사람과 에이전트를 위한 원칙이다.

이 문서는 문서·기획·설계를 검토하고 확인 결과를 보고하는 기준이다.
개발 구조와 코드의 품질 기준은 [개발 원칙](development.md)을 함께 적용한다.

## 검토 범위

최신 파일과 사용자 수정 사항을 읽고 검토 대상을 정한다.
바뀐 줄뿐 아니라 영향을 받는 명세·규칙·구조 설명의 맥락을 확인한다.
전체 문서 검토 요청에서는 모든 Markdown을 확인하고 분담한 범위를 명시한다.

먼저 요구사항·의미·실행 경계를, 다음으로 정본과 참조를, 마지막으로 표현을 확인한다.
실질적인 문제와 개인적인 표현 선호를 구분한다.
의미가 명확한 표현을 개인 취향만으로 반복해서 고치지 않는다.

## 확인할 내용

| 관점 | 확인할 질문 |
|---|---|
| 요구사항 | 사용자 지시가 보존되고 새로운 제한이 임의로 추가되지 않았는가? |
| 의미와 상태 | 확정·제안·미결·구현·검증 상태가 정확한가? |
| 동작과 경계 | 승인·실패·부분 결과·재개와 완료 근거가 설명되는가? |
| 개발 구조 | 책임·의존 방향·확장 계약·코드 단순성·문서화가 개발 원칙에 맞는가? |
| 정본 | 같은 계약이 중복되거나 다른 문서와 충돌하지 않는가? |
| 변경 영향 | 이관 누락, 오래된 상태, 참조 대상 오류가 없는가? |
| 가독성 | 목적·독자·흐름을 코드 없이 이해할 수 있는가? |
| 자료와 추적 | 출처·가상 예시·Git 변경 범위가 적절한가? |

세부 표현은 [Markdown 원칙](markdown.md), 내용은 [작성 원칙](documentation.md)을 따른다.
요구사항·대안 비교·선택 근거는 [기획](planning.md) 원칙을 적용한다.

## 확인 방법

사람과 에이전트가 원문을 읽는 검토와 링크·앵커·형식 확인을 함께 수행한다.
형식 검사가 통과했다고 내용의 정확성까지 검증된 것으로 보고하지 않는다.
렌더링을 확인했을 때만 미리보기 검증을 수행했다고 기록한다.

실제 호스트·리소스의 동작은 실행한 대상과 결과가 있을 때만 검증 완료로 표시한다.
확인하지 못한 항목과 이유를 남긴다.
새 수정이나 미해결 문제가 없으면 같은 확인을 불필요하게 반복하지 않는다.

## 발견과 후속 조치

발견에는 위치, 문제, 영향과 제안하는 수정을 포함한다.
확정 조건의 누락·충돌과 잘못된 실행 경계를 먼저 처리한다.
의미를 유지하는 명백한 정정은 허용된 수정 범위에서 반영한다.

판단이 필요한 제품 선택은 임의로 확정하지 않고 미결 사항으로 남긴다.
수정 후에는 해당 내용과 영향을 받는 참조를 다시 확인한다.
작업 결과에는 검토 범위, 수정한 발견, 남은 문제와 확인 한계를 기록한다.

설계·기능·복잡도·문서 일관성을 보는 관점은 [Google 검토 지침](https://google.github.io/eng-practices/review/reviewer/looking-for.html)을 참고했다.
위 기준은 해당 코드 검토 관점을 DAERI의 문서·설계 작업에 맞게 적용한 것이다.
