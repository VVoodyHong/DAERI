# 프로젝트 검토 원칙

상태: 문서·코드 정합성·간소화·검증 기준

현재 요구·사양과 구현을 대조하고 중복·미사용·대체된 내용을 정리한다.
작업별 규칙과 정본은 [AGENTS](../../AGENTS.md)에서 확인한다.

## 검토 범위

별도 범위를 지정하지 않은 프로젝트 검토는 저장소 전체를 대상으로 한다.
프로젝트가 관리하는 모든 Markdown·소스 코드·테스트·설정·스크립트·의존성·구성도와 빌드·실행 진입점을 확인한다.
범위를 지정하면 해당 대상과 영향을 받는 호출부·계약·검증을 함께 확인한다.

분담 범위와 남은 대상을 파악한다.

## 검토 순서

| 순서 | 확인할 내용 |
|---|---|
| 1. 요구·동작 | 사용자 지시, 책임·권한·실패·재개·완료 근거의 누락·충돌 |
| 2. 문서·코드 정합성 | 사양·공개 입력·기본값·설정·구현·테스트·구성도의 일치 |
| 3. 간소화·구조 | 중복·불필요·미사용·대체된 내용, 문서 정본·코드 책임·의존 방향 |
| 4. 상태·근거 | 확정·제안·미결·구현·검증 구분, 외부 기능·출처·예시의 정확성 |
| 5. 표현·참조 | 목적·흐름·명명·가독성, 링크·앵커·읽기 경로 |

기능 검토는 정본의 각 동작을 구현·테스트에 연결하고 공개 기능에서도 담당 정본으로 역추적한다.
입력 필수값·기본값·타입, 상태 전이·중복 처리, 승인·실행 조건, 저장·삭제·오류·복구를 대조한다.
설치 안내·Skill·도구 설명·생성 설정도 같은 계약을 사용하는지 확인한다.
호스트 지침의 준수, runtime의 강제 검사, 모의 연동과 실제 환경 검증은 각각의 근거로 판정한다.

## 간소화 판단

같은 계약을 여러 문서가 소유하거나 같은 처리가 여러 코드에 있으면 변경 책임을 기준으로 통합한다.
교체된 설계·명칭·설정·이관 잔여물은 현재 계약에 맞춰 수정하거나 삭제한다.
미구현 확정 요구와 명시된 제안·미결은 현재 상태로 구분해 관리한다.

코드·설정·의존성의 미사용 여부는 호출부·공개 인터페이스·등록 방식·빌드·실행 경로를 확인해 판단한다.
문서는 독자·소유 계약·읽기 경로, 코드는 책임·의존 방향·필요한 추상화를 기준으로 병합·분리·삭제를 결정한다.
정리 후에는 현재 지원 동작·필수 보호 조건·저장 자료의 호환성과 승인 범위 안의 자율성을 확인한다.

## 확인과 후속 조치

발견은 위치·문제·영향·최소 수정을 설명한다.
확정 조건과 실행 경계의 문제를 먼저 처리하고 허용 범위의 오류 수정·삭제·병합은 문서·코드·검증에 함께 반영한다.
보고만 요청한 경우에는 발견과 수정안을 제시한다.
제품 판단이 필요하면 담당 정본에 판단 근거·대안·미결 상태를 기록한다.

수정은 사용자 요구·동작 정확성·문맥 이해에 주는 영향을 기준으로 결정한다.
자율적인 도구 선택·업무 구성과 승인·인증·자료 제공의 실제 경계를 함께 대조한다.
수정 후 내용과 영향받는 참조를 확인하고 [검증 기준](development.md#검증)과 [Git·인계 기준](documentation.md#git-기록과-인계)에 따라 결과를 보고한다.

[Google 검토 지침](https://google.github.io/eng-practices/review/reviewer/looking-for.html)의 설계·복잡도·일관성 관점을 문서 검토에 적용했다.
