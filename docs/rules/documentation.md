# 문서 작성 규칙

상태: 상세 작성 기준

DAERI의 Markdown은 에이전트가 참고하는 자료이면서 사람이 맥락을 이해하는 문서다.
독자가 코드를 열지 않아도 목적, 동작, 판단 근거를 따라갈 수 있도록 작성한다.
이 문서는 [AGENTS](../../AGENTS.md)에서 연결하는 문서 작성 규칙의 정본이다.

문장·문단·줄바꿈·표현 형식은 [Markdown 규칙](markdown.md)을 함께 적용한다.
원본 위치와 분류는 [문서 구조](../development/documentation-architecture.md)를 따른다.

## 맥락과 동작 설명

문서 시작에서 목적과 적용 범위를 설명한다.
주요 독자와 읽은 뒤 이해하거나 판단할 내용을 짧게 밝힌다.
관련 정본이 있으면 링크하고 같은 내용을 다시 복사하지 않는다.

동작 명세는 다음 질문에 답할 수 있어야 한다.

- 누가 무엇을 요청하거나 어떤 상황에서 시작하는가?
- 어떤 리소스와 조건을 확인하며 어느 범위에서 실행하는가?
- 사용자는 무엇을 확인하고 어떤 결과를 받는가?
- 실패·거부·범위 이탈·부분 결과가 발생하면 어떻게 처리하는가?
- 무엇을 근거로 완료를 판단하며 아직 정하지 않은 것은 무엇인가?

코드 모듈이나 API 이름의 나열만으로 동작 설명을 대신하지 않는다.
예시는 입력 → 판단·실행 → 사용자가 보는 결과를 연결한다.
예시가 제품의 지원 범위를 제한하는 고정 업무 목록처럼 읽히지 않게 한다.

## 상태와 표현의 정확성

상세 명세·구조·진행 문서 상단에는 상태를 적는다.
가져오기만 담당하는 CLAUDE에는 설명이나 상태를 추가하지 않는다.
작성일·갱신일·결정일과 날짜가 들어간 파일명은 사용하지 않는다.

| 표현 | 의미 |
|---|---|
| 확정 요구사항·채택 | 합의된 제품 조건 또는 선택 |
| 설계 제안·미결 | 검토 중인 방법·기술·기본값 |
| 구현 완료 | 코드가 존재하며 구현 작업이 끝남 |
| 검증 완료 | 대상·방법·결과를 실제 확인함 |
| 대체됨 | 현재 정본이나 실행 지시로 사용하지 않음 |

한 문서에 확정 요구와 제안이 함께 있으면 해당 절에서도 구분한다.
요구·설계·구현·검증이 바뀌면 해당 정본의 상태와 미결 항목도 같은 작업에서 갱신한다.

“지원한다”와 “지원하도록 설계한다”, “검증했다”와 “검증할 예정이다”를 구별한다.
확인한 호스트·OS·버전·리소스 범위를 명시하고 확인하지 않은 대상까지 일반화하지 않는다.

변경 이력과 문서의 시점은 Git으로 관리한다.
제품 기능에 필요한 기간·실행 시각·승인 타임스탬프 계약은 유지한다.

## 링크, 예시, 코드 블록

내부 링크는 저장소 안의 상대 경로로 작성한다.
링크 이름에는 대상의 의미를 적고 이동·삭제 시 참조도 갱신한다.
외부 근거는 해당 내용을 뒷받침하는 공식 문서로 연결한다.

예시는 가상 데이터와 인증 참조를 사용한다.
실제 비밀값·개인정보·사내 운영 데이터를 넣지 않는다.
검증하지 않은 실행 명령이나 설정을 바로 사용할 수 있는 절차처럼 제시하지 않는다.

아직 확정하지 않은 구조는 의사 코드나 예시임을 본문에서 밝힌다.
그림을 사용할 때는 목적과 책임을 설명하는 문장도 함께 제공한다.

## 관련 작업 원칙

기존 문서의 수정·이동·삭제는 [변경 관리](changes.md)를 따른다.
설계 대안의 비교와 선택 근거는 [기획](planning.md) 원칙을 따른다.
내용의 정확성과 정본 일관성은 [검토](review.md) 원칙으로 확인한다.
