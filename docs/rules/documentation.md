# 문서 작성과 변경 규칙

상태: 공통 작성·변경 기준

Markdown은 에이전트의 참고 자료이면서 사람이 목적·동작·판단 근거를 이해하는 문서다.
분류와 정본 위치는 [문서 구조](../development/documentation-architecture.md)를 따른다.

## 설명과 근거

문서 시작에서 목적·적용 범위와 현재 상태를 짧게 밝힌다.
동작은 입력 → 수행 방법·조건 → 결과로 연결하고 거부·실패·부분 결과·완료 근거도 설명한다.
API·모듈은 사용자 동작과 구현 책임을 연결해 설명한다.

같은 계약은 한 정본에 두고 다른 문서는 링크한다.
현재 기능은 입력·조건·처리·결과·실패를 사양으로 설명하고 담당 구현과 대표 검증으로 연결한다.
확정 요구와 현재 구현의 차이는 지원 범위·확장 조건으로 명시하고 변경 때 함께 대조한다.
공식 자료의 사실과 이를 DAERI에 적용한 판단을 구별한다.
예시는 가상 사례로 표시하고 적용한 계약과 실제 지원 범위를 연결한다.

공통 설계는 DB·Cache·Infra·Source·Document 같은 리소스 범주와 역할로 설명한다.
제품별 구현과 공통 계약은 담당 정본에서 구분한다.
실제 사용 예정 제품은 [제품 명세의 환경](../spec/product.md#사용-예정-환경)에 모으고, 구현 기술·프로그램·버전은 필요할 때 담당 정본에서 관리한다.

## 상태와 시점

| 표현 | 의미 |
|---|---|
| 확정 요구·채택 | 사용자가 정한 조건 또는 합의한 선택 |
| 설계 제안·미결 | 제안한 방법·기술·기본값 또는 남은 판단 |
| 구현 완료 | 실제 코드가 존재하고 구현 작업을 마침 |
| 검증 완료 | 대상·방법·결과를 실제 확인함 |

요구와 제안이 섞이면 해당 절에서도 구분한다.
“지원하도록 설계한다”와 “지원한다”, “검증할 예정이다”와 “검증했다”를 구별한다.
검증 결과에는 실제 확인한 호스트·OS·리소스와 추가 확인 대상을 표시한다.

문서의 변경 시점과 이력은 Git으로 관리한다.
파일명은 주제·역할을 표현하는 고정 이름으로 작성한다.
제품 기능에 필요한 기간·실행 시각·승인 타임스탬프는 유지한다.
CLAUDE.md는 AGENTS.md 가져오기 한 줄만 둔다.

## 문장과 Markdown

한 문장은 주요 설명이나 판단 하나, 한 문단은 하나의 주제로 구성한다.
보통 1~3문장으로 쓰고 핵심 동작 뒤에 이유·예외를 설명한다.
긴 조건·괄호·반복은 나누고 승인 조건과 실패 경계를 함께 설명한다.

산문 소스는 문장마다 줄을 나누고 주제가 바뀌면 빈 줄을 둔다.
단일 줄바꿈은 화면에서 같은 문단으로 이어지므로 문단 구분은 빈 줄로 표현한다.
익숙한 한국어·능동형과 일관된 용어를 쓰고 약어는 처음에 설명한다.

- `#` 제목은 하나, 본문은 `##`·`###` 순서로 작성한다.
- 제목·목록·표·코드 블록 앞뒤에 빈 줄을 둔다.
- 절차는 번호 목록, 병렬 조건은 글머리 목록, 비교·대응은 표로 표현한다.
- 표 셀은 짧게 쓰고 긴 설명은 표 아래 문단으로 옮긴다.
- 링크·인라인 코드·표의 행은 하나의 문법 단위로 유지한다.
- 코드 블록에는 언어를 표시하고 필요한 부분만 담는다.
- 강조·목록 계층은 필요한 곳에 두고 문단은 빈 줄로 구분한다.

내부 링크는 상대 경로와 의미 있는 이름을 사용한다.
외부 근거는 해당 주장을 뒷받침하는 공식 문서로 연결한다.
예시에는 가상 데이터와 인증 참조를 사용한다.
명령·설정 예시는 실제 검증한 절차와 설계 예시를 구분한다.

## 동작과 조건의 기술

사양은 목적·입력 → 수행 조건 → 처리와 자율 판단 → 결과 → 실패·재개 순서로 기술한다.
형식·상태·권한처럼 정확성이 필요한 항목은 필드·허용 조건·검증 결과로 정의한다.
성공 조건의 수행 동작과 실패 조건의 상태·오류·다음 조치를 연결한다.

업무 수행 방법은 목표·승인 범위·완료 근거를 기준으로 설명한다.
DAERI는 그 안에서 리소스·도구·분석 방법·실행 순서·재시도를 자율적으로 선택한다.
승인 범위가 달라지는 경우에는 수정 계획과 사용자 확인 절차를 기술한다.
입출력 형식과 승인 경계의 정확성, 범위 안에서의 자율 판단을 함께 유지한다.

동작을 수정할 때에는 원인이 된 지침과 계약의 정본을 갱신한다.
현재 수행할 동작과 관찰 가능한 조건을 직접 설명하고 이전 가정과 중복 지침을 정리한다.
중복된 지침은 정본으로 통합하고 Skill·호스트 문서는 해당 계약의 진입점으로 연결한다.
문장 검토에서는 표현 교체와 함께 입력·출력·실패 경계·확장 가능성의 보존을 확인한다.

## 변경과 이관

수정 전 현재 파일·Git 차이·관련 정본을 읽고 사용자 수정을 파악한다.
사용자 수정과 현재 파일을 변경의 기준으로 삼는다.
표현 정리와 제품 요구 변경을 구분하고 의미 변경의 이유·영향을 설명한다.

현재 요청을 완성하는 데 필요한 부분을 수정한다.
이관 시 필요한 내용을 새 정본에 대조하고 반복·대체된 내용은 제거한다.
짧고 같은 질문에 답하는 내용은 기존 절로 유지한다.

이동·삭제 후 링크·앵커·필수 읽기 경로와 문서 구조를 함께 갱신한다.
이관이 끝난 일반 문서는 정리하고 읽기 경로를 새 정본으로 모은다.
제품 선택 변경은 [기획](planning.md), 정확성 확인은 [검토](review.md)를 따른다.

## Git 기록과 인계

기본 작업 브랜치는 `main`이며 사용자 요청이 있을 때만 별도 브랜치를 사용한다.
스테이징·커밋 전 변경 범위와 내용을 확인한다.
현재 요청의 변경을 목적 단위로 선별해 기록하고 사용자 변경은 해당 의도를 유지한다.
커밋은 관련 목적 단위로 묶고 설정된 작성자 정보로 기록한다.
운영체제 자동 생성 파일은 추적에서 제외한다.

수정한 정본의 상태·미결·검증 범위도 함께 갱신하고 현재 세션에서 다시 읽는다.
인계 응답에는 변경·실제 확인·남은 문제·관련 경로를 남긴다.
현재 계약과 검증 범위는 정본에, 변경 이력은 Git에 남긴다.
원문·링크 확인, 미리보기, 실제 실행의 검증 결과는 각각 구분해 보고한다.
