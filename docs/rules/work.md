# 작업 원칙

상태: 요구사항 해석·설계·개발·문서화·검증·인계의 공통 기준.
작업의 시작과 정본 지도는 [AGENTS](../../AGENTS.md), 전체 검토 절차는 [검토 원칙](review.md)을 따른다.

## 적용과 정본

[서비스 설계](../service.md)는 사용자 동작·구성·책임을, [개발·운영 안내](../development.md)는 구현·설정·API·배포·검증을 관리한다.
규칙은 작업 방법을 정의하고 제품 사양은 해당 정본에서 정의한다.
같은 계약은 한 곳에서 관리하고 다른 문서·호스트 지침은 필요한 조건과 절차로 연결한다.

사용자의 최신 지시와 현재 파일·Git 차이·실제 승인·실행 기록을 작업 기준으로 삼는다.
문서와 최신 지시가 다르면 담당 정본을 함께 갱신한다.
기능 변경은 구현·사양·검증을 한 작업으로 완성한다.

## 요구사항과 설계

사용자·대상·기대 결과·완료 조건과 이번 작업 범위를 먼저 정한다.
입력·수행 조건·자율 판단·결과를 연결하고 책임·권한·자료 제공 범위·실패·재개·완료 근거를 확인한다.
업무 예시는 사용자의 목표를 파악하는 자료로 사용하고 구현은 공통 계약과 현재 지원 기능으로 구성한다.

결과에 큰 영향을 주는 정보만 질문하고 그 답과 무관한 작업은 계속한다.
위임받은 세부 판단은 기존 합의와 최소 구현 원칙으로 진행한다.
승인 범위 안에서는 자율적으로 수행하고 범위 변경은 수정 계획과 사용자 확인으로 연결한다.
설계·구현·실제 설치·외부 변경은 요청된 작업 범위에 맞춰 진행한다.

외부 기능·API·호환성은 사용할 버전의 공식 자료나 실제 확인 결과를 근거로 한다.
확인한 사실, 프로젝트의 선택과 검증할 가정을 구분한다.
구조·외부 계약·배포·권한에 영향을 주는 선택은 이유·비용·제한·영향과 남은 불확실성을 설명한다.
합리적인 대안이나 큰 변경 비용이 있으면 충족할 조건과 비교 기준을 먼저 정한다.

| 상태 | 기록 기준 |
|---|---|
| 확정 요구·채택 | 사용자 지시·합의 또는 위임받은 범위에서 확정한 선택 |
| 제안·미결 | 제안한 방법·기본값과 남은 판단·검증 가정 |
| 구현 완료 | 실제 코드와 관련 사양·검증 작업을 완성 |
| 검증 완료 | 대상·방법·환경·결과를 실제 확인 |

선택 근거와 현재 상태는 담당 정본에서 관리한다.
실행 계획에는 순서·의존 관계·완료 확인 방법을, 실험에는 확인할 항목·담당자·시점·방법을 정한다.
문서는 독립적인 독자·계약·변경 책임이 생길 때 분리한다.

## 개발

### 구조와 최소 코드

| 원칙 | 적용 기준 |
|---|---|
| 클린 코드·아키텍처 | 읽기 쉬운 코드, 명확한 책임, 핵심 정책을 보호하는 의존 방향 |
| 확장성과 범용성 | 기능 계약·포트·어댑터로 리소스 교체·추가 |
| 최소 코드 | 현재 요구를 완성하는 가장 단순한 구현과 필요한 추상화 |
| 문서화 병행 | 동작·계약·구조·검증을 구현과 함께 갱신 |

패키지는 같은 변경 책임의 모듈을 모으고 함수·자료형은 이름·입출력으로 의도를 드러낸다.
핵심 정책은 포트·내부 자료형으로 정의하고 외부 어댑터가 SDK 객체·오류를 경계에서 변환한다.
인터페이스와 계층은 실제 교체·검증·수정 비용을 줄이는 책임 경계에 둔다.
현재 패키지와 의존 관계는 [코드 구조](../development.md#코드-구조)를 따른다.

새 리소스·제품·환경의 차이는 기능·스키마·제약과 설정으로 표현하고 공통 계약으로 호출한다.
업무별 리소스·도구·분석·실행 순서·재시도는 에이전트가 목표·승인 범위·완료 근거에 따라 선택한다.
식별자·개정·충돌 처리는 서비스가 관리하고 모델 입력은 수행할 업무에 필요한 값으로 구성한다.

기존 코드·표준 기능·플랫폼 기능을 우선 사용하고 새 의존성은 필요와 유지 비용을 설명한다.
같은 정책·처리는 동일한 변경 책임을 기준으로 통합하고 미사용·대체된 코드와 설정은 호출·등록·빌드 경로를 확인해 정리한다.
긴 함수·복잡한 조건은 실제 책임으로 나누고 주석은 코드로 드러나지 않는 이유·성립 조건을 설명한다.

### 입력·실패·권한

외부 입력은 경계에서 검증하고 성공·거부·미지원·시간 초과·잘림은 상태·원인·다음 조치로 반환한다.
저장·삭제·오류·복구와 실제 한도·재시도·중복 처리는 제품 계약에 맞춰 구현한다.
같은 필드·타입·기본값·enum은 설정 스키마·공개 인터페이스·예시에서 일치시킨다.

필요한 최소 권한을 사용하고 실제 호출마다 현재 인증·대상·승인·자료 격리·저장 무결성을 검사한다.
검사를 통과한 조건에서 실행하며 실패에는 해당 오류와 재개 절차를 반환한다.
비밀값은 인증 저장소의 참조로 등록하고 실제 연결 시점에 해소한다.
민감 자료는 승인·설정의 제공 범위 안에서 필요한 정보만 반환한다.
리소스 자료는 분석 입력으로, 실행 정책은 현재 설정과 실제 승인 기록으로 해석한다.
추가 통제는 구체적인 요구와 영향에 따라 도입한다.

## 문서

### 사양의 기술

문서 시작에서 목적·적용 범위·현재 상태를 짧게 밝힌다.
사양은 **목적·입력 → 수행 조건 → 처리와 자율 판단 → 결과 → 실패·재개** 순서로 기술한다.
필수값·기본값·타입·상태·권한과 실패 시 오류·다음 조치를 명시해 문서에서 실제 동작을 대조할 수 있게 한다.
API·모듈은 사용자 동작과 구현 책임을 연결하고 공통 설계는 리소스 범주·역할로 설명한다.

추가 요구·오류 수정은 원인이 된 계약의 정본을 개정한다.
요청별 덧붙임·반복 예외는 개정한 계약에 통합하고 이전 가정·중복 설명은 교체·정리한다.
수행할 동작과 관찰 가능한 조건을 직접 정의하며 금지형 지시·제한 나열은 검사 대상·허용 조건·위반 시 결과로 재구성한다.
승인·인증·자료 보호는 실제 검사 조건과 실패 처리로 유지한다.

요구·제안·미결과 구현·검증 상태를 해당 절에서 구분하고 확인한 사실에는 근거를 연결한다.
호스트 지침의 준수, runtime의 강제 검사, 모의 연동과 실제 환경 검증은 각각의 근거로 표현한다.
예시는 가상 데이터·인증 참조를 사용하고 적용한 계약·현재 지원 범위와 연결한다.

### 표현과 변경

익숙한 한국어·능동형·일관된 용어를 사용하고 약어는 처음에 설명한다.
문장은 주요 설명 하나, 문단은 하나의 주제로 구성하며 보통 1~3문장으로 작성한다.
산문 소스는 문장마다 줄을 나누고 문단은 빈 줄로 구분한다.
긴 조건·괄호·반복은 나누고 절차는 번호 목록, 병렬 조건은 글머리 목록, 비교·대응은 표로 표현한다.

- `#` 제목은 하나, 본문은 `##`·`###` 순서로 작성한다.
- 제목·목록·표·코드 블록 앞뒤에 빈 줄을 두고 코드 블록에는 언어를 표시한다.
- 표 셀은 짧게 쓰고 긴 설명은 표 아래 문단으로 옮긴다.
- 링크·인라인 코드·표의 행은 하나의 문법 단위로 유지한다.
- 내부 링크는 상대 경로와 의미 있는 이름, 외부 근거는 해당 주장을 뒷받침하는 공식 문서로 연결한다.

수정 전 현재 파일·Git 차이·관련 정본을 읽고 사용자 수정과 의도를 보존한다.
표현 정리와 제품 요구 변경을 구분하고 의미 변경의 이유·영향을 설명한다.
파일명은 주제·역할을 나타내는 고정 이름으로, 변경 시점·이력은 Git으로 관리한다.
제품의 기간·실행 시각·승인 타임스탬프는 해당 기능의 자료로 유지한다.
`CLAUDE.md`는 `AGENTS.md` 가져오기 한 줄로 유지한다.
이동·삭제 후 정본·읽기 경로·링크·앵커·Skill·호스트 참조를 함께 갱신한다.

## 검증과 인계

관찰 가능한 동작·계약과 실제 실패 위험에 맞춰 검증한다.
코어 정책은 외부 리소스 없이 확인하고 어댑터 모의 계약과 실제 호스트·리소스 연동은 구분한다.
입력 경계·상태 전이·동시 변경·중복·허용·거부·실패·복구를 확인하고 필요하면 재현 사례로 회귀를 검증한다.
의존성·설정·인증은 코드와 구분해 잠금 정보와 재현 가능한 환경으로 관리한다.
최적화는 측정한 병목·실제 한도를 근거로 한다.

변경 후 구현·사양·테스트·설정·공개 입력·기본값·구성도·설치 안내를 양방향으로 대조한다.
원문·링크·앵커·형식을 확인하고 미리보기·실행은 실제 확인한 대상·방법·결과로 보고한다.
검증 결과에는 실제 OS·호스트·리소스·버전과 추가 확인 대상을 표시한다.
검증은 변경·실패·미해결 문제의 영향에 맞춰 수행한다.
전체 검토와 간소화는 [검토 원칙](review.md)에 따라 진행한다.

### Git 기록과 인계

기본 작업 브랜치는 `main`이며 사용자 요청이 있을 때 별도 브랜치를 사용한다.
스테이징·커밋 전 변경 범위를 확인하고 현재 요청의 변경을 목적 단위로 선별한다.
사용자 변경을 보존하고 커밋은 설정된 작성자 정보로 기록하며 운영체제 자동 생성 파일은 추적에서 제외한다.

수정한 정본의 상태·미결·검증 범위를 갱신하고 현재 세션에서 다시 읽는다.
인계에는 변경·삭제·병합, 실제 확인한 환경·검증·결과, 남은 문제·미검토 범위·관련 경로를 남긴다.
현재 계약과 검증 범위는 정본에, 변경 이력은 Git에 남긴다.
