# 기획 원칙

상태: 설계 단계의 작업 기준

요구사항과 설계안을 구체화하는 사람과 에이전트를 위한 원칙이다.

이 문서는 요구사항을 해석하고 대안을 비교해 검토 가능한 설계안을 만드는 기준을 정의한다.

## 문제와 범위

사용자가 해결하려는 문제, 사용 대상, 기대 결과와 완료 조건부터 파악한다.
업무 예시를 고정된 기능 목록이나 필수 워크플로로 바꾸지 않는다.
현재 단계에서 구체화할 범위와 아직 다루지 않을 항목을 구분한다.

확정 요구사항은 [제품 명세](../spec/product.md)를 기준으로 연결한다.
부족한 정보는 가정·제안·미결 항목으로 표시한다.
기술 이름이나 도구 선택부터 제품 요구를 역으로 정하지 않는다.

## 동작과 경계

입력, 수행 방법, 사용자가 받는 결과를 연결해 설명한다.
구성 요소의 책임, 권한, 데이터 제공 범위와 완료 근거를 함께 확인한다.
정상 흐름뿐 아니라 거부·실패·부분 결과·취소·재개도 고려한다.

상세 계약은 해당 명세에 두고 기획 문서에는 관련 정본을 연결한다.
아직 구현하지 않은 설계를 구현 또는 검증 완료로 표현하지 않는다.

## 조사와 가정

외부 기능·호환성·지원 범위는 공식 문서나 실제 확인 결과를 근거로 한다.
출처가 보장하는 사실과 그 사실을 프로젝트에 적용한 판단을 구분한다.
베스트 프랙티스의 폴더·도구·절차를 그대로 필수 조건으로 복사하지 않는다.

결과를 크게 바꾸는 정보가 부족하면 필요한 부분을 질문한다.
그 정보와 무관하게 진행할 수 있는 문서 작업은 계속한다.
이미 허용받은 문서 정리마다 추가 확인 절차를 만들지 않는다.

## 대안 비교와 선택 근거

책임 경계·외부 계약·배포 방식·권한 정책에 영향을 주는 선택은 근거를 설명한다.
바꾸는 비용이 크거나 여러 합리적인 대안이 있으면 비교 기준을 밝힌다.

해결할 문제와 반드시 만족해야 할 제약을 먼저 적는다.
현실적인 대안의 이점·비용·제한과 요구사항 충족 여부를 비교한다.
선택 이유, 예상 영향, 남은 불확실성과 확인 방법을 연결한다.

근거 없는 정밀한 수치나 점수로 선택을 정당화하지 않는다.
선택 근거는 해당 구조 설명이나 명세에서 현재 내용과 함께 관리한다.

## 확정과 제안

사용자가 정한 요구와 선택은 확정 조건으로 기록한다.
위임받은 범위의 통상적인 작업은 그 권한 안에서 진행한다.
위임받지 않은 중요한 제품 선택은 제안 또는 미결 상태로 둔다.

에이전트의 추천과 사용자의 합의를 같은 의미로 기록하지 않는다.
미결인 세부 개발 규격·기술 스택·지원 버전을 임의로 확정하지 않는다.
새 선택이 기존 확정 조건을 바꾸는지 확인한다.

## 구체화의 수준

현재 문제에 필요한 경계와 계약부터 정리한다.
독립적으로 검토할 내용이 생길 때 문서를 나누고 빈 분류를 미리 늘리지 않는다.

실행 계획에는 필요한 순서·의존 관계·완료 확인 방법을 포함한다.
설계안을 실제 프로그램 설치나 외부 자원 변경 지시로 취급하지 않는다.
구조 설계는 [개발 원칙](development.md)을 함께 적용한다.
제품 코드와 언어·도구별 세부 규격은 구현 범위가 정해질 때 구체화한다.

기획 내용은 [작성 원칙](documentation.md)에 맞게 정리하고 [검토 원칙](review.md)으로 확인한다.
