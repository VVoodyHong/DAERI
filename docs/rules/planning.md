# 기획 원칙

상태: 요구 해석·설계 선택 기준

현재 해결할 문제와 완료 조건을 먼저 정하고 검토 가능한 설계안을 작성한다.
확정 요구는 [제품 명세](../spec/product.md), 구조 기준은 [개발 원칙](development.md)을 따른다.

## 문제와 동작

사용자·대상·기대 결과와 이번 범위를 파악한다.
업무 예시에서 사용자 목표를 파악하고 공통 계약과 현재 지원 기능으로 해결 방법을 구성한다.
입력·방법·결과를 연결하고 책임·권한·제공 범위·실패·재개·완료 근거를 확인한다.

결과를 크게 바꾸는 정보만 질문하고 그 정보와 무관한 작업은 계속한다.
세부 판단을 위임받으면 기존 합의와 최소 구현 원칙으로 진행한다.
구현 실험으로 확인할 항목은 담당자·확인 시점과 검증 방법을 정한다.
승인 범위 안의 작업은 자율적으로 진행하고 범위 변경에는 수정 계획을 확인받는다.
설계·구현·실제 설치와 외부 변경은 사용자 요청의 작업 범위로 구분한다.

## 조사와 선택

외부 기능·호환성은 공식 문서나 실제 확인 결과를 근거로 한다.
출처로 확인한 사실, 프로젝트의 판단과 검증할 가정을 구별한다.
베스트 프랙티스는 해결할 문제와 프로젝트 제약에 맞춰 채택한다.

책임·외부 계약·배포·권한에 영향을 주는 선택은 이유를 설명한다.
변경 비용이 크거나 합리적인 대안이 있으면 충족할 제약과 비교 기준을 먼저 밝힌다.
이점·비용·제한·예상 영향과 남은 불확실성·확인 방법을 연결한다.
비교에는 확인 가능한 근거와 불확실성을 사용한다.

## 확정과 상세화

사용자 요구·합의는 확정, 에이전트 추천·가정은 제안 또는 미결로 기록한다.
위임된 범위의 세부 선택은 기존 확정 조건 안에서 진행한다.
스택·개발 규격·지원 버전의 상태는 근거에 따라 확정·제안·미결로 구분한다.
기획 문장도 [동작·조건 기술 규칙](documentation.md#동작과-조건의-기술)에 따라 사용자 목표·자율 판단 범위·결과로 연결한다.

선택 근거는 해당 명세의 현재 내용과 함께 관리한다.
현재 필요한 경계·계약부터 정하고 독립적인 질문·변경 책임이 생길 때만 문서를 나눈다.
실행 계획에는 순서·의존 관계·완료 확인 방법을 포함한다.
제품 코드·언어별 상세는 구현 범위가 정해질 때 구체화한다.

작성·이관은 [문서 규칙](documentation.md), 확인은 [검토](review.md)를 따른다.
