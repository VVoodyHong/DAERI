# 개발 원칙

상태: 사용자 지정 기본 원칙 + 상세 개발 기준

구조·코드·설정·의존성의 품질 기준이다.
실제 착수 범위와 기술 선택은 사용자 요청과 관련 명세에서 확인한다.

## 기본 원칙

| 사용자 지정 원칙 | 적용 기준 |
|---|---|
| 클린 코드 아키텍처 | 읽기 쉬운 코드·명확한 책임·핵심 정책을 보호하는 의존 방향 |
| 확장성과 범용성 | 포트·어댑터와 기능 계약으로 리소스 교체·추가 |
| 최소 코드 | 필요한 동작을 완성하는 가장 단순하고 이해하기 쉬운 구현 |
| 개발 문서화 병행 | 코드와 동작·계약·구조·검증 문서를 함께 갱신 |

## 책임과 의존 방향

패키지는 같은 변경 책임의 모듈을 모으고 모듈·함수는 이름·입출력으로 의도를 드러낸다.
복잡한 조건·긴 함수는 실제 책임을 기준으로 나눈다.
핵심 정책·업무 계약은 포트와 내부 자료형을 기준으로 정의한다.

외부 어댑터가 코어 포트를 구현하고 SDK 객체·오류는 경계에서 변환한다.
인터페이스와 계층은 교체·검증에 필요한 책임 경계에 둔다.
제품의 책임 경계는 [구조 설명](../architecture/overview.md), 구현 디렉터리와 현재 의존 관계는 [패키지 안내](../development/dependencies.md#실행-진입점과-모듈)를 따른다.

## 확장과 단순성

새 리소스는 기능·스키마·제약을 등록하고 공통 계약으로 호출한다.
부처·환경·인스턴스 차이는 설정·계약으로 표현한다.
코어는 기능 계약을 조합하고 업무별 리소스·분석·실행 순서는 에이전트가 승인 범위 안에서 선택한다.

제품별 의미·지원 범위를 드러내고 계약을 처리할 수 있는 조건과 실패 결과를 구분한다.
교체 가능성은 [리소스 계약](../spec/resources/contract.md)을 기준으로 확인한다.
기존 코드·표준 기능을 우선 사용하고 새 의존성의 필요·유지 비용을 설명한다.

핵심 사용자 흐름을 끝까지 완성하고 실제 사용에 필요한 기능·추상화·옵션을 구성한다.
식별자·개정·충돌 처리는 runtime이 관리하고 모델 입력은 수행할 업무에 필요한 값으로 구성한다.
보호 조건은 인증·실제 대상·승인·자료 격리·저장 무결성처럼 현재 기능의 경계를 검증하며 추가 통제는 구체적인 요구와 함께 도입한다.
코드는 의도와 책임이 드러나는 가장 단순한 구조로 작성한다.
같은 정책은 한 원본에서 관리하고 코드 공유는 동일한 변경 책임을 기준으로 판단한다.
경계 분리는 교체·검증·수정 비용을 줄이는 이유가 있을 때 선택한다.

## 입력·실패·권한

외부 입력을 경계에서 검증하고 결과·오류를 계약에 맞춰 반환한다.
거부·미지원·시간 초과·잘림은 해당 상태와 원인·다음 조치로 반환한다.
승인·오류 처리·검증은 경계 계약의 구성 요소로 구현한다.

필요한 최소 권한을 사용하고 실제 호출마다 현재 권한·승인 범위를 검사한다.
검사를 통과한 조건에서 실행하고 검사 실패에는 해당 오류·재개 절차를 반환한다.
비밀값은 인증 저장소의 참조로 등록하고 실제 연결 시점에 해소한다.

민감 자료는 승인·설정의 제공 범위 안에서 필요한 정보만 반환한다.
리소스 자료는 분석 입력으로, 실행 정책은 현재 설정과 승인 기록으로 해석한다.
실제 한도·재시도·중복·복구는 [업무 실행](../spec/tasks/workflow.md), 허용 조건은 [계획·승인](../spec/tasks/approval.md)을 따른다.

## 검증과 의존성

구현 모양보다 관찰 가능한 동작·계약을 검증한다.
코어 정책은 외부 리소스 없이, 어댑터 계약과 실제 연동은 구분해 확인한다.
중요한 허용·거부·실패 경계를 함께 다루고 필요하면 버그 재현 사례로 회귀를 확인한다.

테스트는 관찰 가능한 동작과 실제 실패 위험에 맞춰 구성한다.
실제 검증한 OS·호스트·리소스·버전과 결과를 보고한다.
최적화는 측정한 병목·실제 한도를 근거로 한다.

외부 API는 사용할 버전의 공식 문서를 확인한다.
의존성·설정·인증을 코드와 구분하고 재현 가능한 환경으로 관리한다.
프로그램·지원 버전은 [개발 의존성](../development/dependencies.md)의 정본을 참조한다.
설치 검사·잠금 정보도 그 목록을 기준으로 확인한다.

## 작은 변경과 문서화

한 목적을 완성하는 코드·검증·문서를 함께 변경한다.
리팩터링·표현 수정은 요청의 목적과 영향 범위에 맞춰 진행한다.
계약·동작·설정·사용 방법이 바뀌면 해당 정본을 같은 작업에서 갱신한다.

기능의 정본은 [동작·조건 기술 기준](documentation.md#동작과-조건의-기술)에 따라 작성한다.
개발자가 문서만 읽고 사용자 동작과 관찰 가능한 결과를 설명할 수 있어야 한다.
구현·사양·테스트를 양방향으로 대조해 누락한 기능과 실제보다 넓게 설명한 보장을 함께 확인한다.
호스트의 자연어 판단·Skill 지침과 runtime이 강제하는 조건도 구분한다.

의도한 동작과 구현이 다르면 확정 요구를 기준으로 코드·회귀 검증을 수정한다.
향후 확장 계약은 현재 지원 범위와 구현 조건을 명시한다.
같은 의미의 필드·기본값·enum은 공개 스키마·관리 명령·생성 설정·사양에서 일치시킨다.
대표 검증의 위치는 [구현 범위 표](../development/dependencies.md#구현과-대표-검증)에서 찾는다.

문서는 목적·책임·의존 관계·실패·제약·검증을 설명한다.
주석은 구현 선택의 이유·책임 경계·성립 조건을 설명한다.
Skill·도구 설명·생성 안내도 같은 정본의 계약을 전달한다.
선택은 [기획](planning.md), 문서·Git·인계는 [문서 규칙](documentation.md), 확인은 [검토](review.md)를 따른다.
