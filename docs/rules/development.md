# 개발 원칙

상태: 사용자 지정 기본 원칙 + 상세 개발 기준

DAERI의 구조를 설계하고 코드를 구현·수정·검토하는 사람과 개발 에이전트를 위한 원칙이다.
기본 원칙은 사용자의 지시를 따르며, 상세 기준은 원저자·공식 자료를 프로젝트에 맞게 적용했다.
이 문서의 작성이 구현 단계 시작이나 기술 스택 확정을 뜻하지는 않는다.

## 기본 원칙

| 사용자 지정 원칙 | 적용 기준 |
|---|---|
| 클린 코드 아키텍처 | 읽기 쉬운 코드, 명확한 책임, 핵심 정책을 보호하는 의존 방향 |
| 확장성과 범용성 | 포트·어댑터와 기능 계약으로 리소스를 교체·추가 |
| 최소 코드 | 필요한 동작을 완성하는 가장 단순하고 이해하기 쉬운 구현 |
| 개발 문서화 병행 | 코드 변경과 동작·계약·구조·검증 문서를 함께 갱신 |

## 책임과 의존 방향

모듈과 함수는 하나의 명확한 책임을 갖게 한다.
이름과 입력·출력으로 의도가 드러나도록 작성한다.
복잡한 조건과 긴 함수는 실제 책임을 기준으로 나눈다.

핵심 정책과 업무 계약은 호스트·DB·SDK 같은 외부 구현에 직접 의존하지 않는다.
외부 어댑터가 코어의 포트를 구현하고, 실행 시 구현체를 연결한다.
SDK 객체와 오류는 경계에서 공통 계약에 맞게 변환한다.

의존 방향을 위해 필요한 경계는 유지한다.
모든 함수에 인터페이스를 만들거나 정해진 계층 수·폴더 구조를 강제하지 않는다.
실제 책임 경계는 [구조 설명](../architecture/overview.md)을 따른다.

## 확장성과 범용성

새 리소스는 기능·스키마·제약을 등록하고 공통 계약을 통해 호출한다.
업무 예시마다 코어에 전용 분기나 고정 워크플로를 추가하지 않는다.
부처·환경·대상 인스턴스의 차이는 명시적인 설정과 계약으로 표현한다.

공통 인터페이스를 유지하면서 제품별 의미와 지원 범위를 드러낸다.
지원하지 않는 연산을 같은 의미인 것처럼 변환하거나 성공 처리하지 않는다.
어댑터 교체 가능성은 [리소스 계약](../spec/resources/contract.md)을 기준으로 검증한다.

## 최소 코드와 유지보수성

현재 요구를 완성하는 가장 작은 변경을 선택한다.
기존 기능과 표준 기능을 우선 활용하고, 새 의존성은 필요성과 유지 비용을 설명한다.
사용하지 않는 기능·추상화·옵션·범용 엔진을 미래의 가능성만으로 추가하지 않는다.

줄 수를 줄이기 위해 의도를 숨기거나 여러 책임을 한곳에 몰지 않는다.
같은 정책은 한 원본에서 관리하되, 이름이나 모양만 비슷한 코드를 성급하게 묶지 않는다.
승인 검사·오류 처리·검증처럼 필요한 동작은 최소 코드 원칙으로 생략하지 않는다.

## 명시적인 계약과 실패 처리

외부 입력은 경계에서 검증하고 결과·오류는 계약에 맞춰 반환한다.
접근 거부·미지원·시간 초과·결과 잘림을 빈 성공 결과로 숨기지 않는다.
실패와 부분 완료를 호출자가 구분할 수 있게 한다.

외부 호출에는 시간·검색량·반환량 등 명시적인 실행 한도를 적용한다.
한도는 조회·페이지 처리 과정에서 적용하고 결과 표시만 잘라 제한했다고 판단하지 않는다.
재시도는 안전성과 중복 방지 의미가 확인된 경우에 한해 제한적으로 수행한다.
SDK와 상위 실행기의 중첩 재시도로 호출·부작용·총량이 늘어나지 않는지 확인한다.
자세한 실행·재개 조건은 [업무 흐름](../spec/tasks/workflow.md)을 따른다.

## 권한과 비밀값

필요한 최소 권한을 사용하고 실제 호출마다 권한·승인 범위를 검사한다.
판단 근거가 없거나 확인에 실패하면 허용을 추정하지 않는다.
실제 승인 조건은 [계획·승인 명세](../spec/tasks/approval.md)를 따른다.

비밀값은 모델 입력·로그·오류 메시지·산출물에 넣지 않는다.
민감한 원문은 승인과 설정에서 허용한 범위의 필요한 정보만 제공한다.
조회한 코드·로그·문서의 내용이 실행 지침이나 승인 정책을 바꾸지 못하게 한다.
인증 정보는 사용자 로컬의 참조로 처리한다.

## 변경에 맞는 검증

내부 구현의 모양보다 관찰 가능한 동작과 계약을 검증한다.
핵심 정책은 외부 리소스 없이 확인하고, 어댑터는 공통 계약과 실제 연동을 구분해 확인한다.
수정한 버그는 필요한 경우 재현 사례로 회귀를 확인한다.

승인 전 실행·범위 이탈·실패·재시도·중복 실행 같은 중요 경계는 거부와 허용을 함께 다룬다.
구현을 그대로 반복하는 테스트나 영향이 작은 변경의 형식적인 테스트를 늘리지 않는다.
검증한 OS·호스트·리소스·버전과 결과를 기록한다.

## 의존성, 운영 근거와 성능

외부 API는 사용할 버전의 공식 문서를 확인한다.
의존성·설정·인증 참조를 코드와 구분하고 재현 가능한 환경으로 관리한다.

필요한 프로그램·패키지와 지원 버전은 추후 dependency 목록에서 한 곳으로 관리한다.
현재 구조·기능 명세에는 특정 버전을 지정하지 않고 필요한 역할과 호환성 조건을 설명한다.
목록이 정해지면 설치 검사와 배포의 잠금 정보도 이를 기준으로 검증한다.

업무·계획·호출의 식별자와 결과로 문제를 추적할 수 있게 한다.
이력과 민감 데이터 처리의 기준은 [결과 명세](../spec/tasks/results.md)에 둔다.
성능 최적화는 측정한 병목과 실제 실행 한도를 근거로 한다.

## 작은 변경과 문서화 병행

하나의 목적을 완성하는 단위로 코드·검증·관련 문서를 함께 변경한다.
관련 없는 리팩터링이나 대규모 표현 변경을 섞지 않는다.
현재 요구를 충족하면서 전체 코드의 이해와 수정이 쉬워지는지 검토한다.

동작·계약·설정·사용 방법을 바꾸면 해당 정본을 같은 작업에서 갱신한다.
문서에는 목적, 책임과 의존 관계, 실패·제약, 검증 방법을 설명한다.
코드 주석에는 코드만으로 드러나지 않는 이유와 제한을 남긴다.

구조의 대안 비교와 선택 근거는 [기획 원칙](planning.md)을 따른다.
문서 표현은 [작성](documentation.md)·[Markdown](markdown.md) 원칙을 따른다.
인계와 Git 기록은 [변경 관리](changes.md)를 따른다.

## 원칙 사이의 판단

제품 계약과 안전한 실행 경계를 충족하는 범위에서 단순성을 선택한다.
확정된 어댑터 교체 경계는 유지하고 불확실한 미래 기능은 추가하지 않는다.
경계를 더 나눌 때는 줄 수보다 교체·검증·수정 비용이 줄어드는지 설명한다.

- [Google의 작은 변경 지침](https://google.github.io/eng-practices/review/developer/small-cls.html): 목적을 완성하고 검토할 수 있는 변경 단위.
- [OWASP 권한 검사 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html): 최소 권한·기본 거부·호출마다 권한 검사.
- [AWS의 시간 제한과 재시도 지침](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/): 호출 제한과 재시도 부하·부작용.

자료의 원칙을 DAERI에 적용했으며 특정 언어·프레임워크·모든 도구의 도입을 요구하지 않는다.
